Module 04 · Work like a developer

Stop just writing code.
Learn to work like a developer.

Real development is more than making a page work once. You need a reliable way to save changes, collaborate, understand failures, prove that behaviour works, and recover when something goes wrong. This module builds that workflow from the ground up.

The mental model

A professional workflow is a loop.

You change something, inspect the result, identify problems, fix them, verify the behaviour, and save a meaningful version of the work. Git records the project history. GitHub gives that work a shared home and a collaboration layer. Debugging helps you find why behaviour is wrong. Tests give repeatable checks that protect behaviour as the project changes.

Git

Version control on your machine. It records snapshots of your project and lets you inspect, compare, branch, merge and recover work.

GitHub

A hosted development platform around Git repositories, collaboration, pull requests, issues, review and automation.

Debugging

A disciplined process for turning “something is wrong” into evidence, a cause, a fix and a verification.

Testing

Repeatable checks that compare actual behaviour with expected behaviour. Good tests protect useful behaviour, not implementation trivia.

Developer habit: do not guess for ten minutes when the browser, terminal, Git history or test runner can give you evidence in ten seconds.
01 · Git

Give your project a history you can trust.

Git is a distributed version-control system. A repository stores project history as commits. You can create a repository from a local directory or clone an existing one, then stage and commit changes, inspect history, undo mistakes and work with remotes. The official Git book describes these as the core everyday operations. Git Book.

The three places you need to understand

When learning Git, picture three states rather than memorising commands.

  1. Working tree: the files you are currently editing.
  2. Staging area: the exact changes you have selected for the next commit.
  3. Repository: the committed history stored by Git.

This explains the everyday flow: inspect your changes, choose what belongs together, then create a snapshot.

git status
git diff
git add index.html
git diff --staged
git commit -m "Build learner dashboard"

Start a repository

If you have a project that is not under version control, initialise Git inside its directory. If a repository already exists on GitHub, clone it instead.

# new local project
git init

# existing remote project
git clone https://github.com/OWNER/REPO.git
cd REPO

Do not initialise a new repository inside an existing repository unless you deliberately need a nested repository. For normal projects, one project has one clear repository root.

Commits are meaningful snapshots

A commit should describe a coherent change. Avoid a history full of messages such as “stuff”, “changes”, or “final final”. A useful commit message tells the next reader what changed.

git add .
git commit -m "Add accessible learner form"

# inspect history
git log --oneline --decorate --graph
A commit is not the same thing as a backup file. It is part of a history that lets you inspect how the project changed and move between known states.

Inspect before you commit

Make inspection a habit. git status tells you what Git sees. git diff shows unstaged changes. git diff --staged shows what is currently selected for the next commit.

git status
git diff
git add src/app.js
git diff --staged

Reading the diff before committing catches accidental edits, debug statements and unrelated changes.

Undo without panic

Git has several ways to undo work because “undo” can mean different things. You might want to discard an uncommitted file change, remove something from staging, or create a new commit that reverses an already shared commit.

# remove a file from staging, keep the edit
git restore --staged app.js

# discard an uncommitted change to a file
git restore app.js

# inspect a commit before changing anything
git show HEAD
Careful: commands that discard changes can permanently remove work that has not been committed. Inspect git status and git diff first.

Branches: work without disturbing the main line

A branch is a lightweight movable pointer to a commit. It lets you develop a change separately and later merge it. Git's official documentation describes branches as cheap and encourages branching and merging as part of normal development. Git branching.

git switch -c feature/learner-search
# make changes
git add .
git commit -m "Add learner search"

git switch main
git merge feature/learner-search

Keep a branch focused. One branch for one understandable change is easier to review and easier to recover.

Remotes: share your history

A remote is another copy of the repository that Git knows how to communicate with. After cloning, the usual remote is named origin. fetch downloads remote history without merging it; pull fetches and then integrates according to your configured workflow; push sends your commits to the remote. Git remotes.

git remote -v
git fetch origin
git pull
git push origin main

Understand what is happening before typing a command. “Remote” does not automatically mean “safe backup”; shared history still needs sensible commits and repository permissions.

.gitignore: decide what should not be committed

Some files are generated, local-only or contain secrets. A .gitignore file tells Git which paths to ignore when deciding what is untracked.

node_modules/
.env
.DS_Store
coverage/
Never treat .gitignore as a security system. If a secret was already committed, simply adding it to .gitignore does not erase it from repository history. Rotate exposed credentials and clean history using an appropriate documented process.
02 · GitHub

Turn Git into a collaboration workflow.

GitHub hosts Git repositories and adds collaboration features around them. The key beginner transition is from “I made a change” to “I can propose, review, discuss, test and merge a change”. GitHub's pull-request quickstart recommends creating a branch, making a focused change and opening a pull request for review. GitHub pull-request quickstart.

Repository basics

A repository normally contains the source code, documentation, configuration and history needed to understand the project. Learn to recognise the README, default branch, commits, branches, issues, pull requests and repository settings.

For this course, your FullStack Bible repository is itself a useful laboratory: every module is a real change that can be inspected through Git history.

The pull request workflow

  1. Start from an up-to-date base branch.
  2. Create a focused branch.
  3. Make the change.
  4. Run checks and inspect the diff.
  5. Commit with a useful message.
  6. Push the branch.
  7. Open a pull request.
  8. Review the code and automated checks.
  9. Resolve feedback and update the branch.
  10. Merge when the repository's rules are satisfied.
git switch main
git pull
git switch -c feature/profile-card
# edit files
git add .
git commit -m "Add profile card"
git push -u origin feature/profile-card

Issues and pull requests are different

Issue

A place to describe a bug, task, question or piece of work. It captures the problem or desired outcome.

Pull request

A proposed set of code changes. It is where implementation, discussion, review and checks meet before integration.

Review like an engineer

Do not review only for formatting. Ask whether the change matches its goal, handles important failure cases, preserves accessibility, avoids unnecessary complexity and has appropriate tests. Keep feedback specific and explain the reason when the reason is not obvious.

Small pull requests are easier to understand and review. GitHub's quickstart explicitly recommends keeping a first pull request focused and simple. Source.
03 · Debugging

Replace guessing with evidence.

Debugging is the process of locating and understanding the cause of incorrect behaviour, then changing the program and verifying the result. The goal is not merely to make the error disappear. The goal is to understand why it happened and prevent the same class of problem from returning.

The five-step debugging loop

  1. Reproduce: find a reliable sequence that causes the problem.
  2. Observe: record the visible symptom and exact error message.
  3. Reduce: remove unrelated code or inputs until the problem is smaller.
  4. Hypothesise: state what you think is causing it.
  5. Test: change one relevant thing, rerun the reproduction and verify the result.

If the hypothesis is wrong, that is useful evidence. Update it rather than forcing the code to fit your first guess.

Use the browser's evidence

Chrome DevTools provides tools for inspecting the DOM and CSS, reading console messages, setting JavaScript breakpoints and examining network activity. These tools turn the browser into an investigation environment. Chrome DevTools documentation.

Console

Read errors and warnings. Inspect values. Test small expressions. Avoid leaving random debug logging in production code.

Elements

Inspect the actual DOM and styles the browser is using, not just what you think your HTML and CSS contain.

Sources

Set breakpoints, pause execution, inspect variables and step through code to see what actually happens.

Network

Inspect requests, URLs, methods, status codes, response data, timing and failed requests.

Breakpoints beat console.log for many bugs

When the problem depends on changing values or control flow, pause the program at the interesting line.

function calculateTotal(items) {
  const subtotal = items.reduce((sum, item) => sum + item.price, 0);
  const tax = subtotal * 0.18;
  return subtotal + tax;
}

Place a breakpoint before the calculation and inspect items, subtotal and tax. You are no longer asking “why is the total wrong?” in the abstract; you are checking the exact values at the exact moment they are used.

Common failure categories

  • Syntax error: the program cannot be parsed.
  • Runtime error: execution reaches an operation that fails.
  • Logic error: the program runs but produces the wrong result.
  • State error: the program has the wrong data at the wrong time.
  • Network error: a request fails, returns an unexpected status or receives unexpected data.
  • UI/CSS error: the underlying state may be correct while the rendered result is not.

Classifying the failure narrows the search.

Debugging network requests

async function loadLessons() {
  const response = await fetch("./lessons.json");

  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }

  return response.json();
}

Check the request URL, method, status, response body and browser console. A completed HTTP request is not automatically a successful application operation; your code should handle non-success responses deliberately.

Do not “fix” an error by hiding it. Removing an error message, catching every exception without handling it, or adding random delays can make a bug harder to see. Make the failure observable, understand it, then fix its cause.
04 · Testing

Prove behaviour repeatedly.

A test describes behaviour that should remain true. A useful test has an input or action, an expected result and a clear failure when the expectation is not met. Testing is not a replacement for debugging: debugging investigates a problem; testing gives you repeatable evidence about expected behaviour.

Test levels

Unit

Checks a small piece of logic in isolation, such as a calculation or transformation.

Integration

Checks that multiple parts work together, such as a form handler with storage or an API layer.

End-to-end

Checks a user-visible flow through a real browser, such as opening a page, submitting a form and seeing the result.

Manual testing

A human deliberately explores behaviour that is difficult or expensive to automate. It remains valuable, especially for visual and exploratory work.

What makes a good test?

  • It describes meaningful behaviour.
  • It is isolated enough that one failure has a clear cause.
  • It produces the same result reliably under the same conditions.
  • It fails clearly when the behaviour is broken.
  • It avoids depending on internal implementation details when user-visible behaviour is what matters.

Playwright's guidance specifically recommends testing user-visible behaviour and keeping tests isolated. Playwright best practices.

Start with assertions

An assertion states what you expect to be true. For example, if a learner completes a lesson, the completion count should increase and the completed state should appear in the interface.

// Conceptual example
expect(progress).toBe(70);
expect(completedLesson).toBeVisible();

The exact test framework syntax can vary. The mental model does not: perform a controlled action, observe the result, compare it with the expected result.

End-to-end testing with Playwright

Playwright Test is an end-to-end testing framework for modern web applications. It includes a test runner, assertions, isolation, parallel execution and browser tooling, and supports Chromium, WebKit and Firefox. Playwright documentation.

import { test, expect } from '@playwright/test';

test('learner can complete a lesson', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: 'Complete lesson' }).click();
  await expect(page.getByText('Completed')).toBeVisible();
});

Playwright's web-first assertions wait for the expected state rather than requiring arbitrary manual delays. Writing tests.

Run and debug tests

npx playwright test
npx playwright test --headed
npx playwright test --ui
npx playwright show-report

Playwright supports headless runs, headed runs, UI mode and reports. Its documentation also provides tracing and debugging workflows. Running and debugging tests.

Do not confuse coverage with quality

Coverage can tell you which code was executed by tests, but execution alone does not prove that the right behaviour was checked. A small set of well-chosen tests around important user journeys can be more informative than many shallow assertions.

Capstone · Developer workflow

Build, break, investigate, test, ship.

Use a small version of the learning dashboard from Module 03. Your goal is not to build a huge application. Your goal is to practise the complete developer loop.

Project setup

module-04-capstone/

├── app.js
├── data/

├── tests/
│   └── dashboard.spec.js

Initialise Git, create the first commit, and make the repository understandable before adding features.

Challenge A — Git workflow

  1. Initialise or clone the project.
  2. Create a branch named feature/lesson-status.
  3. Add a lesson list with complete/incomplete state.
  4. Inspect the diff.
  5. Commit the focused change.
  6. Push the branch to GitHub.
  7. Open a pull request with a concise description and testing notes.

Challenge B — Deliberately break it

Introduce at least three controlled bugs:

  • Break a DOM selector.
  • Use the wrong JSON property name.
  • Change the request path so the network request fails.
  • Optionally introduce a logic error in the completion counter.

For each bug, record: symptom → evidence → hypothesis → fix → verification.

Challenge C — Add tests

Write tests for at least these user-visible behaviours:

  1. The dashboard loads its lessons.
  2. A learner can mark a lesson complete.
  3. The completed state is visible.
  4. A failed data request produces a useful error state.

Use stable, user-facing locators where possible. Avoid writing tests that merely assert the exact internal CSS class or JavaScript variable name.

Definition of done

  • Git history contains focused commits.
  • The repository has a useful .gitignore.
  • The change was made on a feature branch.
  • The GitHub pull request explains what changed and how it was tested.
  • At least one bug was investigated with browser evidence.
  • Tests cover important user-visible behaviour.
  • The project handles a failed request without silently breaking.
  • The final branch is clean and the working tree is understood.
Capstone goal: finish knowing not only how to write the code, but how to change it safely, explain it, investigate it and prove that it works.
