01 · Computer basics

Understand the machine you work on.

A developer does not need to be a computer engineer. You do need to know where your work lives, which program opens it, how programs communicate with the operating system, and what the computer is doing when you run something.

The four things to keep separate in your mind

1. Hardware

Hardware is the physical equipment: processor, memory, storage, screen, keyboard, mouse, network hardware and so on. Your programs ultimately run on this physical machine. You do not need to memorise every component. What matters is the practical distinction: hardware is the physical machine; software is the instructions and programs that run on it.

2. Operating system

The operating system is the main software layer that manages the computer and gives other programs a standard way to use it. Windows, macOS and Linux are examples. On a phone, Android and iOS play the same broad role. The operating system manages things such as files, applications, memory, devices, networking and user permissions.

3. Application

An application is a program you use for a particular job. Your browser is an application. Your code editor is an application. A terminal is an application that lets you communicate with the operating system by typing commands. The same file can often be opened by different applications because the file is separate from the application that edits it.

4. Your project

A web project is simply a collection of files organised so that they belong together. At first this may be a folder containing an HTML file. Later it may contain styles, scripts, images, configuration files and many other folders. The project is yours; the editor, browser and terminal are tools you use to work on it.

What you should be able to do before moving on

  1. Install and remove an application without being confused by the process.
  2. Find where an application is installed or where your personal files are stored.
  3. Create a folder and a text file.
  4. Rename, copy, move and delete a file.
  5. Recognise that a file has a name and usually an ending such as .html, .css, .js, .png or .pdf.
  6. Open the same file in the appropriate application and understand that the file itself is not the application.
  7. Know how to connect your machine to the internet and confirm that the browser can reach a website.
Professional habit: learn what each tool is responsible for. If a file is wrong, inspect the file. If the page looks wrong, inspect the browser. If a command fails, inspect the terminal message. Do not randomly change five things at once.
02 · Files, folders & paths

Learn where everything lives.

MDN describes a website as a collection of files that must be assembled into a sensible structure. Learning to handle those files well is not optional: every web project you build will depend on it. MDN: Dealing with files.

File, folder, path: three ideas you must own

A file

A file is a named piece of stored information. An HTML file contains web-page structure. A CSS file contains visual rules. A JavaScript file contains instructions that can make a page interactive. An image file contains image data. The file's ending helps the operating system and applications understand what kind of file it is.

A folder

A folder is a container used to organise files and other folders. Think of it as a drawer. A project folder should contain the things that belong to that project rather than mixing them into your general downloads or desktop.

A path

A path tells you where something is. An absolute path starts from a known starting point on the computer. A relative path describes a location from where you currently are. In web development you will use paths constantly because one file often needs to point to another file.

my-first-site/
  index.html
  images/
    profile.jpg
  styles/
    style.css
  scripts/
    app.js

In this example, index.html is at the project root. The image is inside the images folder. The stylesheet is inside styles. The names are deliberately simple and predictable.

File names that will save you trouble

Use names that tell you what the file contains. Keep names short enough to read and consistent enough to recognise. For beginner projects, lowercase names with hyphens are easy to work with: about.html, contact-page.html, hero-image.jpg. Avoid names that differ only by capital letters, avoid unnecessary spaces, and avoid mysterious names such as final-final-new2.html.

Do not hide the file ending while you are learning. If you intend to create index.html but your editor or file manager secretly creates index.html.txt, the browser will not see the file as an HTML document. Knowing the actual file name prevents hours of unnecessary confusion.

Relative paths: the idea you will use everywhere

Suppose index.html is in the project folder and style.css is inside styles. From index.html, the stylesheet is found at styles/style.css. If a file is one folder deeper and needs to reach its parent folder, .. means “go up one folder”.

project/
  index.html
  styles/style.css
  pages/about.html

From index.html → styles/style.css
From pages/about.html → ../styles/style.css

Do not memorise paths as magic symbols. Read them literally: “start here, enter this folder, then open this file.”

Build a clean first project

Create this exact structure using your file manager before you write serious code:

fullstack-practice/
  module-01/
    first-page/
      index.html
      images/
      styles/
      scripts/
      notes/

Keeping practice work separate from the learning application itself will make later lessons easier to understand. You will know exactly which files you created and why they exist.

03 · How the web works

From tapping a link to seeing a page.

MDN's explanation of the web is the foundation used here: a browser acts as a client, a server provides resources, DNS helps find the server, HTTP carries requests and responses, and the browser assembles the returned files into the experience you see. MDN: How the web works.

First: the internet and the web are not the same thing

The internet is the global network that lets computers and other devices communicate. The web is one service that uses that network. Websites use web technologies to exchange pages, images, scripts, styles and data. Email, online games and other services can use the internet without being websites.

Client and server

Your browser is normally the client in this conversation. A server is a computer or service that receives requests and sends back resources or performs work. When you open a website, your browser asks for something and a server answers. The server might return an HTML document, an image, a CSS file, JavaScript, or data.

Think of it as a restaurant: your browser is the customer placing an order; the server is the kitchen handling the order; the response is what comes back. This analogy is only for intuition. Real web communication has many more details.

What a web address contains

A web address is called a URL. You will see URLs constantly, so learn to read them rather than treating them as mysterious strings.

https://learn.example.com/courses/start?lesson=1#files
│      │              │       │             │
│      │              │       │             └─ page position
│      │              │       └─ extra information
│      │              └─ path to a resource
│      └─ website name
└─ secure web communication

The exact pieces vary, but the important beginner idea is that the URL tells the browser how to communicate and where the requested resource is located.

DNS: finding the computer behind a website name

People prefer names such as developer.mozilla.org. Computers communicate using network addresses. DNS, the Domain Name System, helps translate a website name into the network address needed to contact the right service. You do not manually perform this lookup every time; your device and network software handle it for you.

If DNS cannot resolve a name, the browser may not know where to send the request. That is why a website can fail before any page code is even delivered.

HTTP: the conversation between browser and server

HTTP is the set of rules used for web requests and responses. A browser can send a request asking for a resource. The server answers with a response that includes a status and, when appropriate, the requested content.

For example, GET commonly means “give me this resource”. A response such as 200 means the request succeeded. 404 means the requested resource was not found. 500 indicates a problem on the server side. These numbers are not random; they give software and developers a standard way to understand what happened.

HTTPS: why you see the lock

HTTPS is HTTP protected by encryption. It helps prevent people on the network from simply reading or changing the communication between your browser and the website. It also helps your browser verify that it is communicating with the intended website through a trusted certificate system. You should treat secure communication as the normal expectation for modern websites, especially when accounts, payments or private information are involved.

What happens when you press Enter

  1. You enter a URL or choose a link.
  2. The browser determines where it needs to connect.
  3. DNS may be used to find the network address associated with the website name.
  4. The browser establishes the network connection and sends an HTTP request.
  5. The server receives the request and decides what response to send.
  6. The browser receives the response, which may contain HTML and references to other files.
  7. The browser requests additional resources such as CSS, JavaScript, images and fonts.
  8. The browser processes those resources and builds the page you can see and interact with.

This sequence is simplified, but it is the mental model you need at this stage. MDN's browser-loading guide goes deeper into how the returned files become the rendered page. Read it here.

Important distinction: a website can be reachable while its application is broken. DNS, the network connection, the server, the returned files and the browser are different parts of the journey. Good developers learn to identify which part failed instead of calling everything “the website”.
04 · Browser & developer tools

Turn the browser into an investigation tool.

Every modern browser includes developer tools. MDN describes them as tools for inspecting loaded HTML, CSS and JavaScript, seeing requested resources and debugging code. Chrome's official documentation also provides dedicated DevTools documentation and debugging guidance. MDN DevTools guide · Chrome DevTools.

Open developer tools

On a desktop browser, common options include right-clicking a page and choosing an inspection option, using the browser menu, or using a keyboard shortcut. The exact shortcut differs by browser and operating system. The important thing is not the shortcut; it is knowing that the browser has a built-in workspace for examining what the page is doing.

On mobile browsers, the full developer tools experience is usually provided by connecting the phone to a computer running a desktop browser, or by using a browser-specific remote debugging workflow. You do not need to master remote debugging yet.

The Elements / Inspector area

This area lets you inspect the HTML structure currently loaded in the browser. You can select a visible part of a page and see the corresponding HTML. You can also inspect the visual rules affecting it.

Use it to answer questions such as: “Which element contains this text?”, “Why is this box this wide?”, “Which rule changed this color?”, or “Is this element actually present on the page?”

Changes you make here are normally temporary. They help you investigate and experiment; they do not automatically rewrite your project files.

The Styles area

When you select an element, the browser can show the visual rules currently affecting it. You can temporarily change a value, such as a margin or font size, and immediately see the result. This is one of the fastest ways to learn what a visual rule actually does.

Professional workflow: experiment in the browser first, understand the change, then make the intentional change in your real CSS file. Do not assume a browser experiment has been saved to your project.

The Console

The Console is a place where the browser reports messages and where you can run small JavaScript expressions. It is especially useful when a script fails. Errors often tell you what went wrong and where the browser noticed it.

console.log("Hello from the browser");

If you see an error, read the first useful line carefully. Look for the file name, line number and description. Do not immediately copy the whole error into a search engine without first understanding what the browser is telling you.

The Network area

The Network area shows requests made by the page. This is where you investigate “the browser asked for something, but what happened?” You can see resources such as documents, stylesheets, scripts and images, their status codes, and timing information.

A missing image might show a failed request. A stylesheet that was requested from the wrong location may return a not-found response. A server error may return a 500-series status. This makes Network one of the most useful tools for understanding the path between your files and the browser.

Responsive testing

Desktop browsers can emulate different screen sizes so you can inspect how a page behaves at smaller widths. This is useful because modern websites must work across phones, tablets and computers. Treat this as a testing aid, not proof that a page works perfectly on every physical device.

Your first DevTools investigation

  1. Open any simple website you are allowed to inspect.
  2. Open developer tools.
  3. Select a heading in the page.
  4. Find the HTML element that represents it.
  5. Temporarily change its font size.
  6. Change its color.
  7. Open the Console and run 2 + 2.
  8. Open Network and reload the page.
  9. Find the main document request.
  10. Find at least one image, stylesheet or script request.
Goal: after this exercise, the browser should no longer feel like a black box. You should be able to look inside and ask useful questions.
05 · Files, folders & terminal

Control your project with typed commands.

The terminal is a text-based way to interact with your computer. Instead of clicking through folders, you type instructions. Git's official book also teaches its command-line tools because the command line exposes the full set of Git operations and builds transferable skills. Git: The Command Line.

What you are looking at

When you open Terminal on macOS/Linux or PowerShell/Command Prompt on Windows, you see a prompt. The prompt is simply the computer waiting for your instruction. The location shown by the prompt tells you which folder your next command will operate in.

Different operating systems use slightly different commands. That is normal. The ideas are the same: see where you are, list what is there, move to another folder, create something, inspect it, and remove or move it when necessary.

The essential commands

Where am I?

macOS/Linux: pwd
PowerShell: Get-Location

What is here?

macOS/Linux: ls
PowerShell: Get-ChildItem
Windows Command Prompt: dir

Move into a folder

cd folder-name
Go up one level with cd ...

Create a folder

mkdir practice
Creates a folder named practice.

Read commands as sentences

Do not memorise commands as magic spells. Read them as short instructions.

mkdir fullstack-practice
cd fullstack-practice
mkdir module-01
cd module-01

That means: “make a folder called fullstack-practice; go into it; make a folder called module-01; go into it.” This way of thinking will scale to much more advanced work.

Create and inspect a first HTML file

On macOS/Linux, a simple way to create an empty file is:

touch index.html

On PowerShell:

New-Item index.html

Then list the folder contents and confirm that index.html exists. Open the file in your code editor and put this inside:

<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>My first page</title>
  </head>
  <body>
    <h1>Hello, web.</h1>
    <p>I built my first page.</p>
  </body>
</html>

Save it and open it in your browser. You have now completed the first full loop: create a folder, create a file, write content, save it, and ask a browser to display it.

Moving, copying and deleting

These operations are powerful, so understand them before using them.

# macOS / Linux
cp index.html copy.html
mv copy.html old-index.html
rm old-index.html

PowerShell uses different command names, including Copy-Item, Move-Item and Remove-Item. Windows Command Prompt uses commands such as copy, move and del.

Safety rule: never run a delete command against a folder you do not fully understand. Before deleting, use a listing command and confirm your current location. The terminal does exactly what you tell it to do; it does not know what you meant.

Five terminal habits that make you faster

  1. Use Tab completion. Start typing a file or folder name and press Tab when your terminal supports it. This reduces typing and spelling mistakes.
  2. Use the Up Arrow. It recalls previous commands so you can edit and run them again.
  3. Use clear output when needed. clear is common on macOS/Linux; Clear-Host is available in PowerShell. Windows Command Prompt commonly uses cls.
  4. Read before pressing Enter. Especially when moving or deleting files.
  5. Work from a known project folder. The fewer random locations you use, the fewer path mistakes you make.
06 · Capstone lab

Build your first complete workspace.

This is the point where the separate ideas become one workflow. Do it yourself. Do not copy the finished result and call it complete.

Part A — Create the project

  1. Create a folder named fullstack-module-01.
  2. Open a terminal in that folder or navigate to it with cd.
  3. Create index.html.
  4. Create folders named images, styles, scripts and notes.
  5. Open the project in your code editor.

Part B — Build a simple page

Your page should contain a meaningful title, one main heading, two paragraphs, an unordered list and at least one link. Keep the content about yourself as a learner. Do not worry about visual design yet.

Use semantic HTML elements for their meaning rather than choosing elements because they happen to look a certain way. MDN's HTML module explains that meaningful structure helps browsers, accessibility tools and other systems understand the page. MDN: Structuring content with HTML.

Part C — Investigate your own page

  1. Open the page in your browser.
  2. Open developer tools.
  3. Inspect your main heading.
  4. Temporarily change its appearance in the browser.
  5. Open Console and run a simple calculation.
  6. Reload with Network visible and find the main document.
  7. Resize the page using the responsive device controls.

Part D — Break it on purpose

Professional developers do not learn only by making things work. They learn by understanding failure.

  1. Change the name of your HTML file temporarily and try to open the old address. Observe what happens.
  2. Change a link so it points to a file that does not exist. Inspect the result.
  3. Put a file in the wrong folder and observe the effect of an incorrect path.
  4. Add a small JavaScript error only if you know how to remove it, then inspect the Console.
  5. Fix each problem one at a time.

For every failure, write down: What I expected → What happened → What evidence I found → What I changed → What fixed it.
