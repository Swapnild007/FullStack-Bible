The mental model

The backend is a boundary, not a second frontend.

A backend runs outside the user's browser and is responsible for work that must not be trusted to the client: accessing private data, applying business rules, checking identity and permissions, validating incoming data, and coordinating database or external-service operations. Next.js describes itself as a framework for full-stack web applications, and its App Router supports server-side application code alongside React interfaces. Next.js documentation

01Browser
02HTTP request
03Backend
04Database / services
05Response
Core rule: anything sent by a browser is untrusted. A hidden input, disabled button, client-side TypeScript type, or frontend route guard can improve user experience, but none of them is the final security boundary. The server must make the important decision.

Public code

Frontend code is delivered to users. Never put database passwords, private API keys, or authorization secrets in it.

Server code

Server code can access protected resources and enforce rules before returning a result.

Database

The database persists state and should also enforce important data-integrity rules.

External services

Payments, email, storage, AI, and other providers should be called from controlled server-side boundaries when secrets are required.

01 · APIs

Design the conversation between client and server.

An API is a contract for exchanging data or triggering operations. For web applications, HTTP provides the transport: a client sends a request and a server returns a response. MDN documents HTTP as a client-server protocol and defines standard request/response concepts and status-code classes. MDN HTTP overview

Read an HTTP request

POST /api/lessons HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/json

{
  "title": "Build an API",
  "courseId": "course_123"
}

Think in five questions: where is the request going, what operation is being requested, what metadata accompanies it, what data is being sent, and who is making the request.

Read an HTTP response

HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": "lesson_456",
  "title": "Build an API"
}

Useful status codes include 200 for a successful request, 201 when a resource is created, 204 for success with no response body, 400 for a malformed or invalid request, 401 when authentication is required or failed, 403 when the identity is known but access is not permitted, 404 when the resource is not found, 409 for a conflict, 422 when the server understands the request but cannot process its content in a particular API design, and 500 for an unexpected server failure. Status codes are grouped into 1xx, 2xx, 3xx, 4xx, and 5xx classes. MDN status codes

Resource-oriented API design

There is no single mandatory style for every API, but resource-oriented naming is a useful starting point.

GET    /api/courses
GET    /api/courses/course_123
POST   /api/courses
PATCH  /api/courses/course_123
DELETE /api/courses/course_123

GET    /api/courses/course_123/lessons

Keep the contract predictable. Define what each method accepts, what it returns, which status codes can occur, and which identity or permission is required. Do not expose database tables blindly as public endpoints.

Next.js Route Handlers

With the App Router, Next.js provides Route Handlers for defining server endpoints. They live in a route.ts file inside the app directory and can work with the Web Request/Response APIs.

// app/api/lessons/route.ts
export async function GET() {
  const lessons = await getLessons();
  return Response.json({ lessons });
}

export async function POST(request: Request) {
  const body = await request.json();
  // validate → authenticate → authorize → save
  const lesson = await createLesson(body);
  return Response.json(lesson, { status: 201 });
}

Next.js also notes an important architecture choice: when server-rendered application code already runs on the server, it may access a database directly rather than making a needless internal API request. An API layer is especially useful when a browser, mobile client, or other external consumer needs the endpoint. Next.js data fetching guidance

API errors are part of the contract

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "fields": {
      "title": "Title is required."
    }
  }
}

Return enough information for a legitimate client to recover, but do not expose stack traces, SQL statements, secrets, internal hostnames, or debugging details to users.

CORS is not authentication. CORS controls whether browser JavaScript is allowed to read a cross-origin response. It does not prove that a caller is a trusted user. MDN explains that browsers enforce same-origin restrictions and use CORS headers to permit selected cross-origin access. MDN CORS
02 · Authentication

First answer: who are you?

Authentication verifies an identity. Authorization is a separate decision about what that identity may access or do. Next.js's learning material makes the same distinction: authentication establishes who the user is; authorization determines what they can access. Next.js authentication chapter

Authentication

“Is this request associated with a valid user identity?”

Authorization

“Given that identity, is this action or resource allowed?”

Typical login flow

  1. User submits credentials over HTTPS.
  2. Server validates the request shape.
  3. Server looks up the account without exposing sensitive fields.
  4. Server verifies the password against its stored password hash.
  5. Server creates an authenticated session or another carefully designed credential.
  6. Browser stores or receives the credential according to the chosen security model.
  7. Later requests carry proof of the authenticated session.
  8. Server verifies that proof before serving protected data.

OWASP recommends treating authentication and session management as security-sensitive systems rather than as a simple login form. Sessions need unpredictable identifiers, controlled lifetime, secure invalidation, and appropriate cookie protections. OWASP Authentication Cheat Sheet OWASP Session Management

Passwords are verified, not stored

Never store a user's password as plaintext. Password storage should use a password-specific, deliberately slow hashing algorithm with a unique salt. OWASP currently recommends Argon2id for new password storage where available, with scrypt as an alternative and bcrypt mainly for legacy situations. Fast general-purpose hashes such as SHA-256 are not appropriate password-storage algorithms because attackers can guess them too quickly. OWASP Password Storage

// Conceptual flow — use a vetted library in real code
storedHash = passwordHasher.hash(password)

// At login
valid = passwordHasher.verify(password, storedHash)
Do not invent cryptography. Do not write your own password-hashing algorithm, session-token generator, encryption scheme, or authentication protocol when a well-maintained security library or established identity provider is appropriate.

Sessions and cookies

A session lets the server associate later requests with an authenticated user. A common web pattern is an opaque session identifier in a cookie; the server maps that identifier to session state. Cookies can be configured with security attributes such as HttpOnly, Secure, and an appropriate SameSite policy. MDN documents Set-Cookie as the response mechanism by which a server asks the browser to store a cookie. MDN Set-Cookie

Set-Cookie: session=opaque-random-id;
  HttpOnly;
  Secure;
  SameSite=Lax;
  Path=/

HttpOnly prevents normal frontend JavaScript from reading the cookie. Secure restricts it to secure transport. SameSite controls when the browser includes the cookie in cross-site contexts. Exact settings depend on the application's architecture.

Tokens are not magic

You will encounter bearer tokens, signed tokens, and OAuth/OIDC flows. The important lesson is that possession of a bearer credential is powerful: whoever has it may be treated as the user. Token storage, expiry, rotation, audience, issuer, signing keys, revocation strategy, and transport all matter.

For a first-party browser application, do not choose JWTs simply because they are popular. Understand the threat model and use the authentication solution recommended for your framework and architecture. Next.js's own learning material demonstrates using an established authentication library rather than hand-building the entire session system. Next.js authentication

Logout and session lifecycle

  • Invalidate the server-side session when using server-managed sessions.
  • Expire credentials appropriately.
  • Regenerate or rotate session identifiers when the authentication state changes where your session architecture requires it.
  • Protect password-reset and account-recovery flows with the same care as login.
  • Require re-authentication or stronger verification for particularly sensitive operations when appropriate.
03 · Authorization

Then answer: what may you do?

Authorization is an access-control decision. A logged-in user is not automatically allowed to read every record or call every operation. OWASP recommends least privilege and deny-by-default access control, with authorization enforced server-side. OWASP Authorization Cheat Sheet

Start with explicit rules

UserActionResourceDecision
GuestReadPublished lessonAllow
LearnerReadEnrolled courseAllow
LearnerEditAnother learner's profileDeny
InstructorEditOwned courseAllow
LearnerDeleteCourseDeny
AdminManageSystem settingsAllow

Do not let the browser decide the final answer. A UI can hide a Delete button, but the server must reject an unauthorized DELETE request too.

Roles are useful, but not the whole problem

Role-based access control (RBAC) can express broad rules such as “admins can manage users.” But real applications often need object-level checks: “this instructor can edit this course because they own it.” That second decision depends on the relationship between the user and resource, not just a role.

const user = await requireUser(request);
const course = await getCourse(courseId);

if (!course) return notFound();
if (course.ownerId !== user.id && user.role !== 'admin') {
  return forbidden();
}

// Only now perform the mutation.

Prevent IDOR / object-level access failures

Never assume that knowing an ID grants access to the object. If a request says /api/users/123/profile, the server must check whether the current identity is allowed to access user 123. Changing the URL or request body must not bypass the rule. OWASP's secure-code-review guidance explicitly calls for server-side authorization, default-deny controls, and protection against insecure direct object reference patterns. OWASP secure code review

Useful sequence: authenticate the request → load the resource → authorize the specific action on that resource → perform the action. Do not treat “logged in” as equivalent to “allowed.”
04 · Validation

Do not trust the shape of incoming data.

Validation checks whether incoming data is acceptable before the application uses it. OWASP recommends validating untrusted input as early as possible and distinguishes syntactic validation—whether the data has the correct shape—from semantic validation—whether the value makes sense for the business rule. OWASP Input Validation

Client validation and server validation have different jobs

Client

Fast feedback, better forms, fewer accidental mistakes, better user experience.

Server

Security and correctness boundary. The server validates before processing or persisting the data.

A user can disable JavaScript, modify a request in DevTools, call the endpoint directly, or use a completely different client. Therefore client-side validation can never replace server-side validation.

Syntactic validation

title: string
minimum length: 1
maximum length: 120
courseId: valid identifier
level: one of "beginner" | "intermediate" | "advanced"
completed: boolean

Use strong types, explicit ranges, length limits, and allowlists for fixed choices. Avoid relying on a denylist such as “reject anything containing suspicious characters.” OWASP specifically warns that denylisting is easy to bypass and recommends allowlist validation as the stronger primary approach. OWASP validation strategies

Semantic validation

startDate must be before endDate
price must be >= 0
course must exist before lesson is created
learner cannot enroll twice
only an owner can edit their course

Notice that the last two rules involve database state and authorization. Validation is not one giant function; it is a set of checks at the correct boundaries.

Validate at the boundary, then use typed data

type CreateLessonInput = {
  title: string;
  courseId: string;
  level: 'beginner' | 'intermediate' | 'advanced';
};

// request body is unknown until validated
const input: CreateLessonInput = parseAndValidate(body);

// only validated data crosses this boundary
await createLesson(input);

TypeScript types describe what your program expects; they do not automatically validate JSON arriving over the network at runtime. Runtime validation is still required at external boundaries.

Database constraints are another line of defense

API validation protects the application workflow, while database constraints protect stored data. For example, a unique constraint can prevent duplicate emails even if two requests race each other. A foreign key can prevent a lesson from referencing a nonexistent course. A check constraint can reject an invalid value even if an application bug tries to write it.

05 · Secure backend thinking

Security is a system of boundaries.

Authentication, authorization, validation, database constraints, transport security, session management, and error handling work together. None should be treated as a single “security feature.”

HTTPS

Protect credentials and application traffic in transit. Never design a login flow around plaintext HTTP.

CSRF

If browser credentials such as cookies are automatically attached to requests, state-changing operations need appropriate CSRF defenses. OWASP documents synchronizer-token patterns and other mitigations.

Rate limiting

Limit abusive request patterns, especially around login, password recovery, expensive operations, and public APIs.

Secrets

Keep database credentials, signing keys, and provider secrets out of source code and client bundles. Use environment variables or a dedicated secret-management system as appropriate.

Cookie-based sessions and CSRF

Cookies are automatically attached according to browser cookie rules. That convenience means a malicious site may sometimes cause a browser to send a credentialed request even though it cannot read the response. CSRF defenses ensure a state-changing request was intentionally initiated by your application. OWASP documents synchronizer tokens as a common defense for cookie-authenticated applications and recommends unpredictable, secret tokens validated by the server. OWASP CSRF Prevention

Do not leak internal failures

// Good public response
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "Something went wrong."
  }
}

// Keep stack traces, SQL details, secrets and internal paths
// in protected server logs—not in the API response.

A disciplined request pipeline

  1. Parse the HTTP request.
  2. Apply request-size/content-type limits where appropriate.
  3. Validate input shape and business constraints.
  4. Authenticate when the endpoint is protected.
  5. Authorize the specific action and resource.
  6. Perform the database or service operation.
  7. Return a documented response and appropriate status code.
  8. Log security-relevant failures without logging secrets or passwords.
Important nuance: the exact order can vary by application. For example, some systems authenticate before detailed validation to avoid exposing information about protected resources. What matters is that every trust boundary has an explicit control and that sensitive decisions happen on the server.
Capstone lab

Build the Learning Hub backend.

Extend the application from Modules 07 and 08 into a backend that can safely serve learners, courses, lessons, and enrollments. You are not finished when the endpoint returns JSON; you are finished when its contract, identity checks, permission checks, validation, data rules, and failure states are understandable.

Build these API operations

EndpointPurposeProtection
GET /api/coursesList published coursesPublic
GET /api/courses/:idRead a coursePublic if published

PATCH /api/courses/:idEdit a courseOwner/Admin

Authentication work

  1. Create a registration/login design using a vetted password-hashing library or an established authentication provider.
  2. Store only the password hash, never the original password.
  3. Create a secure authenticated session.
  4. Protect the session cookie appropriately for the deployment.
  5. Implement logout and session invalidation.
  6. Return generic authentication failures so you do not unnecessarily reveal whether a particular account exists.

Authorization work

  • Guest: can view public published content.
  • Learner: can manage their own enrollment and learning state.
  • Instructor: can create courses and edit courses they own.
  • Admin: can manage all courses and users.
  • Every protected object must be checked on the server.
  • Try changing IDs manually and confirm that another user's resources remain inaccessible.

Validation work

POST /api/courses

{
  "title": "   ",
  "level": "super-expert",
  "price": -50
}

Expected result:
400 or 422 according to your documented API contract

No invalid course is written to the database.

Test missing fields, wrong types, extra fields where your contract rejects them, extreme lengths, invalid enum values, nonexistent foreign keys, duplicate enrollment, and unauthorized ownership changes.

Attack-minded tests

  1. Call a protected endpoint without authentication.
  2. Call it as a different authenticated user.
  3. Change a resource ID in the URL.
  4. Modify a hidden or supposedly read-only field.
  5. Send invalid JSON.
  6. Send very large strings or unexpected arrays.
  7. Try repeated login failures and observe rate limiting.
  8. Inspect cookies and confirm sensitive session data is not readable by ordinary page JavaScript when using an HttpOnly session cookie.
  9. Inspect API error responses and confirm they do not expose stack traces or secrets.
  10. Verify database constraints still reject invalid state even if application validation is bypassed.

Definition of done

You should be able to draw one complete request on paper: browser → HTTP request → route handler → validation → authentication → authorization → database → response. Then explain what happens when each step fails.
