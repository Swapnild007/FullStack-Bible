01 · Plan

Build the right thing before building it beautifully.

A product begins with a problem, a user, and an outcome—not a framework. Your job is to turn an ambiguous idea into a small, testable product definition. GitHub Issues can be used to capture bugs, features, ideas, and work; GitHub Projects can organize that work as it evolves.

Start with the problem

Write the situation in plain language. Who has the problem? What are they trying to accomplish? What makes the current approach difficult? What evidence tells you the problem is worth solving?

Problem statement

“A learner who is building a full-stack project needs one place to track lessons, practice tasks, project work, and progress because scattered notes make it difficult to know what to do next.”
Do not start with: “I want to build a React/Next.js/AI app.” Technology is an implementation decision. The user problem comes first.

Define the smallest useful product

An MVP is not a low-quality product. It is the smallest version that can test a meaningful assumption with real users.

  1. List the user outcome.
  2. Identify the one core workflow that creates that outcome.
  3. Remove features that do not support that workflow.
  4. Define what “done” means before coding.

Write acceptance criteria

Turn a feature into observable behavior. “Build a dashboard” is vague. “A signed-in learner can mark a lesson complete and still see it completed after refreshing the page” can be tested.

Feature: lesson completion

Given a signed-in learner is viewing a lesson
When they select “Complete lesson”
Then the lesson is stored as completed
And the dashboard reflects the updated progress
And refreshing the page preserves the state

Plan the work

Break the product into vertical slices that each produce a working outcome. Use issues for concrete work, keep changes focused, and connect implementation work to the product requirement. GitHub's current workflow guidance describes branches, commits, pull requests, review, checks, and merge as the normal collaboration loop.

02 · Build

Build in thin, complete slices.

You already know HTML, CSS, JavaScript, TypeScript, React, Next.js, PostgreSQL, APIs, authentication, security, testing, deployment, and AI. Now combine them instead of learning another framework for its own sake.

Every boundary should have a reason. Keep secrets on the server. Validate untrusted input at the boundary. Authorize access to the actual resource. Let the database enforce important invariants.

Build the vertical slice

  1. Create the data model needed for one workflow.
  2. Create the backend operation.
  3. Add authentication and authorization where required.
  4. Validate input on the server.
  5. Build the UI.
  6. Add loading, empty, success, and error states.
  7. Test the complete workflow.
  8. Only then move to the next slice.
Why? A product can have ten polished screens and still fail because its central workflow does not work. Vertical slices expose integration problems early.

Keep product decisions visible

Record important decisions in short notes: why the feature exists, what was intentionally excluded, what data is stored, what assumptions remain unproven, and what would cause you to change direction. This prevents the codebase from becoming the only source of truth.

Use AI without handing over ownership

Module 11 taught AI-assisted development. In a real product, apply the same discipline: ask AI to explain alternatives, generate bounded changes, write tests, inspect failures, and challenge assumptions. Review every consequential change yourself. Your product requirements, security model, tests, and release process remain human-owned.

03 · Test

Test the product, not just the code.

A product is more than functions passing unit tests. Test the workflows users depend on, the failure paths they will encounter, and the security boundaries that protect their data.

Unit

Does a focused function or component behave correctly across important inputs?

Integration

Do application pieces work together correctly across database, API, authentication, and validation boundaries?

End-to-end

Can a real user complete the important workflow from the interface through the backend?

Security

Can a user access only what they are allowed to access? Do invalid and hostile inputs fail safely?

Use security testing as part of delivery

The OWASP Web Security Testing Guide is a comprehensive framework for testing web applications and web services. Use it as a reference when designing security test cases rather than treating security as a final checkbox.

Release blocker: a feature that works but exposes another user's data is not “almost finished.” The security boundary is part of the feature's definition of done.

Test the production configuration

Development behavior can differ from production. Test the production build, production-like environment variables, database migrations, caching behavior, logging, error handling, and deployment process before launch.

04 · Launch

Shipping is an engineering process.

Launching means moving from a controlled development environment to real users and real consequences. Next.js documentation describes deployment options for full-stack applications, while its learning material demonstrates a Develop → Preview → Ship workflow with branch-based preview deployments.

Pre-launch checklist

  • Production build succeeds.
  • Environment variables are configured without exposing secrets.
  • Database migrations have been tested and a rollback/recovery plan exists.
  • Authentication and authorization have been tested.
  • Critical workflows have automated tests.
  • Accessibility has been checked on important flows.
  • Error logging and monitoring are available.
  • Backups and recovery expectations are understood.
  • Analytics or product measurement captures only what you actually need.
  • There is a clear owner for responding to failures and user reports.

Preview before production

Use a branch for a focused change, commit meaningful snapshots, open a pull request, run automated checks, review the diff, and validate the preview before merging. GitHub describes pull requests as the place to discuss and review changes before they enter the project, with checks and changed-file review built into the workflow.

Release safely

For a risky change, prefer a reversible release. Separate deployment from feature exposure when your architecture allows it. Use migrations that can be rolled forward safely, monitor the first period after release, and have a documented rollback path.

Launch rule: “deployed” means the software is running. “launched” means users can use it and you can observe, support, and recover it.

Security is part of product delivery

NIST's Secure Software Development Framework organizes secure development around preparing the organization, protecting software, producing well-secured software, and responding to vulnerabilities. The current NIST project page also lists a newer SP 800-218 Revision 1 draft, so treat the framework as an evolving practice rather than a one-time checklist.

05 · Improve

The first launch is the start of the learning loop.

Once users interact with the product, replace assumptions with evidence. Improvement is not “add more features.” It is learning which changes make the product more useful, reliable, understandable, and sustainable.

01Observe
02Learn
03Change
04Measure

Measure the right signals

Activation

Do new users reach the first meaningful outcome?

Engagement

Do users return because the product remains useful?

Reliability

Are errors, failed requests, and outages within acceptable bounds?

Outcome

Is the product actually solving the problem it was created to solve?

Do not worship metrics. A number is evidence, not an explanation. Combine quantitative signals with support conversations, interviews, usability observations, and direct feedback.

Prioritize deliberately

When many things could change, compare them using evidence: user impact, confidence in the problem, implementation cost, risk, and strategic relevance. Keep a short queue of validated work rather than an endless feature wishlist.

Run an improvement cycle

  1. Write the observed problem.
  2. Identify the evidence.
  3. Form a specific hypothesis.
  4. Ship the smallest useful change.
  5. Measure the result.
  6. Keep, revise, or remove the change.
Final capstone · FullStack Bible

Build, ship, and improve one real product.

Your final project combines the entire roadmap. You are not graded on how many technologies you can name. You are demonstrating that you can take a real problem through a complete software lifecycle.

Product brief

  1. Choose one real problem you understand.
  2. Define one primary user.
  3. Write the desired outcome.
  4. Define the smallest useful version.
  5. Write acceptance criteria.
  6. Design the data model.
  7. Build the core vertical slice.
  8. Add authentication, authorization, and validation where required.
  9. Add tests for the critical workflow and failure paths.
  10. Run a production build and security/performance checks.
  11. Deploy a preview.
  12. Launch to a small real audience.
  13. Collect evidence.
  14. Ship one improvement based on that evidence.
