Before you begin

Learning objectives

Network security becomes much easier when packets stop looking like mysterious lines in a dashboard. This chapter builds the path from an application's data to frames, packets, segments, encrypted sessions and observable telemetry.

  • Explain layers and encapsulation without treating the OSI model as a literal implementation map.
  • Understand Ethernet, MAC addresses, ARP and local-network trust.
  • Explain IPv4, IPv6, subnetting, routing and fragmentation concepts.
  • Understand TCP state, reliability, flow control and congestion control.
  • Understand UDP, QUIC and when applications choose them.
  • Explain DNS, DHCP, BGP and routing trust.
  • Understand TLS 1.3 and certificate-based endpoint authentication.
  • Explain HTTP, proxies, firewalls, NAT and segmentation.
  • Read packet telemetry conceptually and correlate network evidence with processes and identities.
Mental model: a network is a distributed system in which independent machines make assumptions about addresses, identities, state and messages. Security depends on which of those assumptions are authenticated, encrypted, observable and enforceable.
Chapter 01

Layers, encapsulation and the journey of data

Applications do not send “packets” directly. They create application data, which is transformed by several protocol layers before transmission.

1.1 TCP/IP versus OSI

The TCP/IP model groups practical internet protocols into application, transport, internet and link layers. The seven-layer OSI model is useful as a conceptual vocabulary, but real implementations do not map one-to-one onto seven independent boxes.

1.2 Encapsulation

Suppose an application sends an HTTP request. HTTP creates application data. A transport protocol such as TCP adds transport metadata. IP adds source and destination addressing. Ethernet or another link technology adds link-layer information.

application data → transport segment/datagram → IP packet → link-layer frame

At the receiver, the process is reversed: each layer interprets its own metadata and passes the payload upward.

1.3 Security boundaries

Each layer has different trust assumptions. Encryption at one layer does not automatically protect metadata at every other layer. A TLS connection can protect application content while IP addresses, timing and traffic volume remain observable.

1.4 Why analysts need layers

When a network event appears suspicious, ask which layer is abnormal. An unexpected TCP state transition is different from a malicious HTTP request, and a routing anomaly is different from a DNS manipulation event.

Chapter 02

Ethernet, MAC addresses and local-network trust

2.1 Frames and MAC addresses

Ethernet moves frames across a local link. A MAC address identifies a network interface at the link layer; it is not a global identity and should not be treated as proof of who owns a device.

2.2 Switching

Ethernet switches learn which MAC addresses appear on which ports and forward frames accordingly. Broadcast and unknown-destination behavior means some traffic can be visible beyond the final destination under appropriate conditions.

2.3 VLANs

VLANs create logical Layer-2 segments. They can reduce broadcast scope and support network design, but VLAN configuration is not a substitute for application authentication or encryption.

2.4 Local attacks as trust failures

MAC spoofing, ARP manipulation and rogue network devices demonstrate a common principle: link-layer identifiers are not automatically authenticated identities. Defenses include switch controls, segmentation, authenticated higher-layer protocols and monitoring for unexpected changes.

Chapter 03

ARP and neighbor discovery

IPv4 hosts need a way to map an IP address to a local link-layer destination. ARP provides that mapping on Ethernet-like networks.

3.1 ARP operation

A host can broadcast a request asking which device owns an IPv4 address; the owner responds with its link-layer address. Hosts cache these mappings to avoid repeating the exchange for every packet.

3.2 Why ARP is security-sensitive

Classic ARP does not provide strong cryptographic authentication of replies. An attacker with suitable local access may attempt to insert false mappings. The resulting traffic redirection can enable interception or denial of service.

3.3 IPv6 neighbor discovery

IPv6 uses Neighbor Discovery Protocol (NDP), which is built on ICMPv6 rather than ARP. NDP has its own security considerations, including router and neighbor-advertisement trust.

Defensive lesson: encryption at the application layer can reduce the value of local traffic interception, but it does not eliminate the availability and routing consequences of local-layer manipulation.
Chapter 04

IPv4, IPv6, subnets and packet forwarding

4.1 IP addressing

IP provides addressing and routing between networks. IPv4 uses 32-bit addresses; IPv6 uses 128-bit addresses. Neither protocol, by itself, establishes the real-world identity of the sender.

4.2 Subnetting

A subnet divides an address space into a network prefix and host portion. CIDR notation expresses the prefix length, such as 192.0.2.0/24 or 2001:db8::/32. Documentation ranges such as these are useful for examples without referring to real systems.

4.3 Routing

A router selects a next hop based on its forwarding information. The packet's destination address is evaluated against routes, commonly using longest-prefix matching.

4.4 TTL and Hop Limit

IPv4 TTL and the IPv6 Hop Limit reduce the chance that packets circulate indefinitely. Each forwarding hop decrements the value; when it reaches the relevant limit, the packet is discarded.

4.5 Fragmentation

IPv4 and IPv6 handle fragmentation differently. IPv4 routers may fragment packets under applicable conditions, while IPv6 places fragmentation responsibility on the source using an extension header. Path MTU Discovery helps endpoints avoid inappropriate packet sizes.

Chapter 05

TCP: state, reliability, flow and congestion

TCP is a connection-oriented transport protocol that provides an ordered byte stream with reliability mechanisms.

5.1 Three-way handshake

SYN → SYN/ACK → ACK

The handshake establishes initial sequence-number state and confirms that both endpoints can participate in the connection. It is not itself an authentication mechanism.

5.2 Sequence numbers and acknowledgements

TCP numbers bytes so the receiver can acknowledge what arrived and the sender can retransmit missing data. This creates a reliable stream above an unreliable IP layer.

5.3 Flow control

The receive window communicates how much additional data the receiver can accept. Window scaling allows larger effective windows on high-bandwidth, high-latency networks.

5.4 Congestion control

TCP congestion control responds to network conditions rather than simply sending as fast as possible. Algorithms differ across implementations and versions, but the goal is to avoid persistent network overload while maintaining useful throughput.

5.5 TCP states

Important states include LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT, CLOSE-WAIT and TIME-WAIT. State transitions are valuable telemetry because unexpected patterns can indicate broken applications, scanning, exhaustion or other anomalies.

5.6 Security implications

SYN floods exploit the resources consumed by partially established connections. Defenses can include SYN cookies, connection limits, load balancing and upstream filtering. No single control solves every availability attack.

Chapter 06

UDP, QUIC and modern transport

UDP provides a minimal datagram transport without TCP's built-in reliability and connection semantics.

6.1 UDP

UDP carries datagrams identified by source and destination ports. It does not guarantee delivery, ordering or duplicate suppression. Applications that need those properties must implement them themselves or use a protocol above UDP.

6.2 Why applications use UDP

Real-time media, DNS and many specialized protocols benefit from low overhead or application-controlled behavior. Losing a packet can sometimes be preferable to waiting for retransmission of old data.

6.3 QUIC

QUIC runs over UDP but implements reliable streams, congestion control and cryptographic handshake behavior in the protocol. HTTP/3 uses QUIC as its transport. This means “UDP traffic” is not necessarily simple or unauthenticated application traffic.

6.4 Security visibility

Encrypted modern transports change what network sensors can infer. Defenders increasingly need endpoint telemetry and metadata such as destination, timing, process identity and connection patterns rather than relying on payload inspection alone.

Chapter 07

DNS: names, delegation and trust

7.1 Resolution

DNS is a distributed naming system. Recursive resolvers obtain answers from authoritative servers and cache them according to TTL values. Records include A, AAAA, CNAME, MX, NS, TXT and others.

7.2 Recursive versus authoritative

A recursive resolver performs resolution on behalf of clients. An authoritative server provides answers for zones for which it is authoritative. Keeping those roles conceptually separate helps analysts understand where an answer originated.

7.3 DNS security

DNSSEC adds cryptographic authentication of DNS data through signed records and a chain of trust. It does not encrypt the resolver conversation. DoH and DoT encrypt DNS transport to a resolver, improving privacy of that channel but not replacing DNSSEC's data-authenticity function.

7.4 DNS cache poisoning

Cache poisoning attempts to cause a resolver or client to retain an incorrect answer. Defenses include DNSSEC where applicable, source-port and transaction-ID protections, secure resolver configuration and monitoring for suspicious changes.

7.5 DNS as telemetry

DNS is useful security evidence because many applications resolve names before connecting. Query volume, newly observed domains, unusual record types, failed resolution and process-to-domain relationships can provide context.

Chapter 08

DHCP and network configuration trust

DHCP can provide addresses, routes, DNS resolvers and other network configuration automatically.

8.1 Basic exchange

A simplified DHCPv4 exchange is often remembered as DORA: Discover, Offer, Request, Acknowledge. The exact message flow varies with state and options.

8.2 Rogue DHCP

A rogue DHCP service can provide incorrect configuration to clients. The danger is not the protocol name; it is that clients may trust network-provided configuration without independently authenticating its source.

8.3 Defensive controls

Switch-level DHCP snooping, segmentation, authenticated management and monitoring can reduce risk. Endpoint behavior should also be monitored for unexpected gateway or resolver changes.

Chapter 09

Routing, BGP and the trust of the Internet

9.1 Routing inside organizations

Interior routing protocols distribute reachability information within an administrative domain. Policy, topology and convergence determine how traffic moves.

9.2 BGP

The Border Gateway Protocol exchanges reachability information between autonomous systems. BGP is policy-driven and does not inherently provide strong cryptographic proof that every route announcement represents the intended origin.

9.3 RPKI and route origin validation

Resource Public Key Infrastructure can provide cryptographic authorization data for route origins. Route Origin Validation can then classify announcements against those authorizations. This improves protection against certain route-origin problems but does not solve every routing-security issue.

9.4 Security lesson

Routing demonstrates a recurring network principle: reachability and identity are different. Knowing where a packet was routed does not automatically prove who originated its application data.

Chapter 10

TLS 1.3, certificates and encrypted trust

TLS protects application traffic by combining cryptographic key establishment, integrity protection and endpoint authentication.

10.1 What TLS provides

Correctly configured TLS provides confidentiality and integrity for the protected connection and can authenticate a server using certificates. Client authentication is optional and depends on the application.

10.2 TLS 1.3 handshake

TLS 1.3 uses ephemeral key exchange in normal deployments, providing forward secrecy when ephemeral parameters are not compromised. The handshake negotiates cryptographic parameters and establishes traffic keys before protected application data is exchanged.

10.3 Certificates

X.509 certificates bind public keys to identities through a certificate chain. A client validates the chain toward a trusted root and checks relevant constraints such as hostname, validity and key usage.

10.4 What TLS does not hide

Traditional TLS does not make the existence of a connection invisible. IP addresses, packet sizes, timing and traffic volume can remain observable. Some protocol metadata has additional privacy mechanisms, but visibility varies by protocol and deployment.

Key distinction: encryption protects data in transit; authentication answers who the protocol endpoint is expected to be. You need both for a meaningful secure channel.
Chapter 11

HTTP, HTTP/2 and HTTP/3

11.1 HTTP semantics

HTTP defines requests and responses, methods such as GET, POST, PUT, PATCH and DELETE, status codes, headers and representations. Security depends heavily on how applications interpret these semantics.

11.2 HTTP/1.1

HTTP/1.1 uses a textual request/response format and persistent connections. Head-of-line effects can occur when multiple requests share transport behavior.

11.3 HTTP/2

HTTP/2 uses binary framing and multiplexes multiple streams over a connection. Header compression reduces overhead. Application semantics remain HTTP.

11.4 HTTP/3

HTTP/3 maps HTTP semantics onto QUIC streams. This changes transport behavior while preserving the application-layer model.

11.5 Security analysis

Inspect method, path, authority, headers, authentication context, content type and response behavior. A network sensor that sees encrypted TLS payloads may need endpoint or reverse-proxy telemetry to obtain application-level evidence.

Chapter 12

Firewalls, NAT, proxies and segmentation

12.1 Firewalls

Firewalls enforce traffic policy based on attributes such as addresses, ports, protocol state and sometimes application identity. Stateful firewalls track connection state rather than evaluating each packet independently.

12.2 NAT

Network Address Translation changes address/port information as traffic crosses a boundary. NAT can conserve IPv4 address space and influence reachability, but it is not equivalent to a security policy.

12.3 Forward and reverse proxies

A forward proxy acts on behalf of clients. A reverse proxy sits in front of servers and can provide TLS termination, routing, authentication integration, rate limiting and observability.

12.4 Segmentation

Segmentation reduces the paths available for lateral movement and limits blast radius. Strong segmentation is based on explicit trust relationships rather than assuming that an internal network is inherently trusted.

Chapter 13

Packet telemetry: from bytes to evidence

Packet capture is evidence, not an automatic verdict. Analysts interpret headers, protocol state, timing and application context to form a defensible conclusion.

13.1 What a packet capture can reveal

Depending on encryption and capture location, evidence may include source/destination addresses, ports, protocol flags, packet sizes, timing, retransmissions, DNS metadata, TLS handshake metadata and application payloads.

13.2 Wireshark and tcpdump

Wireshark provides interactive protocol dissection and filtering. tcpdump provides lightweight command-line capture and filtering. Both are most useful when the analyst knows the protocol expected and the security question being tested.

13.3 Zeek

Zeek converts network traffic into structured logs such as connections, DNS, HTTP and TLS observations. This is useful when organizations need durable telemetry rather than storing every raw packet indefinitely.

13.4 Scapy

Scapy is a programmable packet-manipulation framework useful for authorized protocol research and testing. Its educational value comes from understanding how protocol fields and state interact.

13.5 Correlation

The strongest network evidence is correlated with endpoint process identity, user identity, DNS resolution, authentication events and application logs. A connection to an unusual address means something different when it belongs to an expected update service versus an unsigned unknown process.

Chapter 14

Network detection engineering

14.1 Start with a hypothesis

Examples include “a workstation is making repeated connections to a new external destination” or “a server is receiving unexpected inbound traffic.” A detection should state what evidence would support or weaken the hypothesis.

14.2 Indicators versus behavior

An IP address, domain or hash is an indicator. Indicators can change quickly. Behavioral patterns such as unusual beacon timing, process-to-network relationships or protocol misuse can be more durable.

14.3 False positives

Legitimate software can generate unusual traffic. Detection quality improves through allowlists with ownership, asset context, identity, process information, destination reputation and historical baselines.

14.4 Response linkage

A detection is operationally useful when it leads to an action: investigate, isolate, block, revoke credentials, patch, change policy or continue monitoring. Detection without response ownership becomes dashboard noise.

Mastery review

20 questions — with answers

Answer each question yourself first, then open the explanation.

01 · What is encapsulation?
Answer: Encapsulation is the process by which each network layer adds its own metadata around data from the layer above.

Why: It lets protocols perform different jobs independently while still moving one application message across a network.
02 · Why is a MAC address not a strong identity?
Answer: A MAC address identifies a link-layer interface value, not a cryptographically verified person, device owner or application identity.

Why: Higher-layer authentication is still required when identity matters.
03 · What problem does ARP solve?
Answer: ARP maps an IPv4 address to a link-layer address on a local network.

Why: IP forwarding on a local Ethernet segment requires the sender to know where to deliver the frame.
04 · What is the difference between IPv4 and IPv6?
Answer: IPv4 uses 32-bit addressing; IPv6 uses 128-bit addressing and changes several mechanisms around addressing, neighbor discovery and packet handling.

Why: Security monitoring must understand both when an environment is dual-stack.
05 · What does a router do?
Answer: A router forwards packets between networks using its forwarding information and destination address.

Why: Routing determines reachability; it does not by itself authenticate the application sender.
06 · What does the TCP three-way handshake establish?
Answer: It establishes initial connection state and sequence-number synchronization between TCP endpoints.

Why: It establishes transport state, not user or endpoint identity.
07 · What is the difference between TCP flow control and congestion control?
Answer: Flow control protects the receiver from being overwhelmed; congestion control responds to conditions in the network path.

Why: They address different bottlenecks even though both influence sending behavior.
08 · Why is UDP not simply “insecure TCP”?
Answer: UDP is a different transport design that intentionally provides minimal datagram semantics without TCP's reliability and connection machinery.

Why: Security properties depend on the protocol above UDP; QUIC, for example, adds strong transport and cryptographic behavior over UDP.
09 · What is QUIC?
Answer: QUIC is a modern transport protocol carried over UDP that provides reliable streams, congestion control and integrated cryptographic handshake behavior.

Why: HTTP/3 uses QUIC, so modern encrypted traffic cannot be understood correctly by assuming all UDP is simple datagrams.
10 · What does DNSSEC provide?
Answer: DNSSEC provides cryptographic authentication of DNS data through signed records and a chain of trust.

Why: It addresses data authenticity; it does not by itself encrypt the DNS conversation.
11 · What do DoH and DoT change?
Answer: DNS over HTTPS and DNS over TLS encrypt DNS transport between a client and resolver.

Why: They improve privacy of that channel but do not replace DNSSEC's role in authenticating DNS data.
12 · Why can rogue DHCP be dangerous?
Answer: A rogue DHCP service can provide clients with incorrect addresses, gateways or DNS configuration.

Why: Clients may trust network-provided configuration, so a malicious configuration can redirect or disrupt traffic.
13 · What does BGP do?
Answer: BGP exchanges reachability information between autonomous systems and applies routing policy.

Why: Incorrect route announcements can affect where internet traffic travels, making routing security a global trust problem.
14 · What does RPKI/ROV help validate?
Answer: It provides and evaluates cryptographic authorization information for route origins.

Why: It helps detect or reject certain unauthorized route-origin announcements, although it does not solve every BGP security issue.
15 · What security properties does correctly configured TLS provide?
Answer: TLS can provide confidentiality and integrity and can authenticate an endpoint through certificates.

Why: Encryption without correct endpoint authentication can leave an application vulnerable to connecting securely to the wrong endpoint.
16 · What is a certificate?
Answer: An X.509 certificate binds a public key to identity and policy information under a certificate authority trust chain.

Why: Certificate validation allows a client to determine whether a presented public key is authorized for the intended identity.
17 · Why isn't NAT a security boundary by itself?
Answer: NAT changes addressing and often affects reachability, but it does not define authorization policy or authenticate application identities.

Why: Security should come from explicit access-control and authentication mechanisms.
18 · What is the difference between a forward proxy and a reverse proxy?
Answer: A forward proxy acts for clients; a reverse proxy sits in front of servers.

Why: Reverse proxies can centralize routing, TLS termination, authentication integration, rate limiting and application telemetry.
19 · What makes packet capture useful evidence?
Answer: It records observable network state such as addresses, ports, flags, timing, sizes and protocol metadata, with payload visibility depending on encryption and capture location.

Why: Evidence becomes useful when interpreted against a specific protocol and security hypothesis.
20 · What is the most important network-security mental model?
Answer: Treat networking as a system of assumptions about address, identity, state, message integrity, confidentiality, reachability and evidence.

Why: Most network attacks can be understood by identifying which assumption failed and which control should authenticate, encrypt, restrict or monitor it.
Completion standard: You should now be able to trace an application message through the network stack, explain where trust exists and fails, understand modern encrypted transports, and interpret network telemetry as evidence rather than as automatic verdicts.
