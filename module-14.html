1. The advanced Git mental model

Git becomes much easier when you stop thinking of it as a file-copying system and start thinking in terms of commits, references and snapshots. A commit points to a tree of files and to its parent commit or parents. Branches and tags are references that point at commits.

01Working tree
02Index
03Commit
04Reference
05Remote

What you should be able to reason about

  • Working tree: the files currently checked out.
  • Index: the proposed next snapshot.
  • Commit: an immutable snapshot with ancestry.
  • Branch: a movable reference to a commit.
  • Remote-tracking branch: your local record of a remote reference.
A dangerous Git command is not dangerous because Git is mysterious. It is dangerous when you do not know which reference or snapshot it will change. Before rewriting history, inspect the graph.
git status
git log --oneline --graph --decorate --all
git diff
git diff --staged

2. History surgery: rebase, cherry-pick and bisect

Interactive rebase

Interactive rebase lets you reorder, edit, squash, split or drop local commits. It is primarily a history-shaping tool. Do not casually rewrite commits that other people have already based work on.

git rebase -i HEAD~5

Common actions are pick, reword, edit, squash, fixup and drop.

Cherry-pick

Cherry-pick applies the change introduced by a specific commit onto another branch. It is useful for focused fixes, release branches and carefully selected backports. It can also create duplicate logical history if used without discipline.

git cherry-pick <commit>

Bisect

Git bisect performs a binary search through commit history. You identify a known-good commit and a known-bad commit; Git checks out a midpoint and you classify it. Repeat until the first bad commit is identified.

git bisect start
git bisect bad
git bisect good <known-good-commit>
# test
git bisect good   # or: git bisect bad
git bisect reset
The important skill is not memorizing commands. It is turning a vague regression into a deterministic yes/no test that can be repeated at each midpoint.

3. Worktrees and parallel development

A normal Git checkout gives you one working directory per repository clone. A worktree lets one repository have multiple working directories attached to different branches. This is useful when you need to keep an interrupted feature untouched while investigating another branch.

git worktree add ../hotfix hotfix/login
git worktree list
git worktree remove ../hotfix
UsefulKeep a long-running feature checked out while reviewing or fixing another branch.
Watch forShared repository metadata still exists underneath the worktrees; treat branch ownership and cleanup deliberately.

4. Collaboration models

Git is a mechanism. Team workflow is a policy. Compare short-lived branch workflows, trunk-based development and release-branch models. The goal is to reduce integration risk while preserving review and release controls.

Trunk-basedSmall changes integrate frequently. Feature flags can separate deployment from user exposure.
Release branchesA branch can stabilize a release while development continues elsewhere, at the cost of additional merge and backport work.
Squash mergeCompresses a PR into a clean logical commit on the target branch.
Merge commitPreserves the branch topology and can retain useful integration history.

Review quality

  • Keep pull requests small enough to understand.
  • Separate refactoring from behavioral changes when practical.
  • Require automated checks before merge.
  • Write commit and PR descriptions around intent and risk.
  • Prefer reversible changes when production rollback matters.

5. Monorepo architecture

A monorepo stores multiple related applications and packages in one repository. It does not automatically mean one deployable application, one runtime, or one release cycle. The engineering challenge is establishing boundaries that remain understandable as the repository grows.

apps/
  web/
  admin/
  docs/
packages/
  ui/
  domain-types/
  api-client/
  eslint-config/
  tsconfig/

package.json

Healthy package boundaries

  • A package has a clear purpose and public API.
  • Consumers do not import private implementation paths.
  • Dependency direction is intentional.
  • Shared code is genuinely shared rather than merely convenient.
  • Application-specific behavior stays in the application when possible.
A monorepo can make bad architecture easier to spread. If every package can import everything else, you have a large folder—not a well-designed monorepo.

6. Package managers and workspaces

Workspace support lets one package manager understand several packages as a coordinated project. npm supports a workspaces field in the root package.json; pnpm provides workspace-specific tooling and conventions.

{
  "private": true,
  "workspaces": ["apps/*", "packages/*"]
}

Understand the dependency graph

Suppose apps/web depends on @fsb/ui, and @fsb/ui depends on @fsb/types. A tooling system should understand that changing types may require rebuilding ui and then web.

types → ui → web
             ↘ docs

Learn the difference between runtime dependencies, development dependencies, peer dependencies and workspace-local packages. Lockfiles capture resolved dependency versions so installs can be reproduced more reliably.

7. Task graphs, caching and orchestration

When a repository contains many packages, blindly running every lint, test and build on every change wastes time. A task orchestrator models tasks and their dependencies, then determines what must execute.

01Inputs
02Graph
03Affected tasks
04Cache
05Outputs

Cache correctness

A cached result is valid only when the cache key represents all relevant inputs. Inputs can include source files, lockfiles, compiler configuration, environment variables and dependency versions. A false cache hit is worse than a slow build because it can produce incorrect results while appearing successful.

task: build
inputs:
  source + package.json + lockfile + config
outputs:
  dist/**

Modern tooling such as Turborepo can execute dependency-aware tasks and reuse cached results. The conceptual skill transfers to other build systems.

8. Engineering quality gates

Developer tooling should create a fast path to correctness. Use the cheapest useful checks as early as possible and reserve expensive checks for later stages.

01Format
02Lint
03Types
04Tests
05Build
FormattingRemoves review noise and makes diffs easier to scan.
LintingEncodes repeatable code-quality rules.
Type checkingCatches incompatible assumptions before runtime.
TestsProtect behavior and regression boundaries.

Hooks

Git hooks can run checks locally at points such as commit or push. Tools such as Husky and lint-staged can help coordinate focused checks. Hooks should remain fast and should not be the only quality gate: CI must enforce important checks independently.

A good developer workflow feels fast because feedback is layered: immediate local checks, targeted tests, then broader CI validation.

9. Configuration as a product

Shared configuration packages are powerful but easy to abuse. Instead of copying an ESLint or TypeScript configuration into every application, a monorepo can publish an internal configuration package.

packages/
  config-eslint/
  config-typescript/

apps/web/package.json
  devDependencies:
    "@fsb/config-eslint": "workspace:*"

Centralization gives consistency, but it also creates coupling. Version or document breaking configuration changes, and provide an escape hatch when an application genuinely has different constraints.

10. CI/CD tooling and reusable workflows

CI should reproduce the same engineering contract regardless of who opened the change. A useful pipeline validates the repository in stages: install deterministically, restore safe caches when appropriate, run quality checks, test affected packages, build deployable outputs and publish artifacts when needed.

pull request
   ↓
install from lockfile
   ↓
format/lint/types
   ↓
test
   ↓
build
   ↓
artifact / deployment

GitHub Actions supports reusable workflows, job dependencies, artifacts and dependency caching. Reusable workflows reduce duplicated CI logic; caches should never be treated as a source of secrets or trusted executable state.

CI security: GitHub's current guidance warns that caches can be poisoned or expose sensitive cached contents if workflows are poorly scoped. Never put secrets in dependency caches, and carefully control cache writes for low-trust pull-request workflows.

11. Release and dependency discipline

Semantic versioning

Learn the intent of major, minor and patch changes. The important engineering skill is communicating compatibility expectations rather than blindly changing version numbers.

Lockfiles

Commit the lockfile appropriate to your package manager. It records resolved dependency information and makes CI and teammate installs more reproducible.

Dependency updates

  • Review changelogs and breaking changes.
  • Update intentionally rather than constantly chasing every version.
  • Run tests after updates.
  • Separate unrelated dependency upgrades from product changes when possible.
  • Remove unused dependencies rather than accumulating them.

12. Deliberate failure drills

Drill A — stale cache

Change a build input without updating the cache key. Observe how a false cache hit can return an old output. Fix the key.

Drill B — dependency boundary leak

Let an application import an internal file from another package. Move that file and observe the hidden coupling. Replace it with a documented package export.

Drill C — broken rebase

Create two conflicting commits, start an interactive rebase, resolve the conflict, verify the resulting history and use reflog to understand recovery points.

Drill D — slow CI

Run every task for every package. Measure the baseline. Then introduce dependency-aware execution and caching. Compare execution time and verify that correctness remains unchanged.

14. Capstone — FullStack Bible engineering platform

Transform a small multi-app codebase into a maintainable engineering platform. Your final architecture should contain at least two applications and three shared packages.

Required deliverables

  • Repository architecture diagram.
  • Workspace configuration.
  • Shared TypeScript configuration.
  • Shared lint/format configuration.
  • Explicit package exports.
  • Dependency graph.
  • Deterministic install using the lockfile.
  • Local quality command.
  • CI quality pipeline.
  • Dependency-aware build strategy.
  • Cache strategy with documented inputs and outputs.
  • Failure drill results.
  • Developer onboarding document.
  • Decision record explaining why the chosen monorepo tooling fits the project.

Definition of done

A contributor can make a focused change, run fast local checks, open a pull request, receive reproducible CI results, understand the affected package graph and recover from a bad change using Git history rather than guessing.
