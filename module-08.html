The mental model

Data is not just a collection of JSON objects.

A relational database stores structured information in tables. SQL is the language you use to describe, read, change, and combine that information. PostgreSQL is a database system that implements SQL and adds a large set of capabilities around it. The official PostgreSQL tutorial introduces relational concepts, SQL, tables, queries, joins, aggregates, foreign keys, and transactions. PostgreSQL 18 Tutorial

Database

The system that stores and manages persistent application data.

Table

A structured collection of rows with defined columns and rules.

Row

One stored record representing an instance of something.

Relationship

A defined connection between records in different tables.

Rule for this module: model the information first, then write the SQL. A query can be technically valid and still represent the wrong business relationship.
01 · SQL

Learn to speak to the database.

SQL is declarative: you describe the result or change you want, while the database determines how to execute it. Start with the operations that appear constantly in real applications.

Create and inspect tables

A table has columns, data types, defaults, and constraints. Start by making the shape of your data explicit.

CREATE TABLE lessons (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  level text NOT NULL,
  completed boolean NOT NULL DEFAULT false
);

SELECT * FROM lessons;

Do not treat a table as a spreadsheet with unlimited freedom. Constraints make invalid states harder to store in the first place.

Insert, read, update, delete

These four operations form the foundation of application data work. Learn them well before moving to complicated query builders or ORMs.

INSERT INTO lessons (title, level)
VALUES ('SQL foundations', 'beginner');

SELECT id, title, level
FROM lessons
WHERE level = 'beginner'
ORDER BY id;

UPDATE lessons
SET completed = true
WHERE id = 1;

DELETE FROM lessons
WHERE id = 1;
Important: always understand the WHERE clause before running an UPDATE or DELETE. Without a condition, every matching row—or potentially every row—can be changed.

Filtering, sorting, and limiting

SELECT title, level
FROM lessons
WHERE completed = false
  AND level IN ('beginner', 'intermediate')
ORDER BY title ASC
LIMIT 10;

Learn how conditions combine with AND, OR, NOT, comparisons, IN, and null checks. Remember that NULL means “unknown or absent”; it is not the same as an empty string or zero.

Aggregates and grouping

Applications often need summaries rather than individual rows.

SELECT level, COUNT(*) AS lesson_count
FROM lessons
GROUP BY level
ORDER BY lesson_count DESC;

Understand the difference between filtering rows with WHERE and filtering grouped results with HAVING.

Joins: combine related data

A join connects rows using a relationship. An inner join returns matching rows from both sides; a left join keeps every row from the left side and adds matching data when it exists.

SELECT
  lessons.title,
  courses.title AS course_title
FROM lessons
JOIN courses
  ON courses.id = lessons.course_id;

Do not memorise join diagrams alone. Ask: “Which rows must remain even when the other table has no match?” That question determines whether an inner or outer join fits the requirement.

02 · PostgreSQL

Use a real relational database.

PostgreSQL provides the database engine, SQL language support, constraints, transactions, indexes, schemas, views, roles, and many other capabilities you will meet in production applications. The current PostgreSQL documentation is version 18; its tutorial is explicitly designed to provide hands-on introduction to PostgreSQL, relational concepts, and SQL.

PostgreSQL types

Choose types based on the meaning of the data. Common application types include integer, bigint, numeric, text, boolean, date, timestamp, uuid, jsonb, and arrays. Type choice affects what values can be represented and how operations behave.

CREATE TABLE learners (
  id uuid PRIMARY KEY,
  name text NOT NULL,
  email text NOT NULL UNIQUE,
  joined_at timestamptz NOT NULL DEFAULT now()
);

Constraints are executable rules

Use NOT NULL when a value is required, UNIQUE when duplicates are forbidden, CHECK for a condition, PRIMARY KEY for row identity, and FOREIGN KEY for a relationship. PostgreSQL documents these constraints as mechanisms for controlling what data can be stored.

CREATE TABLE courses (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  price numeric(10,2) CHECK (price >= 0)
);

Transactions

A transaction groups related database operations so the application can commit the whole operation or roll it back. This matters when several changes must remain consistent.

BEGIN;

UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;

COMMIT;

If an error occurs before the commit, the application can roll the transaction back instead of leaving a partially completed operation.

Indexes: make the right reads efficient

An index can help PostgreSQL find rows without scanning the whole table for every query. Indexes are not free: they consume storage and add work when rows are inserted or changed. Create indexes based on real query patterns and verify them with PostgreSQL's query-planning tools later in your learning path.

CREATE INDEX lessons_course_id_idx
ON lessons (course_id);
03 · Data modelling

Design the information before the tables.

Data modelling is the process of deciding what your application needs to remember, how those things are represented, and how they connect. Start from real requirements, not from table names.

Step 1 — Identify entities

Ask what distinct things exist in the problem domain. In a learning platform, you might have learners, courses, lessons, and enrollments.

Step 2 — Identify facts

For each entity, list the facts that belong to it. A learner has a name and email. A course has a title. A lesson has a title and belongs to a course. Keep facts with the entity they describe.

Step 3 — Choose identity

Every important record needs a stable way to identify it. PostgreSQL supports identity columns and primary keys. The identifier should not silently change because a display name changed.

Step 4 — Avoid accidental duplication

If the same fact is copied into many rows, updates can become inconsistent. Relational modelling usually separates independently meaningful entities and connects them through keys. Normalisation is the discipline of reducing problematic duplication while preserving useful relationships.

Bad shape: storing course_title repeatedly in every lesson row when the lesson already references a course.

Better shape: store the course once and reference its identifier from lessons.

Schema thinking

Before writing SQL, draw the entities and relationships. For each relationship, state its cardinality: one-to-one, one-to-many, or many-to-many. Then decide which table owns the foreign key or whether a junction table is required.

04 · Relationships

Make connections explicit.

One-to-one

One row corresponds to at most one row in another table. It is useful when two sets of information have separate ownership or security/lifecycle requirements.

CREATE TABLE learner_profiles (
  learner_id uuid PRIMARY KEY
    REFERENCES learners(id),
  bio text
);

One-to-many

One parent can have many children. The foreign key normally lives on the many side.

CREATE TABLE lessons (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  course_id integer NOT NULL
    REFERENCES courses(id),
  title text NOT NULL
);

One course can have many lessons; each lesson belongs to one course.

Many-to-many

When many rows on each side can be connected, use a junction table.

CREATE TABLE enrollments (
  learner_id uuid REFERENCES learners(id),
  course_id integer REFERENCES courses(id),
  enrolled_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (learner_id, course_id)
);

The composite primary key prevents the same learner/course relationship from being inserted twice. PostgreSQL's foreign-key constraints maintain referential integrity by requiring referenced values to exist.

Foreign keys and deletion rules

A foreign key says that a value must match a row in another table. PostgreSQL supports actions such as NO ACTION, RESTRICT, CASCADE, SET NULL, and SET DEFAULT. Choose these based on the business meaning of deleting the parent; never use CASCADE simply because it is convenient.

05 · Reliable data

Make invalid states difficult to store.

Constraints

Put basic invariants in the database so every application path must respect them.

Transactions

Group changes that must succeed or fail together.

Indexes

Support important access patterns without indexing every column blindly.

Nullability

Decide deliberately whether absence is meaningful and allowed.

Application + database: TypeScript types help your application code reason about values, but they do not replace database constraints. The database is the final persistence boundary.
Capstone lab

Build the data layer for a Learning Hub.

Design and implement a small PostgreSQL schema that could support the Next.js application from Module 07.

Requirements

  1. Create tables for learners, courses, lessons, and enrollments.
  2. Give every table an appropriate primary key.
  3. Use meaningful PostgreSQL data types.
  4. Add required NOT NULL, UNIQUE, and CHECK constraints.
  5. Model course → lesson as one-to-many.
  6. Model learner ↔ course as many-to-many through enrollments.
  7. Write queries for a learner's courses, a course's lessons, and completion summaries.
  8. Use a transaction for a multi-step operation.
  9. Add indexes only where the expected query pattern justifies them.
  10. Explain every relationship in plain language before writing the final SQL.

Example completion query

SELECT
  c.title,
  COUNT(l.id) AS total_lessons,
  COUNT(*) FILTER (WHERE p.completed = true) AS completed_lessons
FROM courses c
JOIN lessons l ON l.course_id = c.id
LEFT JOIN lesson_progress p
  ON p.lesson_id = l.id
 AND p.learner_id = '00000000-0000-0000-0000-000000000001'
GROUP BY c.id, c.title
ORDER BY c.title;

Do not just copy this query. Explain why the left join is used, what each grouping column means, and what happens when a lesson has no progress row.

Capstone standard: your schema should be explainable on paper. If you cannot explain why a foreign key exists, what relationship it represents, and what should happen on deletion, the model is not finished.
Data tooling beyond SQL

Know when the database is not the only data system.

ORMs sit above SQL; they do not replace database knowledge

An ORM maps application objects and operations to database queries. It can improve developer ergonomics, migrations and type safety, but it does not remove the need to understand joins, transactions, constraints, query plans and indexes. Always know what SQL the application is causing the database to execute.

Rule: use the ORM as an abstraction, not as permission to ignore the database. Database constraints remain valuable because data can be written through more than one code path.

Redis is a separate system with different trade-offs

Redis is commonly used for caching, ephemeral state, rate limiting, queues and other fast-access workloads. Treat it as a separate data system with its own availability, eviction, consistency and recovery characteristics.

Do not make Redis the only copy of important durable business data unless you have explicitly designed for that requirement and its recovery model.

Object storage is for blobs

Large files such as images, videos, exports and documents are usually better stored in object storage than inside relational rows. Keep metadata and authorization rules in the database while the object store holds the bytes.

Database: file id, owner, content type, size, object key
Object storage: actual bytes

Design upload authorization, content-type validation, size limits, lifecycle/retention rules and private versus public access explicitly.
