Learning objectives

Cryptography is not “making data unreadable.” It is a collection of mathematical constructions and trust systems that provide specific security properties under explicit assumptions. This chapter teaches you to choose and reason about those properties rather than memorizing algorithms.

  • Distinguish confidentiality, integrity, authenticity, authorization and non-repudiation.
  • Explain entropy, randomness, nonces, salts and keys.
  • Understand hashes, MACs and authenticated encryption.
  • Explain symmetric encryption, public-key cryptography, signatures and key agreement.
  • Understand KDFs and secure password verification.
  • Explain X.509 certificates, certificate chains, trust anchors and PKI.
  • Understand revocation, OCSP, CRLs and certificate transparency.
  • Understand key lifecycle, HSMs, rotation, recovery and destruction.
  • Explain why secure protocols compose primitives instead of inventing new cryptography.
  • Understand the post-quantum transition and crypto-agility.
Mental model: every cryptographic design has primitive → key → protocol → trust anchor → lifecycle. A mathematically strong primitive can still fail because the wrong key was used, a nonce was reused, identity was not authenticated, or secrets were poorly managed.

01 · Security properties and threat models

Confidentiality

Confidentiality means an unauthorized party should not learn protected information. Encryption is the usual mechanism, but confidentiality also depends on endpoint security, key protection, memory handling, logs and backups.

Integrity

Integrity means unauthorized modification should be detectable or prevented. A plain hash can detect accidental or known-value changes, but an attacker who can replace both the message and its hash can defeat that construction. Integrity against an active attacker requires an authenticated construction such as a MAC, authenticated encryption or a digital signature.

Authenticity

Authenticity answers whether data or a protocol endpoint is associated with the party expected by the verifier. A signature can authenticate possession of a private key; PKI adds a trust framework that binds that key to an identity.

Authorization is different

Cryptography can establish identity or protect a capability, but it does not decide whether the authenticated principal is allowed to perform an action. Authorization remains an application or policy decision.

Threat model

State the attacker capabilities: passive observation, active modification, replay, endpoint compromise, stolen credentials, malicious insiders, supply-chain compromise or future cryptanalytic capability. A construction is only meaningful relative to the threat it is intended to resist.

02 · Entropy, randomness, nonces and salts

Entropy

In security engineering, entropy describes unpredictability available to a process. Keys, nonces and authentication secrets often depend on unpredictable values. Operating systems provide cryptographically secure random-number generators designed for this purpose.

CSPRNGs

A cryptographically secure pseudorandom number generator expands a secure internal state into outputs that should be computationally unpredictable. Application code should use platform cryptographic randomness rather than inventing a random generator from timestamps, counters or general-purpose pseudo-random functions.

Nonces

A nonce is a value intended to be used according to a protocol-specific uniqueness requirement. It is not automatically secret. In AES-GCM, nonce uniqueness under a given key is critical; accidental reuse can seriously compromise authenticated encryption.

Salts

A salt is normally public, unique per stored secret, and combined with a password before password hashing. It prevents two identical passwords from producing the same stored hash and makes large precomputed lookup tables less useful.

password + unique salt → password KDF → stored verifier

Randomness failure

Weak randomness can collapse otherwise sound cryptography. Historical failures have occurred when keys were predictable or repeated. Randomness is therefore a foundational dependency, not an implementation detail.

03 · Cryptographic hash functions

A cryptographic hash maps arbitrary-length input to a fixed-length digest. Security goals include preimage resistance, second-preimage resistance and collision resistance.

Collision resistance

A collision is two different inputs producing the same digest. For an ideal n-bit hash, generic collision search has roughly 2^(n/2) work because of the birthday phenomenon. This is why digest length matters differently for collision resistance than for preimage resistance.

SHA-2 and SHA-3

SHA-256 and SHA-512 belong to SHA-2. SHA-3 uses the Keccak construction and a different internal design. The choice should follow protocol and library requirements rather than personal preference.

Hash is not encryption

Encryption is designed to be reversible with the correct key. A cryptographic hash is not intended to be reversed. Password storage therefore uses a password KDF rather than “encrypting passwords” or applying a fast general-purpose hash once.

Hash-based integrity

Hashes are useful for content addressing, file integrity and signatures. For adversarial integrity, the hash normally becomes an input to a MAC or signature scheme rather than standing alone.

04 · Symmetric encryption and authenticated encryption

Block ciphers

A block cipher transforms fixed-size blocks under a secret key. AES operates on 128-bit blocks and defines AES-128, AES-192 and AES-256. The key length does not mean the block is that size.

Modes

Modes define how a block cipher handles longer messages. ECB exposes repeated plaintext patterns and is unsuitable for ordinary data encryption. Modern systems generally use authenticated-encryption constructions rather than manually composing encryption and integrity.

AES-GCM

AES-GCM combines AES with a polynomial authentication mechanism to provide confidentiality and integrity. Its security depends critically on nonce management and correct associated-data handling.

ChaCha20-Poly1305

ChaCha20-Poly1305 is an authenticated-encryption construction built from a stream cipher and a MAC. It is widely used in modern protocols and can perform well on systems without dedicated AES acceleration.

Associated data

Authenticated encryption can protect additional data from modification without encrypting it. Protocol metadata such as version, record type or routing context can sometimes be bound as associated data so attackers cannot alter it without detection.

Rule: use a vetted AEAD library/API. Do not design your own cipher mode, nonce scheme or encryption protocol for production data.

05 · Public-key cryptography and key agreement

Key pairs

Public-key systems use a public key that may be shared and a private key that must remain controlled. Depending on the algorithm, the pair can support signatures, encryption or key agreement.

RSA

RSA security is based on properties related to integer factorization. Modern RSA deployments require appropriate key sizes, padding schemes and protocol use. “Raw RSA” is not a safe application-level encryption format.

Elliptic-curve cryptography

ECC provides useful security with comparatively small keys. ECDSA is a signature algorithm; ECDH is a key-agreement mechanism. Correct parameter and nonce handling is essential.

Diffie-Hellman

Diffie-Hellman allows two parties to derive shared secret material over a channel where an observer can see the public exchange. On its own, unauthenticated key agreement is vulnerable to active man-in-the-middle attacks; authentication must bind the exchange to the intended identities.

Key establishment versus encryption

Public-key cryptography is usually used to authenticate or establish key material, while symmetric AEAD protects large volumes of application data efficiently. This combination is the basis of hybrid cryptography.

06 · Digital signatures and trust in keys

A digital signature allows a verifier to check that a message was signed by the holder of a private signing key and has not changed since signing, assuming the algorithm and implementation are secure.

Signing and verification

The signer uses a private key; the verifier uses the corresponding public key. Ed25519 is a modern signature scheme designed for efficient and robust use. ECDSA and RSA signatures remain widely deployed where compatibility requires them.

What a signature does not prove

A valid signature proves control of a private key under the signature scheme. It does not automatically prove the human identity behind that key. A certificate authority, organizational trust store or other explicit binding is required for identity assertions.

Canonicalization

Protocols must define exactly what bytes are signed. Two systems that interpret the same logical object differently can produce signature-verification failures or, worse, security gaps. Structured data signing therefore requires deterministic serialization or a precisely specified canonical representation.

Replay

A valid old signature can sometimes be replayed. Protocols that need freshness must bind signatures to timestamps, nonces, sequence numbers or unique transaction identifiers as appropriate.

07 · Passwords, KDFs and authentication secrets

Why passwords are special

Human-chosen passwords have much lower entropy than cryptographic keys. A password database therefore needs a deliberately expensive verification mechanism so large numbers of guesses become costly.

Argon2id, scrypt, bcrypt and PBKDF2

Modern password-storage choices include memory-hard Argon2id and scrypt, as well as established bcrypt and PBKDF2 deployments. Parameters should be selected for the current environment and periodically reviewed as hardware changes.

Salt and work factor

Each password should have a unique salt. The KDF's work and memory parameters increase the cost of offline guessing. A pepper can add an application-held secret, but it introduces key-management requirements and should not replace proper KDF use.

Current digital-identity guidance

NIST SP 800-63B-4 is the current NIST authentication-and-authenticator guideline. It addresses password and authenticator requirements, including handling of compromised or commonly used passwords and appropriate lifecycle practices.

Passkeys and phishing resistance

Passkeys use public-key credentials rather than transmitting a reusable password to the verifier. They can provide strong phishing resistance when implemented through appropriate platform authenticators and relying-party protocols.

08 · PKI: building a trust hierarchy

What PKI solves

Public keys are easy to copy. The hard problem is deciding which public key belongs to which identity. PKI addresses this binding through certificates, certificate authorities, trust anchors, validation rules and operational processes.

Root and intermediate CAs

A root CA is a trust anchor distributed through a trust store. Intermediate CAs issue end-entity certificates while keeping the root key offline or otherwise strongly protected. This hierarchy limits exposure of the root signing key and allows operational separation.

Certificate chain

Root trust anchor → Intermediate CA → End-entity certificate → Service identity

A verifier builds and validates a chain, checking signatures, validity, constraints and the intended identity.

Trust stores

Browsers and operating systems maintain collections of trusted roots. An enterprise may add private roots for internal services. Trust-store changes are therefore security-sensitive administrative actions.

Private PKI

Internal PKI is useful for enterprise workloads, device identity and service-to-service authentication. Its security depends on CA governance, certificate issuance policy, private-key protection and reliable revocation or short-lived credential strategies.

09 · X.509 certificates and validation

Certificate contents

X.509 certificates include a subject/identity representation, public key, issuer, validity period, serial number, extensions and a CA signature. Modern web certificates commonly use Subject Alternative Name for the identities they cover.

Hostname validation

A TLS client must verify that the requested hostname is authorized by the certificate's identity fields. A certificate signed by a trusted CA is not sufficient if it is issued for a different hostname.

Key usage and constraints

Extensions can constrain how a certificate or CA may be used. Basic Constraints identify CA certificates; Key Usage and Extended Key Usage express permitted operations. Validation libraries should enforce these rules rather than applications reimplementing them incompletely.

Expiration

Expiration limits how long a certificate is considered valid. Shorter lifetimes reduce exposure from forgotten credentials but increase operational dependence on reliable automated renewal.

Misissuance

A certificate can be technically valid yet issued incorrectly. Certificate transparency and CA governance provide additional mechanisms for detecting and responding to misissuance in publicly trusted PKI.

10 · Revocation, OCSP, CRLs and transparency

Why revocation exists

If a private key is compromised or a certificate is issued incorrectly, waiting until its expiration may be unacceptable. Revocation mechanisms communicate that a certificate should no longer be trusted.

CRLs

A Certificate Revocation List is a signed list of revoked certificate serial numbers published by a CA. CRLs can become large, so systems need strategies for distribution and caching.

OCSP

Online Certificate Status Protocol lets a client query certificate status. OCSP introduces availability and privacy considerations, and implementations may use stapling so the server supplies a signed status response during a TLS exchange.

Certificate Transparency

Certificate Transparency uses append-only public logs to make publicly trusted certificate issuance auditable. Monitoring these logs can reveal certificates issued for an organization's domains that security teams did not expect.

Short-lived certificates

Short lifetimes can reduce the window of exposure and lessen dependence on revocation. They shift the problem toward reliable automated issuance, renewal and deployment.

11 · Key management lifecycle

Generate

Generate keys using approved cryptographic randomness and algorithms. Never derive production cryptographic keys from predictable identifiers, timestamps or ordinary random functions.

Store and use

Protect private keys with access controls appropriate to their value. Hardware Security Modules (HSMs) can provide protected key storage and cryptographic operations. Cloud KMS services provide managed key lifecycle capabilities but remain dependent on correct IAM and configuration.

Rotate

Rotation reduces the amount of data or time exposed if a key is compromised. Rotation design must account for old-data decryption, overlapping validity, distributed caches and rollback.

Back up and recover

Some keys must be recoverable; others, such as ephemeral session keys, should not be. Backup copies must be protected to the same or stronger standard as production copies.

Revoke and destroy

Compromise response may require revoking certificates, disabling credentials and destroying key material. Destruction must account for backups, replicas, logs and hardware copies.

Key-management principle: cryptographic strength is bounded by the weakest point in the key lifecycle. A perfect cipher with a leaked key provides no confidentiality.

12 · Secure protocol composition

TLS as a case study

TLS combines key agreement, authentication, transcript integrity and authenticated encryption into a protocol with defined state transitions. Applications should use mature TLS implementations rather than composing raw primitives themselves.

Context binding

Secure protocols bind keys and messages to the intended context. This helps prevent a credential or signed message from being valid in a different protocol, service or transaction than intended.

Forward secrecy

With ephemeral key agreement, compromise of a long-term authentication key does not automatically reveal previously captured session traffic, assuming the ephemeral secrets were not also compromised. This limits the impact of later key compromise.

Downgrade resistance

Protocols must prevent attackers from forcing participants toward weaker versions or algorithms. Secure negotiation includes transcript binding and explicit version/cipher-suite rules.

Cryptographic agility

Agility means a system can replace algorithms and parameters without a complete architectural rewrite. It is valuable for responding to newly discovered weaknesses and for the transition to post-quantum algorithms.

14 · Post-quantum cryptography and crypto-agility

Large-scale fault-tolerant quantum computers would threaten widely used public-key constructions based on integer factorization and discrete logarithms. Symmetric cryptography is affected differently, with security margins generally addressed through suitable key sizes.

Migration is an engineering project

Organizations need an inventory of algorithms, libraries, protocols, certificates, hardware and stored encrypted data. “Where is RSA/ECC used?” is often harder to answer than choosing a new algorithm.

NIST standardization

NIST's post-quantum standardization work selected lattice- and hash-based approaches for standardization. The transition should follow current NIST publications and implementation guidance rather than relying on early experimental algorithms.

Hybrid approaches

Hybrid key establishment can combine classical and post-quantum components so a protocol retains security if one component remains secure. The exact construction must be specified by the protocol standard; concatenating outputs casually is not a security proof.

Harvest-now-decrypt-later

An adversary may capture encrypted traffic today and attempt decryption later if future capabilities permit it. Long-lived sensitive data therefore deserves special attention during migration planning.

Crypto-agility

Separate algorithm identifiers from business logic, keep key formats versioned, test rotation, maintain compatibility windows and make cryptographic dependencies observable. Agility is an architecture property, not a single library setting.

15 · Secure cryptography in application engineering

Prefer high-level APIs

Application developers should use platform or library APIs that expose safe authenticated-encryption, key generation, password verification, certificate validation and signing primitives. Avoid implementing AES rounds, elliptic-curve arithmetic or certificate validation yourself.

Secrets in applications

API keys, signing keys and database credentials should not be committed to source control. Use secret-management systems, narrow permissions and automated rotation. Logs should be reviewed for accidental secret disclosure.

Data classification

Not every value needs encryption everywhere. Identify sensitive data, define where it exists, determine who needs access, then choose encryption at rest, in transit or application level as appropriate.

Testing

Security tests should verify properties such as certificate validation, authentication failure, authorization boundaries, nonce handling, key rotation and secret absence from logs. Tests should use known test vectors where standards provide them.

Dependency discipline

Cryptographic libraries receive security fixes and algorithm updates. Track versions, supported algorithms, advisories and end-of-life status. A secure construction implemented by an obsolete dependency can still create operational risk.

16 · Mastery review — 20 questions with answers

01 · Why is a hash not the same as encryption?
Answer: Encryption is designed for reversible protection with a key; a cryptographic hash is designed as a one-way digest with collision and preimage security goals.

Why: Different problems require different constructions.
02 · What is the difference between integrity and authenticity?
Answer: Integrity concerns unauthorized modification; authenticity concerns whether data or an endpoint is associated with the expected source or identity.

Why: A checksum can detect changes without proving who created the data.
03 · Why are nonces important in AEAD?
Answer: Many AEAD constructions require nonce uniqueness under a given key.

Why: Reuse can expose relationships between messages and may undermine authentication security.
04 · What is a salt?
Answer: A salt is a unique value combined with a password before password hashing/KDF processing.

Why: It prevents identical passwords from sharing the same stored verifier and reduces the value of precomputed tables.
05 · What is a MAC?
Answer: A Message Authentication Code is a keyed construction that lets parties sharing a secret key detect unauthorized message modification and authenticate the message to holders of that key.

Why: Unlike a plain hash, an attacker without the key cannot normally generate a valid MAC.
06 · Why is AEAD preferred to separate encryption and integrity in application code?
Answer: AEAD provides confidentiality and authentication as one standardized construction with defined composition rules.

Why: Manual composition is easy to get subtly wrong, especially around nonce, padding and verification behavior.
07 · What does public-key cryptography solve?
Answer: It enables operations such as digital signatures and key establishment without requiring both parties to pre-share the same secret key.

Why: This supports scalable trust systems such as PKI and secure session establishment.
08 · Why is unauthenticated Diffie-Hellman vulnerable to man-in-the-middle attacks?
Answer: An active attacker can substitute their own public parameters with each endpoint and establish separate shared secrets.

Why: Key agreement establishes shared secrecy, but authentication is required to bind that secrecy to the intended identities.
09 · What does a digital signature prove?
Answer: It proves, assuming the scheme is secure, that the signer controlled the corresponding private key and that the signed bytes have not changed.

Why: Identity still requires a trusted binding between the public key and an entity.
10 · Why should passwords use a password KDF?
Answer: Human passwords have limited entropy, so verification must be deliberately expensive to slow offline guessing.

Why: Fast hashes are designed for performance and therefore make billions of guesses cheaper.
11 · What is PKI?
Answer: Public Key Infrastructure is the operational trust system around public keys, certificates, certificate authorities, trust anchors, validation and lifecycle processes.

Why: Public keys alone do not tell a verifier which real-world identity they belong to.
12 · What is a trust anchor?
Answer: A trust anchor is a public key or certificate that a verifier accepts as trusted without needing to validate it through another certificate in that local trust decision.

Why: Certificate chains ultimately terminate at configured trust.
13 · Why is hostname validation necessary for TLS?
Answer: It verifies that the certificate presented by the server is valid for the identity the client intended to contact.

Why: A certificate signed by a trusted CA can still be issued to a different hostname.
14 · What is the difference between CRL and OCSP?
Answer: A CRL publishes a signed list of revoked certificates; OCSP provides a protocol for querying certificate status.

Why: They represent different operational approaches to communicating revocation state.
15 · What does certificate transparency add?
Answer: It provides publicly auditable logs of certificates issued by participating public CAs.

Why: Organizations can monitor for unexpected certificates and detect some forms of misissuance.
16 · Why is key management as important as algorithm choice?
Answer: A strong algorithm cannot protect data if its key is predictable, exposed, over-permissioned, never rotated after compromise or irrecoverably lost when recovery is required.

Why: Cryptographic security is an end-to-end lifecycle property.
17 · What is forward secrecy?
Answer: Forward secrecy limits the ability of a later compromise of long-term authentication keys to decrypt previously captured sessions.

Why: Ephemeral session key material is independently generated and discarded after use.
18 · Why should applications avoid custom cryptography?
Answer: Cryptographic security depends on subtle mathematics, composition, randomness, encoding, side-channel behavior and protocol state.

Why: Mature standards and libraries provide reviewed constructions and tested implementations.
19 · Why does post-quantum migration require an inventory?
Answer: Organizations must know which algorithms, certificates, libraries, devices and stored data depend on vulnerable public-key assumptions.

Why: You cannot migrate cryptography you cannot locate.
20 · What is the core cryptographic mental model?
Answer: Identify the security property, threat model, primitive, key, protocol context, trust anchor and lifecycle before evaluating a cryptographic design.

Why: Most real failures occur at the boundaries between these pieces rather than because AES or SHA-256 suddenly stopped working.
Completion standard: You should be able to explain why a primitive exists, how it is composed into a protocol, how identity is bound through PKI, how keys live and die, and how to recognize cryptographic misuse without inventing your own cryptography.
