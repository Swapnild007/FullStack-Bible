Chapter 01

Computer architecture: what a computer actually is

At the simplest level, a computer repeatedly transforms state. Instructions are fetched, decoded and executed; data is read and written; devices generate events; and privileged software changes the rules under which less-privileged software runs.

1.1 The major pieces

A conventional computing platform contains one or more processors, volatile memory, persistent storage, device controllers, buses/interconnects and firmware. Modern systems also contain security-oriented hardware such as a TPM, secure enclave or platform security controller depending on the design.

The processor has architectural state: general-purpose registers, an instruction pointer, flags/status registers and control state. Memory contains instructions and data. Devices expose registers or queues through which software controls hardware. Persistent storage retains information after power is removed.

1.2 State and authority

Security becomes clearer when architecture is described in terms of authority. A register that controls memory translation is more security-sensitive than an application variable. A firmware update mechanism has more authority than an ordinary file write. A device capable of DMA may access memory outside the normal CPU instruction path.

Therefore, a threat model should identify not just components but who can cause state transitions. An attacker who controls a low-level component may bypass assumptions made by higher layers.

1.3 Privilege is a hardware-assisted concept

Processors provide mechanisms that operating systems use to separate privileged execution from ordinary application execution. The exact names differ between architectures. The principle is consistent: security-sensitive operations require a higher authority level, while applications execute with fewer privileges.

A system call is therefore not simply a normal function call. It is a controlled transition from a less-privileged execution context into the kernel's privileged context. The kernel validates the request, performs the operation if authorized, and returns control to the application.

1.4 Why this matters to cybersecurity

If an attacker obtains kernel-level control, ordinary application-level security assumptions can fail. If firmware is compromised, the operating system may start from an already-untrusted platform. This is why platform security is a foundation rather than a separate niche.

Check your understanding
  • Why is “who can change this state?” often more useful than simply asking “what component is this?”
  • Why does an application not normally get unrestricted access to CPU control state or physical devices?
Chapter 02

Memory hierarchy, virtual memory and caches

Memory is not one uniform thing. A security engineer must understand the difference between architectural addresses, virtual addresses, physical memory, caches and persistent storage.

2.1 The hierarchy

Registers are closest to execution. CPU caches provide faster access than main memory but have limited capacity. Main memory holds active program state. Persistent storage provides durable state. The exact cache levels and topology depend on the processor.

This hierarchy exists because speed, capacity, cost and physical distance cannot all be optimized simultaneously. The operating system and hardware cooperate to make this hierarchy appear much simpler to applications than it really is.

2.2 Virtual memory

Most modern operating systems give each process a virtual address space. A memory-management unit translates virtual addresses into physical locations, usually through page tables maintained by the operating system and consulted by hardware.

Virtual memory provides isolation: two processes can use the same virtual address without referring to the same physical memory. It also enables permissions such as readable, writable and executable mappings.

2.3 Pages and permissions

Memory is commonly managed in pages. A page-table entry can encode attributes controlling whether a page is present, writable, executable, accessible from user mode and more. These permissions are security controls, not merely performance settings.

2.4 Caches and timing

Caches remember recently used data. This creates timing differences between cache hits and misses. When secret-dependent operations influence cache state, an attacker who can observe timing may sometimes infer information without directly reading the secret.

This class of weakness is called a side channel: the information is leaked through an observable property of the system rather than through the intended program output. Similar channels can arise from power, electromagnetic emissions, branch prediction and other implementation details.

2.5 Security engineering response

Mitigation depends on the threat model. Cryptographic code may use constant-time techniques; operating systems may isolate workloads; processors may provide architectural protections; cloud platforms may reduce cross-tenant exposure. The correct lesson is not “caches are insecure.” The lesson is that performance mechanisms can become security-relevant state.

Chapter 03

Instruction execution, control flow and binary state

Source code is an abstraction. Eventually the processor executes machine instructions and manipulates registers and memory. Reverse engineering, debugging and vulnerability research require moving comfortably between these levels.

3.1 Fetch, decode, execute

A processor obtains instructions from memory, interprets their encoding and performs the requested operation. Modern CPUs are internally far more complex — pipelines, speculative execution, out-of-order execution and multiple execution units may all be involved — but the architectural model remains useful: an instruction consumes state and produces new state.

3.2 Instruction pointer

The instruction pointer identifies the architectural location associated with the next instruction in the control-flow sequence. Calls, returns, conditional branches, exceptions and interrupts alter the sequence.

That makes control-flow integrity a security concern. If a memory-safety flaw lets an attacker influence a control-flow target, the attacker may attempt to redirect execution. Modern mitigations attempt to make such redirection harder or detectable.

3.3 Endianness

Endianness describes how a multi-byte value is laid out in memory. In little-endian representation, the least-significant byte occupies the lowest address. In big-endian representation, the most-significant byte occupies the lowest address. Protocol specifications may define their own byte order.

3.4 Calling conventions

A calling convention defines how compiled functions exchange values: where arguments are placed, where return values appear, which registers must be preserved and how stack alignment is handled. The ABI adds broader binary-compatibility rules.

Knowing the ABI explains why a debugger can show a function's arguments, why a crash report contains particular register values and why binaries compiled by different tools can interoperate.

3.5 Exceptions and interrupts

An exception is an event associated with instruction execution or processor state; an interrupt is an externally signaled event that requests processor attention. The processor transitions into an appropriate handler under privileged control. These mechanisms are essential for system calls, faults, timers and device I/O.

Chapter 04

Stack, heap, object lifetime and memory safety

Many high-impact software vulnerabilities begin with an incorrect relationship between a program's idea of an object and the bytes that actually occupy memory.

4.1 The stack

The call stack commonly contains function-local state, saved registers and return information. Its exact layout is compiler-, ABI- and architecture-dependent. A stack buffer overflow occurs when an operation writes beyond the intended bounds of an object associated with stack storage.

4.2 The heap

Dynamic allocation allows objects to live beyond a single function invocation. Allocators manage regions of memory and maintain metadata needed to satisfy allocations and releases.

Important vulnerability classes include use-after-free, where code accesses an object after its lifetime ended; double-free, where an allocation is released more than once; and out-of-bounds access, where code reads or writes outside an object's valid region.

4.3 Integer errors

Integer overflow and truncation can become memory-safety problems when arithmetic is used to calculate allocation sizes or bounds. A value that looks mathematically correct may not fit in the chosen integer representation. The resulting smaller allocation can then be followed by a larger copy.

Chapter 05

Firmware: the software that starts before your software

Firmware occupies an unusual security position. It is software, but it initializes and controls hardware before the normal operating system is running.

5.1 What firmware means

Firmware is low-level software associated with a device or platform and commonly stored in non-volatile memory. It can configure hardware, initialize devices, establish boot policy and provide runtime services.

Firmware exists in many places: platform firmware, storage controllers, network adapters, embedded controllers, GPUs, routers, printers and other devices. Therefore “firmware security” is broader than BIOS security.

5.2 UEFI

UEFI provides a standardized firmware interface and boot environment. The UEFI Forum currently lists UEFI Specification 2.11, released in December 2024. Its Platform Initialization specification is listed at version 1.10, released July 2026. citeturn0search0

UEFI defines interfaces and data structures, but an implementation is still software and can contain defects. The security engineer therefore evaluates the implementation, configuration, update path and trust anchors — not merely whether a platform says “UEFI.”

5.3 Firmware persistence

Persistent firmware can survive an operating-system reinstall. That makes firmware compromise materially different from an ordinary malicious file. NIST SP 800-193 treats platform firmware as a foundational part of system operation and organizes resilience around mechanisms that protect, detect and recover from unauthorized changes. citeturn0search1

5.4 Firmware update security

A secure update system needs authenticity, integrity, version control, authorization, rollback policy and recovery. A signature alone is not the entire update architecture: the platform also needs a policy for which signer is trusted, which versions are acceptable and what happens if an update is interrupted or later found vulnerable.

Chapter 06

Boot architecture and the chain of trust

Boot security is about deciding what is allowed to become the next layer of authority.

6.1 A simplified boot sequence

Power → immutable/early hardware state → platform firmware → boot policy → boot manager/loader → operating-system kernel → system services → applications

The real sequence varies by architecture and platform, but the security concept is stable: earlier stages influence what later stages are permitted to execute.

6.2 Secure Boot

Secure Boot establishes a policy for authenticating boot components before execution. The platform checks whether a component is authorized according to its trust database and policy, then permits or rejects execution.

This answers a specific question: “Is this boot component authorized to execute?” It does not prove that the component is bug-free or that the operating system is safe after boot.

6.3 Trust anchors and keys

A signature verifies that a piece of data corresponds to a trusted signing key. The difficult security question is how that trust is established and maintained. Key compromise, unauthorized enrollment, poor revocation and weak update policy can undermine a technically correct signature check.

6.4 Secure Boot limitations

  • A trusted component can still contain a vulnerability.
  • A compromised trusted signing key can authorize malicious software.
  • Misconfiguration can weaken the intended policy.
  • Runtime attacks after boot are outside Secure Boot's primary purpose.
Chapter 07

Measured boot: recording what actually happened

Secure Boot and measured boot solve different problems. One can enforce an execution policy; the other can create evidence about the sequence of measurements observed during boot.

7.1 Measurement versus verification

A measurement is normally a cryptographic digest of data or state. Measuring a component does not automatically declare it safe. It creates a value that can later be compared against an expected state or used as part of an attestation protocol.

7.2 PCR extension

TPM Platform Configuration Registers are commonly updated through an extend operation that combines the previous PCR value and a new measurement:

PCR_new = H(PCR_old || measurement)

This creates a cumulative history. Changing an earlier measurement changes subsequent PCR values, which makes the final state sensitive to the measured sequence.

7.3 Event logs

A PCR value alone does not tell a human analyst which individual components produced it. A measurement log can provide the events needed to interpret the resulting state. Security architecture therefore treats the protected measurement value and the associated evidence as complementary.

7.4 Remote attestation

Attestation extends this idea to a verifier. A platform can provide cryptographic evidence about selected state, and a relying system can make a policy decision from that evidence. For example, a service might require a known platform state before releasing a sensitive credential.

Chapter 08

TPM 2.0 and hardware roots of trust

A TPM is not a magic “security chip.” It is a defined security component with protected operations and state that can support key protection, measurements, authorization and attestation.

8.1 Current specification baseline

The Trusted Computing Group lists TPM 2.0 Library Specification Version 185, March 2026 as the current library specification, with parts covering introduction, architecture, structures and commands. citeturn0search3turn0search12

8.2 What a TPM contributes

  • Protected cryptographic operations.
  • Platform measurement support.
  • Key and authorization mechanisms.
  • Hardware-backed identity and attestation capabilities.
  • Protected state that is harder to manipulate like ordinary application memory.

8.3 What a TPM does not do

A TPM does not automatically make an operating system patched. It does not decide whether a user should access a business application. It does not remove the need for endpoint detection, application security or incident response.

8.4 Root of trust

A root of trust is a foundation whose behavior is sufficiently trusted to anchor later security decisions. NIST IR 8320 describes hardware-enabled security as the first layer of a layered approach and discusses technologies including TPMs, hardware security modules, secure enclaves, trusted execution environments and virtualization. citeturn0search4

Chapter 09

Physical interfaces: UART, JTAG, SPI and I²C

A device can be secure in software and still be exposed through a physical interface. Debugging and manufacturing interfaces are powerful because they often exist precisely to observe or control low-level state.

9.1 UART

UART is a serial communication mechanism frequently used for device consoles and diagnostics. A production device that exposes a privileged console through an accessible header has created an additional trust boundary that must be controlled.

9.2 JTAG

JTAG-related interfaces support hardware test and debugging. Depending on the platform, debug access can provide capabilities far beyond an ordinary application interface. Production designs therefore commonly restrict, authenticate or disable debug functionality according to their threat model.

9.3 SPI

SPI is a synchronous serial bus frequently used for flash storage and peripheral communication. If platform firmware is stored on SPI-attached flash, the storage path becomes part of the firmware security architecture.

9.4 I²C

I²C is a shared serial bus widely used for sensors, controllers and configuration devices. Security depends on which devices are connected, what commands they accept and what authority the controlling firmware has.

9.5 Physical security is not “just physical”

Physical access can cross software security boundaries. An attacker who can modify boot media, connect to an exposed debug port or replace a component may bypass assumptions that were safe under a remote-only threat model.

Authorized research rule: hardware debugging and firmware analysis should be performed only on devices you own or are explicitly authorized to test.
Chapter 10

Devices, DMA and I/O trust

Not every memory access is caused by a CPU instruction. Devices can sometimes perform direct memory access (DMA), allowing hardware to transfer data to or from system memory.

10.1 Why DMA matters

DMA improves performance by allowing devices to transfer buffers without requiring the CPU to copy every byte. From a security perspective, however, a device with broad DMA authority becomes part of the memory-protection boundary.

10.2 IOMMUs

An I/O memory management unit can constrain and translate device memory accesses. This allows the system to assign a device a limited set of memory regions rather than treating the entire physical address space as available.

10.3 Threat-model implication

The security question becomes: which devices can access which memory, under which policy, and who controls that policy? This is especially important in servers, virtualization and high-performance peripheral environments.

Chapter 11

Hardware and firmware supply-chain security

Trust begins before the device reaches the organization. Modern platforms depend on silicon, board vendors, firmware developers, signing infrastructure, update services, drivers and manufacturing processes.

11.1 The dependency graph

A platform can inherit risk from a component that the final operator never directly sees. The practical challenge is inventory: if you cannot identify the component, firmware version, signer and update path, you cannot reliably determine exposure or recovery options.

11.2 Common failure modes

  • Counterfeit or substituted components.
  • Compromised build or release infrastructure.
  • Stolen firmware-signing credentials.
  • Unsigned or weakly authenticated updates.
  • Untracked third-party firmware.
  • Unclear vulnerability disclosure and patch ownership.
  • No tested recovery image or rollback strategy.

11.3 Security controls

Controls include asset inventories, provenance requirements, reproducible or controlled builds where practical, protected signing keys, signed firmware, secure update channels, version policy, vulnerability management, supplier assurance and tested recovery procedures.

NIST's hardware-enabled security guidance emphasizes the platform as the foundation on which higher-layer controls depend. citeturn0search4

Chapter 12

Firmware resilience: protect, detect, recover

Prevention is only one part of platform security. A mature design assumes that an unauthorized change may eventually occur and asks how the platform will detect it and return to a trustworthy state.

12.1 Protect

Protection can include access controls around firmware storage, authenticated updates, hardware write protections, signing policies and separation of update authority from ordinary operating-system users.

12.2 Detect

Detection can involve integrity measurements, authenticated state, update records, configuration monitoring and external management telemetry. Detection is useful only when the organization can interpret the signal and act on it.

12.3 Recover

Recovery requires a trusted source from which the platform can restore firmware and configuration. Recovery paths themselves must be protected; otherwise an attacker may compromise the recovery mechanism and turn it into another persistence layer.

12.4 Why recovery belongs in the threat model

A platform that can detect compromise but cannot recover safely may still have a serious operational weakness. NIST SP 800-193 explicitly addresses protection, detection and secure recovery for platform firmware resilience. citeturn0search1

Chapter 13

Virtualization, isolation and the hardware boundary

Cloud and modern enterprise systems place another layer between physical hardware and applications: virtualization. This creates powerful isolation mechanisms but also creates a new security boundary.

13.1 Hypervisor role

A hypervisor manages virtual machines and mediates access to hardware resources. A guest operating system believes it has processors, memory and devices; the hypervisor maps those abstractions onto the physical platform.

13.2 Why the hypervisor matters

A vulnerability in a guest application may be contained by the guest operating system. A vulnerability that crosses the guest/hypervisor boundary can have much broader impact because the hypervisor manages resources shared by multiple workloads.

13.3 Hardware-assisted isolation

Modern processors provide virtualization extensions and memory-translation features that help enforce isolation. NIST IR 8320 discusses virtualization alongside TPMs, trusted execution environments, secure enclaves and other hardware-enabled mechanisms as part of layered platform security. citeturn0search4

Chapter 14

Platform threat modeling

Threat modeling turns architecture into security decisions. Start with assets, trust boundaries and adversary capabilities rather than jumping directly to a list of vulnerabilities.

14.1 Identify assets

  • Firmware and boot configuration.
  • Cryptographic keys and device identity.
  • Operating-system integrity.
  • Sensitive workload memory.
  • Recovery images and update credentials.
  • Device telemetry and forensic evidence.

14.2 Identify adversary access

Consider remote attackers, malicious software already running on the host, privileged insiders, supply-chain compromise and physical attackers. These are different threat models and should not be mixed casually.

14.3 Map trust boundaries

Draw boundaries between hardware and firmware, firmware and bootloader, bootloader and kernel, kernel and user space, host and device, guest and hypervisor, and management plane and data plane. For every boundary, document the mechanism that enforces it.

14.4 Ask the failure questions

For every critical control, ask: What happens if it is disabled? What happens if its key is compromised? What evidence remains? Can the platform detect the change? Can it recover? Who is authorized to perform recovery?

Chapter 15

Putting the layers together

The value of this discipline is the ability to reason across layers rather than memorizing isolated technologies.

15.1 The key mental model

Think of platform security as a chain of evidence and authority. A later layer should not blindly trust an earlier layer; it should rely on an explicit mechanism appropriate to the threat model.

Example reasoning: “The application validates the user” is not enough to establish platform trust. First ask whether the application itself is running on an authentic operating system, whether the boot path was protected, whether secrets were protected, and whether the platform can detect meaningful integrity changes.

Foundation questions — with answers

Use the question first as a recall exercise. Then open the answer to verify your understanding. The answer is intentionally followed by a short explanation so this section teaches rather than merely tests.

01 · What architectural state does a CPU maintain that is directly relevant to control flow?
Answer: The CPU maintains an instruction pointer/program counter, which identifies the location associated with the next instruction in the execution stream. Registers and status/flags also affect control flow.

Why: Calls, returns, branches, exceptions and interrupts change execution flow. Security problems can occur when a vulnerability lets unintended data influence control-flow-relevant state.
02 · Why is virtual memory a security mechanism as well as a convenience?
Answer: Virtual memory gives processes isolated address spaces and lets the OS/hardware apply permissions to memory pages.

Why: Process isolation helps prevent one process from freely reading or modifying another process's memory.
03 · What is the difference between a cache and main memory?
Answer: A cache is smaller, faster storage close to CPU execution units that keeps recently used data; main memory provides much larger working storage with higher access latency.

Why: Their different timing characteristics can become observable and therefore security-relevant.
04 · Why can timing become a security signal?
Answer: Different execution paths or hardware states can take measurably different amounts of time.

Why: If secret-dependent behavior changes timing, an observer may infer information without directly reading the secret. This is a side channel.
05 · What is a calling convention and why does reverse engineering depend on it?
Answer: A calling convention defines how functions receive arguments, return values, preserve registers and use the stack.

Why: Reverse engineers and debuggers use these rules to reconstruct function boundaries, parameters and execution state from compiled binaries.
06 · What distinguishes a stack buffer overflow from a use-after-free?
Answer: A stack buffer overflow writes beyond the intended bounds of stack-associated storage. A use-after-free accesses an object after its allocated lifetime has ended.

Why: They are different memory-safety failures and can require different analysis and mitigations.
07 · Why are ASLR, NX and stack canaries complementary rather than interchangeable?
Answer: ASLR randomizes important addresses, NX/DEP restricts execution from selected memory, and stack canaries detect some stack corruption.

Why: Each addresses a different part of the exploitation problem. One mitigation does not provide the guarantees of the others.
08 · Why is firmware security different from ordinary application security?
Answer: Firmware can execute before the operating system and can configure hardware and the boot environment with high privilege.

Why: A persistent firmware compromise can survive an OS reinstall and undermine assumptions made by higher software layers.
09 · What does Secure Boot actually establish?
Answer: Secure Boot establishes a policy for authenticating boot components before they execute.

Why: It helps prevent unauthorized boot components from becoming trusted execution, but it does not prove that trusted software is bug-free.
10 · Why does a valid signature not prove that software is bug-free?
Answer: A signature primarily establishes authenticity relative to a trusted signing key; it does not establish that the signed code contains no vulnerabilities.

Why: A legitimately signed component can still contain exploitable defects or be configured insecurely.
11 · What is the difference between measured boot and Secure Boot?
Answer: Secure Boot enforces an execution trust policy; measured boot records measurements of boot state so that the resulting state can be evaluated later.

Why: One primarily answers “may this execute?” while the other helps answer “what was measured during boot?”
12 · What does PCR extension achieve conceptually?
Answer: PCR extension combines the previous PCR value with a new measurement, producing a cumulative value that depends on the measurement sequence.

Why: Changing an earlier measurement changes subsequent values, making the resulting PCR state useful as evidence of measured platform state.
13 · What does a TPM contribute to a platform trust model?
Answer: A TPM provides protected cryptographic and platform-trust capabilities, including support for protected keys, measurements, authorization and attestation.

Why: It gives the platform protected state and operations that are harder to manipulate like ordinary application memory.
14 · Why can an exposed debug interface become a security boundary?
Answer: Interfaces such as UART or JTAG can provide diagnostic or low-level control capabilities that are much more powerful than normal application interfaces.

Why: If an unauthorized person can access those capabilities, they may cross a trust boundary the software threat model assumed was protected.
15 · Why does DMA make device trust relevant to memory isolation?
Answer: A DMA-capable device can transfer data to or from system memory without every transfer being performed by an ordinary CPU instruction.

Why: An IOMMU and related policy can restrict which memory regions a device may access, making device authority part of the memory-isolation model.
16 · Why must firmware recovery be protected too?
Answer: Recovery must restore the platform from a trustworthy source. If the recovery mechanism itself can be modified by an attacker, it cannot reliably restore trust.

Why: Resilience requires a protected path to a known-good state, not merely the ability to reinstall firmware.
17 · What is a root of trust?
Answer: A root of trust is a component or mechanism whose behavior is sufficiently trusted to anchor subsequent security decisions.

Why: Secure boot chains, measurements and protected keys ultimately depend on something at the foundation that later layers can rely upon.
18 · Why is a hypervisor a high-value security boundary?
Answer: A hypervisor mediates hardware resources for virtual machines and can isolate multiple workloads on one physical platform.

Why: A vulnerability that crosses the guest/hypervisor boundary can affect resources outside the compromised guest.
19 · How does a supply-chain compromise differ from a local software vulnerability?
Answer: A supply-chain compromise can introduce malicious or vulnerable components before deployment, potentially affecting many downstream systems at once.

Why: The organization may inherit the compromise through a trusted supplier, build system, signing key or update mechanism rather than through a vulnerability discovered locally.
20 · What four questions should you ask about every critical platform security mechanism?
Answer: Ask: What state does it protect? Who can change that state? What evidence tells us it changed? How does the platform recover?

Why: These questions connect prevention, authority, detection and resilience into one architectural model.

Architecture exercise — answer in your own words

Imagine a laptop starts with an untrusted firmware image. Explain why a perfectly implemented web application cannot, by itself, establish that the machine is trustworthy. Then explain the additional layers that can establish and continuously evaluate trust: firmware authenticity, boot policy, measurements, protected keys, operating-system isolation, application security and operational recovery.
