01 · Computer architecture and security boundaries

A computer is a collection of components that execute instructions, store state and communicate with devices. At the security boundary, the important question is not simply what component exists? but what authority does it have and what state can it influence?

CPU, registers and execution state

The CPU executes instructions using architectural state such as general-purpose registers, an instruction pointer, flags and control registers. On x86-64, the instruction pointer is RIP; on 32-bit x86 it is EIP. Other CPU architectures use different register names and execution models.

Registers are not ordinary RAM. They are part of the processor's immediate execution state. Security-relevant bugs can occur when software unintentionally changes a value that later controls a memory address, branch target, privilege decision or system call.

Privilege levels

Modern processors provide mechanisms that let operating systems distinguish privileged code from less-privileged code. The exact mechanism varies by architecture. The operating system uses these facilities to prevent an ordinary application from freely manipulating kernel memory, device state or security-critical configuration.

Security principle: every higher layer depends on the lower layer maintaining its security assumptions. If an attacker can replace trusted firmware or gain equivalent privileged hardware control, application-level authentication and authorization cannot restore trust in that machine.

02 · Memory hierarchy and caches

Memory is hierarchical because fast storage close to the CPU is expensive and limited while larger storage is slower. A simplified path is registers → CPU caches → main memory → persistent storage.

Cache hierarchy

CPU caches keep recently used data closer to execution units. L1 is typically smaller and faster than L2, while L3 is generally larger and shared more broadly on many processors. The exact organization is architecture-specific.

A cache hit retrieves data from the expected cache level. A cache miss requires fetching data from a lower level. These timing differences can become security-relevant because an observer may sometimes infer information from how long an operation takes.

Side channels

A side channel leaks information through an observable property that is not the intended output of a computation: timing, cache state, power consumption, electromagnetic emissions or other physical effects. A cryptographic algorithm can be mathematically correct and still leak secrets through its implementation.

Defenses depend on the channel. Constant-time implementations reduce timing leakage for sensitive operations; isolation, hardware features and careful system design can reduce cross-tenant leakage. No single mitigation eliminates every side channel.

03 · Instruction execution, endianness and calling conventions

Instruction pointer and control flow

The instruction pointer identifies the next instruction in the architectural execution stream. Branches, calls, returns, exceptions and interrupts change control flow. Security researchers care about control flow because memory-corruption vulnerabilities can sometimes corrupt data that influences where execution proceeds.

Endianness

Endianness describes the order in which the bytes of a multi-byte value are represented in memory. Little-endian systems store the least-significant byte at the lowest address; big-endian systems store the most-significant byte first. Network protocols often specify their own byte order, commonly called network byte order.

Calling conventions

A calling convention defines how functions receive arguments, return values and preserve registers. It also establishes how stack frames and alignment are handled. Understanding calling conventions is essential when reading assembly, debugging crashes and analyzing binary interfaces.

Why this matters to security

Binary exploitation and reverse engineering depend on these details because a crash is ultimately a change in machine state. To distinguish a harmless crash from a control-flow vulnerability, an analyst must understand which values were corrupted, which instruction consumed them and what privilege the affected process had.

04 · Stack, heap and memory safety

Stack

The stack commonly stores function call state, local variables and saved execution information. Its exact layout depends on architecture, compiler and calling convention. A stack buffer overflow occurs when a program writes beyond the intended bounds of an object located on or associated with the stack.

Heap

The heap supports dynamically allocated objects whose lifetime is controlled by the program or its runtime. Security failures include use-after-free, double-free, out-of-bounds access and allocator metadata corruption.

Common vulnerability classes

  • Out-of-bounds read: data is read beyond the intended object, potentially disclosing information.
  • Out-of-bounds write: data is written outside the intended object, potentially corrupting adjacent state.
  • Use-after-free: a program continues using an object after its storage has been released.
  • Double-free: the same allocation is released more than once, potentially corrupting allocator state.
  • Integer overflow: arithmetic wraps or truncates and can produce an incorrectly sized allocation or bounds check.

Mitigation layers

Stack canaries can detect some stack overwrites. DEP/NX can prevent execution from selected writable memory. ASLR randomizes important addresses. Control-flow protections and hardened allocators add further barriers. These mechanisms raise the cost of exploitation; they do not make memory-unsafe code safe.

Engineering lesson: the strongest long-term mitigation is eliminating memory-safety errors where practical through memory-safe languages, safer APIs, compiler hardening, fuzzing, sanitizers and disciplined ownership/lifetime design.

05 · Firmware and UEFI

What firmware does

Firmware is software stored in non-volatile platform components that initializes hardware and provides low-level functionality before or alongside the operating system. Platform firmware can configure processors, memory, devices and the boot environment.

UEFI defines a standardized interface between platform firmware and operating-system loaders and can provide boot and runtime services. The UEFI Forum currently lists UEFI Specification 2.11 as its latest UEFI specification and Platform Initialization 1.10 as its latest PI specification. citeturn0search5

Why firmware is high impact

Firmware operates earlier and often with more privilege than the operating system. A persistent firmware compromise can survive operating-system replacement and can interfere with security software. NIST SP 800-193 therefore frames platform firmware security around protect, detect and recover from unauthorized changes. citeturn0search3

Firmware security properties

  • Authenticity of firmware images and updates.
  • Integrity of the boot chain.
  • Protection of firmware configuration.
  • Controlled update and rollback behavior.
  • Recovery from failed or malicious firmware updates.
  • Auditable provenance of components and firmware versions.

06 · Secure Boot and the chain of trust

Secure Boot

Secure Boot establishes a policy for which boot components are trusted to execute. The platform validates signatures or trust relationships before allowing a boot component to run. The objective is to prevent unauthorized modification of the boot path from silently becoming trusted execution.

Secure Boot is not equivalent to “the computer is secure.” It primarily protects the authenticity of the boot chain. Once a trusted component is running, vulnerabilities in that component can still compromise the system.

Chain of trust

A chain of trust begins with an assumed root of trust and extends verification to later components. A simplified model is:

hardware / platform root → firmware → boot manager → operating-system loader → kernel → system components

Each link must make a defensible decision about what it is willing to trust. If a trusted signing key is compromised or a trusted component has a vulnerability, the chain can still be abused.

07 · TPM 2.0, measured boot and roots of trust

What a TPM is

A Trusted Platform Module (TPM) is a security component designed to provide protected cryptographic and platform-trust capabilities. The TPM 2.0 specification defines cryptographic algorithms, authorization mechanisms and management facilities. The Trusted Computing Group lists TPM 2.0 Library Specification version 185, released March 2026, as its current library specification. citeturn0search12

Measurements and PCRs

Measured boot records measurements of boot-related components and extends them into Platform Configuration Registers (PCRs). A PCR is not simply a writable database entry: the extend operation combines the previous PCR value with a new measurement, creating a cumulative history representation.

PCR_new = H(PCR_old || measurement)

The measurement itself does not automatically prove that a component is malicious or benign. Its value comes from comparing the resulting state against an expected or policy-approved state and from preserving the associated event log.

Attestation

Attestation can allow a verifier to obtain cryptographic evidence about platform measurements. This can support decisions such as whether a workload should receive access to a sensitive resource. Attestation is a trust mechanism; it does not replace application authorization or vulnerability management.

Root of trust

A root of trust is a component or mechanism whose correct behavior is assumed or independently protected strongly enough to anchor further security decisions. Hardware roots of trust can improve assurance because some secrets and measurements are protected outside ordinary application memory.

08 · UART, JTAG, SPI, I2C and physical attack surface

UART

UART is a common asynchronous serial interface. Embedded devices may expose UART for manufacturing, debugging or console access. An exposed diagnostic console can become a security issue if it provides privileged access without strong controls.

JTAG

JTAG is a standardized family of test/debug interfaces used for boundary scan and hardware debugging. Development interfaces can expose powerful capabilities, so production devices should control, disable or authenticate them according to the device's security requirements.

SPI

SPI is a synchronous serial bus commonly used to connect flash memory and peripherals. Firmware storage on SPI flash makes the bus and flash contents part of the platform security boundary.

I2C

I2C is a multi-device serial bus used extensively in embedded systems. Devices communicate through addresses and shared signaling. The security of an I2C-connected component depends on physical access, bus configuration and the privileges of the firmware controlling it.

Important: hardware debugging tools can be legitimate research instruments, but connecting to or modifying equipment you do not own or have explicit authorization to test is not a valid security exercise.

09 · Hardware and firmware supply-chain security

Why supply chain matters

A modern platform depends on silicon vendors, motherboard manufacturers, firmware suppliers, device drivers, update services and component libraries. Security therefore begins before the organization receives the machine.

Threats

  • Counterfeit or substituted components.
  • Compromised firmware build systems.
  • Unsigned or weakly authenticated firmware updates.
  • Malicious or vulnerable third-party firmware components.
  • Compromised signing keys.
  • Insufficient inventory and inability to determine affected versions.

Controls

Useful controls include component inventories, provenance requirements, signed firmware, protected signing infrastructure, secure update mechanisms, rollback/recovery plans, vendor assurance, vulnerability disclosure processes and lifecycle tracking.

NIST IR 8320 describes hardware-enabled security as a foundational layer for cloud and edge platforms and discusses technologies including roots of trust, TPMs, secure enclaves and hardware security modules. citeturn0search9

10 · Bare-metal security engineering

Threat-model the platform

Start with assets, adversaries, physical access assumptions, trust boundaries, recovery capabilities and acceptable failure modes. A laptop used in a controlled office has different physical assumptions from an exposed industrial controller or an internet-connected edge device.

Layer the controls

  • Physical: restrict access to devices, debug ports and removable components.
  • Firmware: signed updates, secure configuration and recovery mechanisms.
  • Boot: Secure Boot and measured boot where supported.
  • Hardware trust: TPM or other roots of trust appropriate to the platform.
  • Operating system: least privilege, isolation, patching and endpoint controls.
  • Application: memory safety, authentication, authorization, validation and secure updates.
  • Operations: inventory, telemetry, incident response and recovery testing.

What a security engineer should be able to explain

By the end of this discipline, you should be able to trace a machine from power-on through firmware and boot into the operating system; explain where trust is established; distinguish Secure Boot from measured boot; describe what a TPM contributes; explain why memory hierarchy and physical interfaces matter; identify firmware and hardware supply-chain risks; and connect these low-level mechanisms to higher-level application security.

Core mental model: security is a chain of assumptions. The job is to identify the assumptions, protect the trust anchors, detect when assumptions fail, and design recovery when prevention is not enough.
