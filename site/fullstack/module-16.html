1. The data-engineering mental model

A database is not just a place to put objects. It defines how data is stored, queried, constrained, updated and recovered. Start from access patterns and correctness requirements: what must be atomic, what can be eventually consistent, which queries are frequent, and how quickly data grows.

01Model
02Query
03Index
04Measure

System of record

The authoritative store for business facts. For many applications this may be PostgreSQL or another transactional database.

Derived index

A structure optimized for retrieval, filtering or ranking. It can be rebuilt when the source of truth is available.

Core principle: specialized search should normally improve retrieval without silently becoming the only copy of business-critical data.

2. Relational vs document modelling

Relational modelling makes relationships, constraints and transactional operations explicit. Document modelling groups data around an aggregate that is commonly read or changed together. Neither shape is universally superior.

Prefer relational structure when

Many entities relate to each other, constraints matter, joins are central, or transactional integrity spans multiple records.

Document modelling fits when

A bounded object is commonly fetched as one unit and embedding reduces unnecessary round trips.

Embedding

Keep tightly coupled data inside the parent document when its lifecycle and access pattern justify it.

Referencing

Keep independently growing or shared data separate when duplication would become costly or inconsistent.

MongoDB's modelling guidance emphasizes designing around application access patterns rather than translating relational tables mechanically into documents.

3. MongoDB foundations

MongoDB stores BSON documents in collections. Learn documents, fields, arrays, nested objects, ObjectId identifiers, CRUD operations, aggregation and indexes before attempting advanced distributed features.

{
  "_id": "course-101",
  "title": "TypeScript Foundations",
  "stage": 5,
  "lessons": [
    { "id": "types", "title": "Types", "duration": 35 },
    { "id": "generics", "title": "Generics", "duration": 42 }
  ],
  "published": true
}

The key design question is not “can MongoDB store this?” It is “what operations should be cheap, atomic and predictable?”

4. Aggregation pipelines

Aggregation lets you transform and summarize documents through a sequence of stages. Think of a pipeline as a data-processing program: filter early when possible, project only what is needed, group deliberately, and understand the cost of each stage.

match → project → unwind → group → sort → limit

Do not assume an aggregation is fast because it returns the correct answer. Inspect indexes, cardinality, intermediate results and execution behavior.

5. Indexes: speed with a cost

An index provides an alternate access path to data. It can turn an expensive scan into an efficient lookup, but indexes consume storage and add work to writes. Index design must follow real query patterns.

Single-field

Useful for queries dominated by one field.

Compound

Supports multiple fields when field order matches important query and sort patterns.

Unique

Can enforce uniqueness where the data model requires it.

Text/search indexes

Useful for specific text retrieval, but dedicated search engines may provide richer relevance capabilities.

Rule: never add indexes blindly. Measure representative queries and account for write amplification and storage.

6. Transactions and consistency

Document databases can support atomic operations and transactions, but a transaction is not a substitute for good modelling. Keep naturally atomic changes together where possible. When operations span systems, database transactions alone cannot make the entire distributed workflow atomic.

7. What search actually solves

A normal database query usually answers a precise predicate: stage = 5, published = true, or an exact identifier. Search addresses a different interaction: a user supplies imperfect text and expects relevant results.

Keyword retrieval

Find documents containing meaningful terms rather than requiring exact structured predicates.

Filtering

Restrict results by stage, category, author, status or other structured fields.

Faceting

Show counts grouped by useful attributes so users can refine a result set.

Ranking

Order results according to relevance signals rather than simply by ID or insertion time.

8. Inverted indexes and tokenization

Search engines commonly build an inverted index: terms point to documents in which they occur. Before indexing, text may be tokenized and normalized. Decisions about case, punctuation, stemming, stop words, synonyms and language all affect recall and precision.

"React Server Components"
        ↓
 tokenize
        ↓
 react | server | components
        ↓
 inverted index
        ↓
 document candidates

An analyzer is therefore part of product behavior. Changing analysis rules can change search results even when the underlying documents have not changed.

9. Ranking and relevance

Finding matching documents is only half the problem. Users care about ordering. Relevance can incorporate term frequency, field importance, exact matches, freshness, popularity or application-specific signals depending on the search engine.

Precision

How much of what you returned is relevant.

Recall

How much of the relevant material you managed to retrieve.

Autocomplete

Optimize for fast partial-input interaction, not the same workload as full search.

Typo tolerance

Useful for human input, but it can introduce surprising matches and extra query work.

10. Filters, facets and pagination

Search UIs often combine free text with structured filters. Define which fields are filterable, sortable and facetable before indexing them. For deep pagination, understand the limitations of offset-based approaches and the alternatives supported by your search technology.

query: "typescript"
filters:
  stage: 5
  published: true
facets:
  stage
  difficulty
sort:
  relevance DESC

11. Search engines

Elasticsearch, Algolia and Meilisearch solve overlapping search problems with different operational and product models. Learn the common architecture first, then learn the provider-specific APIs.

Elasticsearch

Broad search and analytics platform with extensive indexing, querying and aggregation capabilities.

Algolia

Hosted search platform oriented around fast application search experiences and relevance tooling.

Meilisearch

Search engine designed for developer-friendly, fast application search with built-in relevance behavior.

PostgreSQL search

Often a strong option when search requirements are moderate and keeping fewer systems matters.

Choosing a search engine is an architecture decision. Consider query complexity, scale, latency, relevance controls, operational burden, cost and team capability.

12. Synchronizing the search index

The database and search index are two systems. A naive dual-write can fail between writes. For example, the database commit may succeed while the search update fails.

Unsafe dual write
DB write ✓
Search write ✗
→ inconsistent state

Safer patterns include an outbox, change-data capture, provider-managed indexing pipelines or periodic rebuilds. The right choice depends on the database, search platform and freshness requirement.

13. The outbox pattern

With an outbox, the application records the business change and an event describing the required downstream work in the same database transaction. A worker later publishes or applies that event.

BEGIN
  UPDATE courses ...
  INSERT INTO outbox(event_id, type, payload)
COMMIT

worker → search index
       → mark event processed

This does not make the search system instantly consistent. It makes the change durable and gives the system something that can be retried and replayed.

14. Rebuilds, replay and recovery

A production search index should be disposable. If an index becomes corrupt, its mapping changes, or synchronization falls behind, you need a controlled rebuild process.

01Create new index
02Backfill source
03Verify counts
04Switch alias

Keep enough metadata to identify the source version, index version and synchronization position. Never make an unrecoverable search index the only copy of important business data.

15. Search reliability and observability

  • Measure query latency by percentile, not only averages.
  • Track zero-result searches.
  • Track indexing lag.
  • Track indexing failures and retry counts.
  • Measure index document counts against the source.
  • Record search-engine errors without leaking sensitive query content into logs.
  • Monitor resource saturation and rejected requests.

Zero-result queries are especially useful product signals: they can reveal missing content, poor analysis, bad ranking or vocabulary that the product does not yet support.

16. Deliberate failure drills

Drill A — stale index

Update a course in the database while the search worker is offline. Restore the worker and prove the index catches up.

Drill B — duplicate event

Replay the same outbox event twice. Prove the resulting index state remains correct.

Drill C — bad analyzer

Change tokenization and compare result sets. Identify which queries gained or lost relevance.

Drill D — failed rebuild

Interrupt an index rebuild halfway through. Demonstrate that the currently serving index remains usable.
