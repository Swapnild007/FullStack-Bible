1. The system-design mental model

System design is not a contest to name the most technologies. It is the discipline of turning requirements and workload into explicit boundaries, data flows, capacity assumptions, failure behavior and measurable trade-offs.

01Requirements
02Workload
03Architecture
04Failure
05Verify

Functional requirements

What must the system do? Example: learners can open a course, save progress, search lessons and receive an AI-generated explanation.

Non-functional requirements

How well must it work? Define latency, availability, durability, security, throughput, freshness and recovery expectations.

Workload

Estimate requests per second, concurrent users, read/write ratio, payload size, storage growth and peak-to-average traffic.

Constraints

Budget, team size, existing infrastructure, compliance, operational maturity and time-to-market are architecture inputs.

Rule: Do not scale a component before identifying the bottleneck. A faster application tier cannot fix an exhausted database connection pool.

2. Capacity planning without pretending to know the future

Start with assumptions and label them. A useful first model is:

requests_per_second = daily_requests / 86,400
peak_rps = average_rps × peak_factor
concurrency ≈ throughput × average_latency_seconds

If a learning platform receives 4.32 million requests per day, the average is 50 requests/second. If traffic peaks at 6× average, the planning peak is 300 requests/second. This is a planning assumption, not a measured fact.

Measure before multiplying

  • Measure real request rate and latency distributions.
  • Separate average latency from p95/p99 latency.
  • Identify CPU, memory, network, database and external-service saturation.
  • Load-test the actual critical path instead of testing an isolated function and assuming the result represents the system.
Do not confuse capacity with availability. A system can have enough CPU and still fail because a dependency is unavailable, a connection pool is exhausted or a queue is growing without bound.

3. Traffic flow: DNS, CDN, proxy and load balancer

A request often crosses several boundaries before application code runs. Each boundary has a job and a failure mode.

Browser │ ▼ DNS ──► CDN / edge cache │ ▼ Reverse proxy │ ▼ Load balancer ┌───┼───┐ ▼ ▼ ▼ App App App └───┼───┘ ▼ Database / cache / queue

Load balancing

  • Round robin: distributes requests in sequence; simple but not workload-aware.
  • Least connections: can help when request duration varies.
  • Health checks: keep known-unhealthy instances out of rotation.
  • Connection draining: lets an instance finish in-flight work during deployment or shutdown.
  • Client affinity: sometimes useful, but often hides statefulness that should instead be moved to shared durable storage.

TLS termination

HTTPS can terminate at an edge or load-balancing layer, but the internal path still needs an explicit trust model. Do not assume that an internal network is automatically trusted.

4. Stateless application tiers

Horizontal scaling becomes easier when any healthy application instance can handle any request. Avoid storing user session state only in process memory when requests can move between instances.

Good shared state

Database records, durable object storage, managed session storage or a deliberately designed distributed cache.

Risky local state

In-memory sessions, local uploaded files, process-only queues and assumptions that the next request reaches the same server.

// Prefer a request that can succeed on any instance
GET /api/courses/42
        │
        ├── instance A ──┐
        ├── instance B ──┼──► shared durable state
        └── instance C ──┘

Stateless does not mean “the system has no state.” It means the application process does not depend on private local state for correctness.

5. Caching as a correctness decision

Caching trades freshness and memory for lower latency and lower origin load. The key questions are: what is the source of truth, how stale may the result be, who invalidates it, and what happens when the cache is empty?

Cache-aside

Request │ ▼ Cache ── hit ──► return │ miss ▼ Database ──► store result ──► return

Failure modes

  • Cache stampede: many requests miss simultaneously and overload the origin.
  • Stale data: a cached answer outlives the freshness requirement.
  • Hot key: one popular item concentrates load.
  • Negative caching: repeated requests for a missing resource can also require controlled caching.
  • Invalidation bugs: the cache may contradict the source of truth.

At the HTTP layer, browsers and shared caches use directives such as Cache-Control; validators such as ETag can allow a cache to revalidate without downloading an unchanged representation.

Cache-Control: max-age=60
ETag: "course-42-v18"

GET /courses/42
If-None-Match: "course-42-v18"

→ 304 Not Modified

6. Database scaling: optimize before distribute

Database scaling is a sequence, not a single feature. Start with query correctness and measurement, then address connection pressure, read volume, storage growth and write throughput.

01Query plan
02Indexes
03Pool
04Replica
05Partition

Read replicas

Replication can increase read capacity and provide additional recovery options, but replicas introduce replication lag. A request that writes data and immediately reads from a lagging replica may observe an older state.

Partitioning

Partitioning splits a logical table into physically managed pieces according to a partition key. A good key supports pruning and operational needs; a poor key simply moves the bottleneck.

Sharding

Sharding distributes data across independent database nodes. It can increase capacity but makes routing, rebalancing, cross-shard operations, backups and consistency more complex.

Architecture smell: “We will shard it” is not a capacity plan. Identify the access patterns and the actual resource that is saturating first.

7. Queues, workers and asynchronous processing

Queues are useful when work is slow, bursty, retryable or independent of the user's immediate response. The request can persist a job and return while workers process it later.

HTTP request │ ├── validate ├── persist intent └── publish job ─────► Queue │ ┌─────────┴─────────┐ ▼ ▼ Worker A Worker B │ │ └──────► service ───┘ │ success / retry │ DLQ

Delivery is not completion

A message being delivered to a worker does not mean the business operation succeeded. Durable messaging systems commonly use acknowledgements so work can be redelivered when a consumer dies before completion.

Backpressure

If producers create jobs faster than workers can complete them, queue depth grows. Monitor queue age and depth, limit concurrency, scale workers deliberately and decide what should happen when the system cannot keep up.

attempt = 1
wait = min(baseDelay * 2 ** (attempt - 1), maxDelay)
// add bounded jitter in production

8. Distributed failure: timeouts, retries and idempotency

Once a system crosses a network boundary, failure becomes partial. One component can be healthy while another is slow, unreachable or returning errors.

Timeout

Bounds how long a caller waits. Every network dependency needs an explicit budget.

Retry

Repeats an operation after a failure. It must be bounded and applied only when retrying is safe.

Backoff

Spreads retries over time so a failing dependency is not hammered by synchronized clients.

Idempotency

Allows repeated requests to have the same intended effect as one request.

Why retries can amplify an outage

Suppose 1,000 clients each send one request to a slow dependency. If every client retries three times immediately, the dependency can receive up to 4,000 attempts. A recovery mechanism has become a load multiplier.

Idempotent mutation pattern

POST /api/enroll
Idempotency-Key: 8b2f...

server:
  validate request
  begin transaction
  if key already completed:
      return stored result
  create enrollment
  store key + result
  commit
Important: idempotency is an application property. A unique key in a database, transaction boundaries and a durable record of the result often form the foundation.

9. Consistency and distributed state

Consistency describes what readers can observe as data changes. Do not reduce the subject to “strong versus eventual” as a slogan; define the behavior the product actually needs.

  • Strong read-after-write behavior: useful when a user must immediately see a committed change.
  • Eventual consistency: replicas or derived views may converge after a delay.
  • Ordering: consumers may need an ordering key when event sequence matters.
  • Deduplication: repeated delivery requires a safe way to recognize work already applied.
  • Conflict handling: concurrent writers need explicit rules rather than an assumption that timing will always be favorable.
Design exercise: For each feature, write the sentence “After action X, the user must be able to observe Y within Z.” That turns vague consistency requirements into testable behavior.

10. Reliability patterns

Reliable architecture is designed around failure, not merely around the happy path. Useful patterns include graceful degradation, throttling, bounded queues, timeouts, health checks, stateless services and emergency controls.

Graceful degradation

If recommendations fail, the course page can still render. A non-critical dependency should not automatically become a total outage.

Bulkheads

Isolate resource pools so one expensive workload cannot consume every connection or worker.

Circuit breaking

Stop repeatedly calling a failing dependency for a controlled period, then probe recovery.

Emergency levers

Feature flags, rate limits or kill switches can reduce load while preserving the core path.

11. Architecture boundaries: monolith → modular monolith → services

A monolith is not automatically poorly designed. A modular monolith can provide strong boundaries while keeping deployment and operations simple.

Learning Hub — modular monolith ┌───────────────────────────────────────────┐ │ Web App │ ├────────────┬────────────┬─────────────────┤ │ Identity │ Learning │ Search │ ├────────────┼────────────┼─────────────────┤ │ Billing │ Progress │ Notifications │ └─────┬──────┴─────┬──────┴────────┬────────┘ │ │ │ └────────────┴───────┬───────┘ ▼ PostgreSQL │ Queue / Workers

Extract a service when there is a concrete reason: independent scaling, a clear ownership boundary, isolation requirement, different runtime needs or an organizational boundary. Service count is not a maturity metric.

12. Observability for system design

A distributed system cannot be debugged reliably from one server log. Build a view across requests, dependencies and asynchronous work.

Logs

Structured events with request IDs, operation names, outcome and safe diagnostic context.

Metrics

Request rate, latency, errors, saturation, queue depth, database connections and cache hit rate.

Traces

Follow a request across services and dependencies to locate latency and failure boundaries.

Business signals

Enrollment completion, checkout success or lesson-open rate can reveal failures that infrastructure metrics miss.

trace_id=abc123
  web.request  120ms
    db.query    22ms
    cache       2ms
    ai.call     81ms
  result=200

13. Hands-on lab — break a distributed Learning Hub

Do this on paper first, then implement a small simulation if you can. Your objective is to learn the reasoning loop: observe → isolate → choose a control → verify.

  1. Draw the request path for opening a lesson.
  2. Introduce a slow database response.
  3. Add a 2-second dependency timeout.
  4. Decide whether the request should retry.
  5. Add bounded exponential backoff with jitter.
  6. Move non-critical work to a queue.
  7. Define what the user sees when the queue or dependency is unavailable.
  8. Define metrics that prove the mitigation works.

Failure drills

Drill A — cache outage

Cache is unavailable. Decide whether the application fails open to the database, degrades, or rejects requests. Explain the load consequences.

Drill B — worker death

A worker crashes after performing an external side effect but before acknowledging the job. Explain how duplicate delivery can occur and how idempotency protects the operation.

Drill C — replica lag

A user updates their profile and immediately reads from a replica. Explain the stale-read behavior and choose an appropriate consistency strategy.

Drill D — retry storm

An upstream service becomes slow. Ten application instances retry immediately. Design controls that stop the feedback loop.

14. Capstone — 10× Learning Hub architecture

Design the next version of FullStack Bible as if traffic, stored learning data and asynchronous work will each grow by 10×. Do not begin by choosing vendors. Begin with requirements and measurable assumptions.

Deliverable A — requirements

  • Functional requirements for learning, search, progress and AI assistance.
  • Latency and availability expectations for each critical path.
  • Consistency expectations for progress and account state.
  • Security and privacy boundaries.

Deliverable B — architecture

  • Request-flow diagram from browser to data stores.
  • Application scaling strategy.
  • Cache strategy and invalidation rules.
  • Database indexing, pooling, replication and partitioning plan.
  • Queue and worker architecture.
  • Failure isolation and graceful degradation plan.

Deliverable C — reliability

  • Timeout budget for every remote dependency.
  • Retry policy with backoff and idempotency.
  • Queue retry and dead-letter policy.
  • Health checks and emergency controls.
  • Logs, metrics and traces required to diagnose incidents.

Deliverable D — trade-offs

For every major decision write: problem → option → reason → cost → failure mode → measurement. A good architecture is explainable, not merely complicated.

Definition of done: another developer should be able to read your design and understand what happens on the happy path, under peak load, when a dependency is slow, when a worker dies, when data is stale and when the system needs to recover.
