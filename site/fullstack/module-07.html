The mental model

A full-stack app has more than a screen.

A real application has a user interface, URLs, server execution, data access, validation, navigation and states for success, loading and failure. Next.js is a React framework for building full-stack web applications and its current documentation recommends the App Router for newer React features. Next.js Docs

Browser

Displays the interface and runs client-side code where interaction requires it.

Next.js server

Receives requests, renders server components and can execute server-only logic.

Routes

Map URLs to pages and layouts using the App Router's file-system conventions.

Data

Comes from databases, APIs or other services. Secrets stay on the server.

Core idea: do not think “Next.js is React plus some extra files.” Think in terms of an application request moving through routes, server work, client interaction and data.
01 · Next.js

Understand what the framework is doing for you.

Why a framework?

React gives you a way to build interfaces. A full application also needs conventions for routing, rendering, data access, navigation, bundling and deployment. Next.js supplies those conventions so you can build the application rather than assembling every infrastructure piece yourself.

The current Next.js learning path explicitly teaches building a full-stack application with the App Router, including routing, data fetching, authentication and mutations. Next.js App Router course

The App Router mental model

The app directory contains route segments and special files. A page.tsx makes a route publicly accessible. A layout.tsx creates shared UI around nested pages. Other special files handle application concerns such as loading and error states.

app/
├── page.tsx
├── layout.tsx
└── dashboard/
    ├── layout.tsx
    ├── page.tsx
    └── settings/
        └── page.tsx

This produces a root route, a dashboard route and a nested dashboard settings route. Layouts can persist while child pages change during navigation.

Navigation

For navigation inside a Next.js application, use the framework's Link component rather than treating every internal navigation as a fresh browser document load. Next.js can perform client-side navigation and production prefetching for links.

import Link from "next/link";

export function Nav() {
  return (
    <nav>
      <Link href="/dashboard">Dashboard</Link>
      <Link href="/settings">Settings</Link>
    </nav>
  );
}
02 · Routing

Turn a folder structure into an application map.

Static routes

In the App Router, folders represent route segments and a page.tsx file makes the segment accessible. This is file-system routing.

app/
  lessons/
    page.tsx        → /lessons
  profile/
    page.tsx        → /profile

Keeping route-specific UI near its route also makes larger applications easier to navigate.

Dynamic routes

When the URL contains a value such as a lesson ID, use a dynamic segment.

app/lessons/[id]/page.tsx

// /lessons/42
// /lessons/react-components

The dynamic segment becomes data that the page can use to select the correct resource.

Layouts and shared UI

A layout wraps the pages beneath it. This is useful for navigation, sidebars, headers and other UI that should remain shared across a section. Next.js documents nested layouts as a core App Router concept.

app/dashboard/layout.tsx

export default function Layout({ children }: {
  children: React.ReactNode
}) {
  return <div className="dashboard">{children}</div>;
}

Think of the layout as the frame and the page as the current view inside that frame.

Loading, error and not-found states

Applications need explicit behaviour when work is still happening, when something fails, or when a requested resource does not exist. Next.js provides special route-level conventions for these states. Do not design only the successful path.

03 · Server & client code

Learn where your code runs.

Two environments

The browser and server are different environments. Server code can safely access server-only resources such as private environment variables and database credentials. Client code runs in the user's browser and can respond directly to interaction.

In the App Router, components are Server Components by default. When a component needs client-side interactivity such as state or event handlers, you explicitly mark it as a Client Component with "use client". Next.js: Server and Client Components

Choose the boundary deliberately

// Server Component by default
export default async function Page() {
  const lessons = await getLessons();
  return <LessonList lessons={lessons} />;
}

// Client Component
"use client";

import { useState } from "react";

export function LikeButton() {
  const [liked, setLiked] = useState(false);
  return (
    <button onClick={() => setLiked(!liked)}>
      {liked ? "Liked" : "Like"}
    </button>
  );
}

The server can prepare data and the client can handle interaction. Keep the client boundary as small as practical when interactivity is local.

Server-side data access

Server Components can fetch data directly on the server. This can avoid creating an unnecessary API layer for internal server-to-database access. If the browser itself needs an endpoint, or a third-party client must call your application, a Route Handler can provide an HTTP API.

Never put database credentials, private API keys or other secrets into Client Components.

Do not confuse server and browser APIs

Browser-only objects such as window and localStorage are not available during server execution. Conversely, server secrets and database connections should not be shipped to the browser. The network boundary is part of your application design.

04 · Application flows

Build the journey, not isolated screens.

A full-stack feature is a chain of events. For example, creating a lesson might begin with a form, cross the browser/server boundary, validate input, save data and return a new UI state.

1
User action
2
Client UI
3
Server work
4
Data change
5
Updated UI

Example: create a lesson

  1. User opens /lessons/new.
  2. The page renders a form.
  3. The user submits a title and description.
  4. Input is validated. Validation must happen on the server too; browser validation alone cannot be trusted.
  5. Server code writes the validated data to storage.
  6. The application redirects or renders the appropriate success state.
  7. The lessons list reflects the new item.

Example: view a lesson

/lessons/[id]

URL → route segment → server page
    → load lesson → validate existence
    → render content → client interaction

This way of thinking scales to authentication, dashboards, checkout, content management and other products. Start by describing the user's journey, then decide which steps belong on the server and which need the browser.

Data fetching without accidental waterfalls

If independent server requests can begin at the same time, start them together rather than waiting for one to finish before starting another. JavaScript's Promise.all() is one common pattern. The official Next.js course specifically teaches parallel data fetching to avoid unnecessary network waterfalls. Next.js: Fetching Data

const [profile, lessons] = await Promise.all([
  getProfile(),
  getLessons()
]);
Capstone · Full-stack learning app

Build a real application flow.

Project: Learning Hub

Build a small Next.js application where a learner can browse lessons, open a lesson detail page, and create a personal learning item. The goal is not visual complexity. The goal is understanding the complete request and application flow.

Suggested structure

app/
├── layout.tsx
├── page.tsx
├── lessons/
│   ├── page.tsx
│   ├── [id]/
│   │   └── page.tsx
│   └── new/
│       └── page.tsx
├── ui/
│   ├── LessonCard.tsx
│   ├── LessonForm.tsx
│   └── Navigation.tsx
└── lib/
    └── lessons.ts

Build in this order

  1. Create the routes and shared layout.
  2. Create typed lesson data.
  3. Render the lesson list on the server.
  4. Add a dynamic lesson route.
  5. Add a client component where interaction requires browser state.
  6. Add the create-lesson flow.
  7. Add loading, empty, not-found and error states.
  8. Use DevTools to observe navigation and requests.
  9. Test the important user journeys.
Do not hide complexity with magic. If you cannot explain where a piece of code runs, how the URL reaches it, where the data comes from, and what happens after an error, stop and trace the flow before moving on.

Capstone questions

  1. Which components render on the server?
  2. Which component actually needs "use client", and why?
  3. What happens when the lesson ID does not exist?
  4. Where is input validated?
  5. Which data can safely remain server-only?
  6. What does the browser request during navigation?
  7. What happens while data is loading?
  8. What happens when the data source fails?
Application mutations & caching

Understand the server-side work that makes a full-stack app feel complete.

Server Actions are server-side mutations

In the Next.js App Router, a Server Action is an asynchronous server function that can be invoked from the client through React/Next.js mechanisms. Treat the action as a server entry point: validate its inputs, authorize the user, perform the mutation and return only the data the UI needs. Do not treat the existence of a Server Action as an authorization mechanism.

"use server";

export async function markLessonComplete(lessonId: string) {
  // validate lessonId
  // authenticate current user
  // authorize access to lesson
  // update database
  // return safe result
}

Keep secrets, database clients and privileged operations on the server. The browser should receive only what it is allowed to know.

Caching is a data-consistency decision

Next.js applications can cache different layers of work. The important question is not simply “how do I make this faster?” but “who is allowed to see this data, how fresh must it be, and what invalidates it?” Public content, user-specific data and permission-sensitive data have different caching requirements.

Cacheable

Stable public content that can safely be reused by many requests.

Must revalidate

Data whose freshness matters or whose audience can change.

Do not broadly cache

User- or permission-scoped responses unless the cache key and audience are explicitly safe.

Invalidate deliberately

After a mutation, decide which previously cached representation is now stale.
