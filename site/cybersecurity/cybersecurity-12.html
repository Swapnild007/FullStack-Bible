Cloud Infrastructure & Container Security.

Understand how cloud control planes, identities, networks, storage, workloads and container platforms create security boundaries—and how to design, harden, monitor and recover them.

Research boundary: This is theory-first defensive security education. Cloud and Kubernetes examples are architectural and hardening-oriented. Test only in accounts, clusters and environments you own or are explicitly authorized to assess.

01 · Cloud security as a shared-responsibility problem
Cloud security begins by identifying which controls are provided by the cloud service and which remain the customer's responsibility. The exact boundary changes between IaaS, PaaS and SaaS. Moving a workload to the cloud does not transfer accountability for identity, data classification, application security or secure configuration.
Core model: asset → identity → control plane → data plane → network path → workload → data → telemetry → recovery.

NIST describes public-cloud security in terms of security and privacy challenges created by outsourcing infrastructure and services. Treat the provider's documented security model as a dependency, not as a replacement for your own threat model.

02 · Cloud service models and trust boundaries
IaaS generally leaves customers with more responsibility for operating systems, workloads and network configuration. PaaS abstracts more infrastructure but makes platform configuration, application identity and data controls critical. SaaS shifts more operational responsibility to the provider while leaving tenant identity, data governance and configuration decisions important.

Threat modelling should draw explicit boundaries around provider-managed components, tenant-managed resources, management APIs and external integrations. A control that protects one boundary may not protect another.

03 · Cloud accounts, projects, subscriptions and tenancy
Cloud providers use organizational containers such as accounts, subscriptions, projects, folders or management groups. These become security and billing boundaries. Poor separation can turn a compromised development credential into production access or make recovery depend on the same compromised administrative plane.

Use organizational hierarchy deliberately: separate environments, constrain administrative paths, centralize security visibility where appropriate, and design emergency access independently enough to remain usable during an incident.

04 · Cloud IAM and least privilege
Identity is usually the central cloud security control plane. Human users, workloads, automation pipelines and services all need identities with defined permissions. Prefer short-lived credentials and role-based or attribute-aware policies over long-lived shared secrets.

Least privilege is not simply “few permissions.” It means permissions are limited by action, resource, environment, time and trust context where the platform supports those conditions. Review unused and excessive privileges continuously.

05 · Federation, workload identity and credential lifecycle
Federation allows an external identity system to authenticate users without creating independent long-lived credentials for every cloud service. Workload identity provides a similar principle for software: a workload receives an identity appropriate to its role rather than embedding a permanent cloud key in source code or an image.

Security depends on audience, issuer, trust conditions, token lifetime and the exact role granted after authentication. CI/CD identities deserve the same scrutiny as human administrators because pipelines can modify production infrastructure.

06 · Control plane versus data plane
The control plane manages resources: identities, networks, policies, clusters and configuration. The data plane carries application traffic or performs workload operations. Compromise of a control-plane identity can have broad consequences even when individual data-plane services are hardened.

Design separate administrative paths, monitor high-impact control-plane events, require strong authentication for privileged actions and make policy changes auditable.

07 · Cloud networking and segmentation
Cloud networks commonly use virtual networks, subnets, routing tables, security groups or equivalent controls, gateways, load balancers and private service connectivity. Security groups are typically stateful workload-level filters, while network ACLs and routing controls operate at other layers depending on the provider.

Segmentation should reflect trust boundaries rather than merely organizational labels. Sensitive data stores, management interfaces and production workloads should not depend on unrestricted east-west connectivity.

08 · Storage, encryption and data protection
Cloud storage spans object, block and database services. Security properties depend on identity policy, resource policy, encryption, key management, network exposure, retention and backup configuration. “Encrypted” does not mean “authorized”: an identity that can decrypt or retrieve the data may still be overprivileged.

Use classification to determine protection requirements. Separate encryption keys and administrative duties where risk warrants it, protect backups from the same credentials that protect production, and test restoration.

09 · Secrets and key management
API keys, database passwords, signing keys, certificates and tokens are credentials, not ordinary configuration. They should not be embedded in images, source repositories or logs. Central secret-management services can provide access control, rotation and audit trails, while hardware-backed key-management systems can protect cryptographic key material.

Rotation is only useful if applications can tolerate it. Design credential replacement as a lifecycle: issue → use → rotate → revoke → verify → recover.

10 · Virtual machines and host hardening
Cloud virtual machines still require operating-system security: patching, identity controls, firewalling, logging, secure configuration and workload isolation. The hypervisor provides a virtualization boundary, but a vulnerable guest OS or exposed management service remains a customer security issue.

Minimize installed components, restrict administrative access, use hardened images, automate patching where practical, and preserve forensic telemetry without exposing sensitive logs.

11 · Container fundamentals and image security
Containers package applications with dependencies while sharing a host kernel. They are not equivalent to full virtual machines. The container image, registry, runtime, host kernel, network and orchestration layer all contribute to the security boundary.

Image security begins with trustworthy base images, pinned or controlled dependencies, minimal packages, reproducible builds, vulnerability scanning and provenance. Treat registries as part of the software supply chain and restrict who can publish or deploy images.

12 · Container runtime isolation
Container security depends on Linux namespaces, cgroups, capabilities, seccomp, filesystem permissions and mandatory-access-control mechanisms such as SELinux or AppArmor where available. A container configured with excessive privileges can weaken the isolation expected by the workload.

Use the smallest practical privilege set, avoid unnecessary host filesystem exposure, constrain resources and understand which runtime features can cross the host boundary. NIST SP 800-190 treats the container image, registry, orchestrator, host and runtime as related security concerns.

13 · Kubernetes architecture and security boundaries
Kubernetes introduces an API-driven control plane: API server, authentication and authorization, scheduler, controllers and cluster state, plus worker nodes and workloads. The API is therefore a high-value security boundary.

RBAC controls which subjects can perform which API actions. Admission controls can validate or mutate requests. Pod Security Standards define Privileged, Baseline and Restricted profiles, while NetworkPolicy can constrain pod-to-pod and external traffic. These controls solve different problems and should be layered.

14 · Kubernetes RBAC, service accounts and secrets
Granting workload-creation privileges can indirectly expose other resources because a principal able to create a workload may influence which identities, volumes or secrets that workload can use. Kubernetes documentation specifically warns that broad workload-creation permissions can create privilege-escalation paths.

Use dedicated service accounts, narrowly scoped Roles/ClusterRoles, explicit bindings and regular permission review. Kubernetes Secrets are intended for confidential data, but their values are base64-encoded rather than automatically encrypted; configure encryption at rest and least-privilege access.

15 · Kubernetes network, admission and workload policy
NetworkPolicy controls allowed traffic paths when the network implementation supports it. Admission controls can enforce organizational policy before workloads are accepted. Pod Security Admission can enforce the Kubernetes Pod Security Standards at namespace scope.

Security policy should be declarative and version-controlled where practical. Combine identity, admission, workload security, network segmentation and runtime telemetry rather than expecting any one mechanism to contain every failure.

16 · Cloud-native supply chain and runtime security
The software supply chain includes source repositories, dependencies, build runners, container bases, registries, signing/provenance systems and deployment controllers. A trusted runtime cannot compensate for an untrusted artifact entering the deployment path.

Use dependency governance, artifact provenance, controlled registries, signing or verification where appropriate, isolated build identities and audit trails. At runtime, collect process, network, identity and orchestration telemetry so suspicious behavior can be investigated.

17 · Resilience, incident response and recovery
Cloud security includes the ability to contain and recover from compromise. Maintain independent or strongly protected backups, documented recovery roles, tested restoration, centralized security telemetry and emergency-access procedures. Recovery credentials should not depend entirely on the same identity plane that an incident may have compromised.

During an incident, preserve evidence, contain affected identities and workloads, determine the blast radius, rotate compromised credentials, restore from trusted artifacts and validate the environment before returning it to normal operation.

18 · Advanced cloud threat modelling
At advanced level, reason across identity, control plane, data plane, workload and supply chain together. Ask: What identity can make this change? What resource can it affect? Can the action cross an environment boundary? What telemetry proves it happened? Can the organization recover if that identity or control plane is compromised?

A mature architecture treats cloud security as a continuously evaluated system rather than a checklist. Policies, identities, images, networks and recovery paths all change; security controls must therefore be observable, testable and maintainable.

Mastery review · 20 questions with answers
01. What is the shared-responsibility model?It describes how security responsibilities are divided between the cloud provider and customer, with the exact boundary depending on the service model.
02. Why is cloud IAM so important?Cloud management APIs can create, modify or expose many resources, so an overprivileged identity can have broad impact.
03. What is workload identity?A mechanism that gives software a managed identity and permissions without requiring long-lived credentials embedded in code or images.
04. Why separate control plane and data plane thinking?They represent different trust and failure boundaries; control-plane compromise can enable changes across many data-plane resources.
05. Why separate production and development environments?It limits blast radius and prevents lower-trust identities or workloads from automatically inheriting production authority.
06. What does least privilege mean in cloud IAM?Grant only the actions, resources and conditions required for a defined task, then review and remove unnecessary access.
07. Why are long-lived cloud access keys risky?They can persist after the original task, are difficult to rotate safely and may be copied into source, images or logs.
08. What is a container security boundary?A layered boundary involving the image, runtime, host kernel, privileges, filesystem, network and orchestrator rather than the container alone.
09. Why are containers not the same as virtual machines?Containers generally share the host kernel, whereas a VM normally provides a stronger hardware-virtualization boundary with a separate guest kernel.
10. What does NIST SP 800-190 cover?It explains security concerns and recommendations for application container technologies across components such as images, registries, orchestrators, hosts and runtimes.
11. What are Kubernetes Pod Security Standards?Three cumulative policy levels—Privileged, Baseline and Restricted—that constrain pod configurations with increasing strictness.
12. What does Kubernetes RBAC control?Which authenticated subjects can perform specified API actions on specified Kubernetes resources.
13. Why can workload-creation permission be dangerous?A subject able to create workloads may be able to cause pods to consume sensitive identities, volumes or secrets, creating indirect privilege escalation.
14. Are Kubernetes Secrets encrypted by default?No. Kubernetes documents that Secret values are stored unencrypted in etcd by default; encryption at rest and least-privilege access should be configured.
15. What does NetworkPolicy provide?Declarative controls over permitted network traffic between pods and, depending on the implementation, traffic to or from external networks.
16. What is admission control?A control point in the Kubernetes API path that can validate or mutate requests before resources are accepted.
17. Why secure container images before deployment?A vulnerable or untrusted image can introduce risk before runtime controls have an opportunity to compensate for it.
18. What is cloud supply-chain security?Protecting source, dependencies, build systems, artifacts, registries, provenance and deployment identities so untrusted changes cannot silently reach production.
19. Why must cloud recovery be tested?Backups and recovery procedures that have never been restored may fail when needed; testing verifies integrity, permissions, dependencies and recovery time.
20. What is advanced cloud security reasoning?Tracing identities and actions across control plane, data plane, network, workload, supply chain, telemetry and recovery to understand blast radius and prevent recurrence.
Completion standard

You should be able to explain shared responsibility, cloud IAM and workload identity, control/data planes, network segmentation, storage and key management, container isolation, image supply-chain risk, Kubernetes RBAC, Pod Security Standards, NetworkPolicy, admission control, runtime telemetry and cloud recovery.

Practical work should use isolated cloud accounts, local clusters, deliberately vulnerable training environments or systems for which you have explicit authorization.
