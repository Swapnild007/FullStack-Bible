Before you begin

Learning objectives

The operating system is the layer where software requests become privileged actions. To understand endpoint compromise, privilege escalation, persistence, credential theft or container isolation, you need to understand what the kernel controls and what applications are allowed to request.

  • Explain user mode, kernel mode and the system-call boundary.
  • Describe processes, threads, scheduling and inter-process communication.
  • Explain virtual memory, page tables, permissions and copy-on-write.
  • Understand filesystems, file descriptors, permissions, ACLs and device interfaces.
  • Explain Linux namespaces, capabilities, cgroups and common isolation assumptions.
  • Understand Windows SIDs, access tokens, ACLs, privileges, LSA/LSASS and UAC.
  • Reason about debugging interfaces and why they can cross security boundaries.
  • Design useful host telemetry from process, identity, filesystem and network events.
Mental model: an operating system is an authority broker. Applications ask for resources; the kernel validates requests, changes protected state and enforces isolation. Cybersecurity is largely the study of what happens when that authority boundary is misunderstood, misconfigured or bypassed.
Chapter 01

What the kernel actually does

The kernel is privileged software responsible for coordinating hardware and providing controlled abstractions to applications. It is not simply “the background part of the OS.” It is the enforcement layer for many of the machine's most important security boundaries.

1.1 Resource management

The kernel manages CPU time, memory, devices, filesystems, networking and process execution. Applications generally do not manipulate these resources directly; they use operating-system interfaces.

1.2 Privilege boundary

Modern systems separate user mode from privileged kernel mode. User-mode code has restricted access to hardware and kernel memory. A controlled transition is required for privileged operations.

1.3 Security consequence

A compromised ordinary application is potentially contained by the OS security boundary. A kernel compromise is fundamentally different because kernel code can generally access the resources that the kernel itself controls.

This is why kernel vulnerabilities receive serious security attention: the vulnerable component is also an enforcement mechanism.

1.4 Kernel design styles

Operating systems use different architectural approaches, including monolithic kernels, microkernels and hybrid designs. The terminology describes where services and drivers execute, not a simple security ranking. The relevant security question is how much privileged code exists, how it is isolated and how failures propagate.

Chapter 02

Processes, threads and execution context

A process is a protected execution environment containing an address space and operating-system-managed resources. A thread is an execution path within that process.

2.1 Process

A process typically has a virtual address space, open handles or file descriptors, credentials/security context, environment and other kernel-managed state. The exact representation is OS-specific.

2.2 Thread

Threads share many process resources but maintain their own execution state, including registers and stack. Multiple threads can therefore execute concurrently within one process.

2.3 Scheduling

The scheduler decides which runnable thread receives CPU time. Context switching saves and restores execution state. Scheduling policy affects performance, responsiveness and sometimes security properties such as isolation and denial-of-service resistance.

2.4 Process creation

Unix-like systems commonly use fork/exec-style process creation, while Windows uses different process and thread creation APIs. The architectural idea is the same: the OS creates a new execution context and establishes its initial security state.

2.5 Parent-child relationships

Process ancestry is valuable security telemetry. Unexpected parent-child relationships can be suspicious, but ancestry alone is not proof of malicious behavior. Analysts need command lines, identities, signatures, network activity and surrounding context.

Chapter 03

Virtual memory and page-based isolation

Virtual memory is one of the most important OS security mechanisms because it controls which address spaces exist and which memory regions can be accessed.

3.1 Address translation

A process uses virtual addresses. Hardware memory-management units translate them through page-table structures into physical memory locations. The OS creates and manages those mappings.

virtual address → page-table translation → physical page + permissions

3.2 Page permissions

Page mappings can carry attributes such as readable, writable, executable and user/supervisor accessibility. These permissions support important defenses such as preventing ordinary user processes from executing kernel pages.

3.3 Copy-on-write

Copy-on-write lets multiple address spaces initially share physical pages until one needs to modify a page. The OS then creates a private copy. This improves efficiency while preserving isolation.

3.4 Memory-mapped files

Memory mapping lets a file or device region appear in a process's virtual address space. This can improve performance but also creates security concerns around permissions, lifetime, race conditions and untrusted content.

3.5 Swap and page reclamation

Operating systems may reclaim or move memory pages. Security-sensitive data can therefore have a more complicated lifetime than “it was in RAM.” Secure systems consider how credentials and secrets are handled across memory, crash dumps, hibernation and swap-related paths.

Linux's current memory-management documentation covers physical memory, page tables, process addresses, page allocation, page cache, swap, memory reclamation and out-of-memory handling. citeturn0search8

Chapter 04

System calls: crossing into privileged services

A system call is the controlled interface through which user-space software requests a kernel service.

4.1 Why system calls exist

An application cannot safely manipulate every hardware resource directly. Instead, it requests operations such as opening a file, creating a process, allocating mappings or sending network data through kernel APIs.

4.2 The boundary

A system-call transition changes execution context according to CPU and OS rules. The kernel validates arguments, checks permissions and performs or rejects the operation.

4.3 Input validation

Kernel code must treat user-provided pointers, lengths, identifiers and flags as untrusted. Bugs in this boundary can produce privilege escalation because a low-privilege process is interacting with highly privileged code.

4.4 Observability

Tools such as strace on Linux can expose system-call behavior. Similar tracing facilities exist on Windows. Security analysts can use system-call patterns to understand what a program actually requested rather than relying only on its filename or stated purpose.

Chapter 05

Inter-process communication and synchronization

Processes need controlled ways to exchange data and coordinate work. IPC mechanisms are therefore both functionality and security boundaries.

5.1 Common IPC models

Examples include pipes, Unix domain sockets, shared memory, message queues, signals, RPC mechanisms and network sockets. Windows provides named pipes, ALPC and other IPC facilities.

5.2 Shared memory

Shared memory is fast because processes can access the same underlying pages. The trade-off is synchronization and authorization complexity. A shared region must have an explicit ownership and access model.

5.3 Synchronization

Mutexes, semaphores, condition variables and atomic operations coordinate concurrent execution. Race conditions can become security vulnerabilities when a security decision and the protected state change are not atomic.

5.4 TOCTOU

A time-of-check-to-time-of-use race occurs when software checks a property and later uses the resource assuming the property remains unchanged. Between those moments, another actor may alter the resource.

Security lesson: “I checked it” is not enough if the system can change between the check and the security-sensitive operation.
Chapter 06

Filesystems, file descriptors and permissions

6.1 Files are more than documents

Operating systems expose many resources through file-like abstractions. On Unix-like systems, file descriptors can refer to regular files, directories, sockets, pipes, devices and other kernel objects.

6.2 Linux VFS

Linux's Virtual File System provides a common interface over multiple filesystem implementations. This lets applications use consistent operations while the kernel handles filesystem-specific behavior.

6.3 Permissions

Traditional Unix permissions express owner, group and other access for read, write and execute. ACLs can provide more detailed rules. Linux capabilities can separate selected privileged operations from the all-powerful root identity.

6.4 Windows object security

Windows uses security descriptors, access control entries and ACLs for securable objects including files, registry keys, processes, services and devices. Microsoft documents the model around SIDs, access tokens, security descriptors, ACLs and privileges. citeturn0search2turn0search4

6.5 Authorization versus auditing

A DACL controls who is allowed or denied access. A SACL can define auditing for selected access events. These are different purposes: preventing an action and recording an action are complementary controls.

Chapter 07

Linux security architecture

7.1 Users, groups and credentials

Linux processes operate with credentials that influence access decisions. User and group identities are foundational, but modern Linux also uses capabilities and security modules to express finer-grained policy.

7.2 Capabilities

Capabilities divide some traditional root powers into separate units. This supports least privilege by allowing a process to receive only selected privileged operations where appropriate.

7.3 Namespaces

Namespaces isolate views of kernel resources. Linux supports namespaces for areas including processes, mounts, networking, IPC, users and hostnames. They are a foundation of containers but should not be treated as an automatic guarantee of complete isolation. citeturn0search11

7.4 cgroups

Control groups organize processes and control/account for resources such as CPU and memory. They are important for resource governance and container isolation. Kernel documentation specifically discusses resource-control considerations when user namespaces are used. citeturn0search9

7.5 LSM

Linux Security Modules provide hooks through which security policy can be enforced. SELinux and AppArmor are important examples. Their models differ, but both can impose restrictions beyond traditional discretionary permissions.

Chapter 08

ptrace, debugging and privileged observation

Debugging is inherently powerful because it lets one execution context inspect another. Security therefore requires controls around who may trace or modify processes.

8.1 What ptrace enables

On Linux, ptrace-related facilities can observe registers and memory and control execution under applicable policy. This is extremely useful for debugging and authorized security research.

8.2 Why it is security-sensitive

If an attacker can arbitrarily trace a privileged process, debugging capabilities may become a path to obtaining sensitive state or manipulating execution.

8.3 Policy matters

Linux systems can apply restrictions around process tracing. The Yama security module provides additional policy controls in supported configurations. The Linux documentation also notes that user namespaces interact with ptrace capabilities, demonstrating why isolation mechanisms must be understood as a system rather than individually. citeturn0search24

8.4 Windows debugging

Windows debugging also involves privileged process access rights. The security model treats processes and threads as securable objects, with access mediated by security descriptors and tokens. citeturn0search4

Chapter 09

Windows security architecture

Windows security is built around identities, security contexts, securable objects, access checks and privileged system components.

9.1 SIDs

A Security Identifier (SID) identifies a security principal such as a user, group or computer. It is the identity value used throughout Windows authorization rather than a display name.

9.2 Access tokens

An access token describes the security context of a process or thread. Microsoft documents token contents including the user's SID, group SIDs, privileges, logon information and other authorization state. citeturn0search0

9.3 Access checks

When a thread accesses a securable object, Windows compares the thread's security context with the object's security descriptor and applicable ACL entries. This is how identity becomes an authorization decision. citeturn0search7

9.4 Privileges versus permissions

Permissions govern access to objects. Privileges authorize certain system-level operations. These concepts overlap in security impact but are not interchangeable.

9.5 UAC

User Account Control helps reduce the routine use of full administrative privileges. Microsoft documents that administrator accounts can operate with a standard user token and an elevated administrator token, with consent or credentials required for elevation depending on policy. citeturn0search12

Chapter 10

LSA, LSASS and credential protection

Identity infrastructure is a high-value operating-system security boundary because credentials and authentication state can provide access far beyond one process.

10.1 LSA and LSASS

The Local Security Authority manages local security policy and authentication-related functions. The Local Security Authority Subsystem Service, LSASS, is a protected Windows process involved in authentication and security policy.

Microsoft documents that LSASS can maintain credential-related material for active sessions, including Kerberos tickets and other authentication information, depending on configuration and authentication method. citeturn0search1

10.2 Why credential theft is serious

Credential material can allow an attacker to impersonate users or access network resources. Therefore protecting the authentication subsystem is not simply endpoint hardening; it is identity protection.

10.3 LSA protection and Credential Guard

Modern Windows provides protections such as LSA protection and Credential Guard. Credential Guard uses virtualization-based security to isolate sensitive credential material from the normal operating-system environment. citeturn0search5turn0search6

10.4 Defensive principle

Protect privileged identity material, reduce credential exposure, separate administrative identities and monitor abnormal authentication activity. Endpoint security and identity security are tightly connected.

Chapter 11

Drivers, devices and kernel attack surface

11.1 Why drivers are privileged

Drivers translate operating-system requests into device operations. Because many drivers run with high privilege, a driver vulnerability can have consequences far beyond a normal application bug.

11.2 Device objects and access control

Windows treats devices as securable objects. Microsoft explicitly notes that drivers must safeguard the security of the device objects they expose. citeturn0search4

11.3 Linux device model

Linux exposes hardware through kernel subsystems and device nodes. Permissions and policy determine which processes can interact with those interfaces. A device node that provides access to sensitive hardware therefore belongs in the threat model.

11.4 Vulnerable-driver problem

A legitimately signed driver can still contain vulnerabilities. This is another example of why authenticity and security are different properties: knowing who produced code does not prove that its behavior is safe.

Chapter 12

Namespaces, containers and isolation boundaries

Containers are processes isolated through kernel mechanisms rather than miniature independent computers. This distinction is essential to understanding container security.

12.1 What namespaces isolate

Different namespaces provide different views of resources. A PID namespace changes process visibility; a network namespace provides an isolated network stack; a mount namespace changes filesystem mount visibility; user namespaces can map identities between namespace and host contexts.

12.2 What namespaces do not mean

Namespaces do not automatically isolate every kernel attack surface. Containers share the host kernel, so a kernel vulnerability can affect the host or neighboring workloads.

12.3 Capabilities and seccomp

Container security commonly combines namespaces with reduced capabilities and system-call filtering such as seccomp. The objective is to reduce what a compromised workload can ask the kernel to do.

12.4 Resource isolation

cgroups help limit and account for CPU, memory and other resources. Resource controls are security-relevant because uncontrolled consumption can become denial of service.

Chapter 13

Host telemetry and security observability

An operating system produces a continuous stream of evidence. Good defensive engineering selects signals that answer security questions instead of collecting everything without a purpose.

13.1 Process telemetry

Useful fields can include process ID, parent process ID, executable path, command line, user identity, signer information, start time and hashes. Process creation becomes much more valuable when correlated with parent process, identity and network behavior.

13.2 File and persistence telemetry

Monitor security-sensitive locations, executable changes, service creation, scheduled tasks, startup locations, kernel-module changes and permission modifications according to the platform.

13.3 Identity telemetry

Authentication successes and failures, privilege changes, token/elevation events, remote logons and service-account activity help connect endpoint behavior to identity.

13.4 Network telemetry

Outbound connections, listening sockets, DNS activity and process-to-network relationships can reveal unexpected behavior. Network evidence should be correlated with process identity and timing.

13.5 Signal quality

A detection should have a reason to exist. Excessive low-quality alerts train analysts to ignore warnings. Good telemetry is tied to a hypothesis, has sufficient context and leads to an actionable investigation.

Chapter 14

Kernel and host hardening

14.1 Reduce attack surface

Remove unnecessary services, drivers and packages. Restrict administrative access. Keep the kernel and critical components patched. Disable interfaces that are not required.

14.2 Enforce least privilege

Use ordinary user contexts for ordinary work. Grant capabilities and administrative rights only when required. Separate privileged administration from daily activity.

14.3 Protect credentials

Use strong authentication, hardware-backed protection where appropriate, credential isolation and short-lived credentials where practical. Avoid storing secrets in process arguments, source code or world-readable files.

14.4 Isolation

Use sandboxing, application controls, containers or virtual machines according to the threat model. Isolation is strongest when multiple independent controls support it.

14.5 Recovery

Host security includes restoration. Backups, trusted images, configuration management and tested rebuild procedures reduce the operational impact of compromise.

Chapter 15

Advanced reasoning: when OS mechanisms interact

Real incidents rarely involve one isolated mechanism. They happen when several assumptions interact.

SituationUnderlying interactionSecurity question
Container escapeApplication + namespace + kernel vulnerabilityCan untrusted code cross the kernel boundary?
Privilege escalationLow-privilege process + vulnerable privileged componentCan attacker-controlled state influence privileged execution?
Credential theftProcess access + authentication subsystemWho can inspect or influence credential material?
PersistenceFilesystem + service/task mechanism + identityWhich privileged component will execute attacker-controlled state?
Defense evasionProcess + telemetry + permissionsCan the attacker alter or bypass the evidence used for detection?

The mature analyst follows the authority chain: identify the initial privilege, identify the resource being accessed, identify the kernel mechanism enforcing access, and determine what evidence remains after the event.

Mastery review

20 questions — with answers

Try each question before opening the answer. The explanations are part of the curriculum.

01 · What is the primary security purpose of the user/kernel boundary?
Answer: It separates ordinary application execution from privileged operations and protected system state.

Why: A compromised application should not automatically gain unrestricted access to kernel memory, hardware or other processes.
02 · What is the difference between a process and a thread?
Answer: A process provides an execution environment and resources; a thread is an execution path within that process and has its own execution state.

Why: Threads commonly share process memory and resources, so a security boundary between processes is different from a boundary between threads.
03 · Why is virtual memory a security mechanism?
Answer: It provides isolated address spaces and allows memory-access permissions to be enforced by the OS and hardware.

Why: This helps prevent one process from arbitrarily reading or modifying another process's memory.
04 · What does a system call do?
Answer: It provides a controlled interface through which user-space software requests a kernel service.

Why: The kernel can validate the request and apply authorization before performing a privileged operation.
05 · Why are system-call arguments security-sensitive?
Answer: They originate from less-trusted user-space code and are consumed by privileged kernel code.

Why: Incorrect validation of pointers, lengths or flags can turn an ordinary user process into a path toward privilege escalation.
06 · What is a race condition?
Answer: It occurs when program behavior depends on timing or ordering between concurrent operations.

Why: If security checks and state changes are separated incorrectly, another actor may change the state between them.
07 · What is TOCTOU?
Answer: Time-of-check-to-time-of-use occurs when software checks a resource and later uses it assuming the checked property remains unchanged.

Why: A concurrent change can invalidate the original security decision.
08 · What is the Linux VFS?
Answer: The Virtual File System is an abstraction layer that provides common filesystem interfaces over different filesystem implementations.

Why: It lets applications use consistent file operations while the kernel handles implementation-specific details.
09 · What is the difference between permissions and capabilities on Linux?
Answer: Traditional permissions control access based on user/group/other relationships, while capabilities divide selected privileged operations into narrower authorities.

Why: Capabilities can support least privilege without giving a process the complete authority traditionally associated with root.
10 · What do Linux namespaces provide?
Answer: They provide isolated views of selected kernel resources such as processes, mounts, networking and users.

Why: They are fundamental to containers, but containers still share the host kernel.
11 · What is the role of cgroups?
Answer: cgroups organize processes and control or account for resource consumption such as CPU and memory.

Why: Resource limits help prevent one workload from consuming resources needed by others.
12 · Why is ptrace security-sensitive?
Answer: It can allow one process to inspect or control another process under applicable policy.

Why: Debugging authority over a privileged process can expose sensitive state or alter execution.
13 · What is a Windows SID?
Answer: A Security Identifier uniquely identifies a Windows security principal such as a user, group or computer.

Why: Authorization decisions use security identities such as SIDs rather than relying only on display names.
14 · What is an access token?
Answer: It is a security context attached to a Windows process or thread containing identity and authorization information such as SIDs and privileges.

Why: Windows uses that context when deciding whether an operation against a securable object is permitted.
15 · What is the difference between a DACL and a SACL?
Answer: A DACL defines access-control decisions, while a SACL defines auditing rules for selected access events.

Why: Authorization and evidence collection are different security functions and often need both.
16 · Why is LSASS a high-value security component?
Answer: LSASS participates in Windows authentication and maintains security-related state and credential material for active sessions depending on configuration.

Why: Compromise of authentication infrastructure can affect multiple identities and network resources.
17 · Why doesn't a signed driver automatically mean a safe driver?
Answer: A signature establishes authenticity relative to a trusted signer; it does not prove the driver contains no vulnerabilities.

Why: A legitimate but vulnerable privileged driver can still create a serious kernel attack surface.
18 · Why are containers not identical to virtual machines?
Answer: Containers generally isolate processes using the host kernel, while a virtual machine provides a separate guest operating-system environment behind a hypervisor boundary.

Why: A container workload can still be affected by vulnerabilities in the shared host kernel.
19 · What makes host telemetry useful for detection?
Answer: Telemetry is useful when it captures enough context to test a security hypothesis, such as process identity, parent process, user, command line, file changes and network relationships.

Why: A single isolated event is often ambiguous; correlated evidence produces stronger conclusions.
20 · What is the most important mental model for OS security?
Answer: Think in terms of authority, boundary, state and evidence: who has authority, what boundary is supposed to restrict it, what protected state can change, and what evidence remains when it does.

Why: This model connects kernel internals to real security problems such as privilege escalation, credential theft, persistence, container escape and detection.
Completion standard: You should now be able to explain how an application request becomes a kernel action, how the OS isolates memory and identities, where Linux and Windows enforce authorization, why privileged components are high-value targets, and how host telemetry can expose changes in system state.
