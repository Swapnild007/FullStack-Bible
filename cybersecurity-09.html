01 · Active Directory as an enterprise control plane

Active Directory Domain Services (AD DS) is a directory service and identity infrastructure for Windows environments. It stores objects such as users, groups, computers and services, and provides authentication, authorization-related information, policy-based administration and service discovery.

The security significance

AD is not merely a user database. Domain controllers participate in authentication and maintain directory state that can control access across large portions of an enterprise. A compromise of identity-control infrastructure can therefore have a much larger blast radius than compromise of a single workstation.

User/device → identity → policy → authentication → authorization → enterprise resource

Control-plane thinking

When analysing AD security, separate the identity control plane from ordinary workloads. Domain controllers, privileged identities and systems that can modify identity infrastructure deserve stronger trust boundaries and administrative controls than ordinary endpoints.

Core mental model: protect the systems that can change who is trusted, what they can access and how authentication works. Those systems form the enterprise identity control plane.

02 · Domains, forests, objects and the schema

Domain

A domain is a logical administrative and security boundary within AD DS. It has its own directory partition and domain controllers, and it participates in a forest-wide namespace and trust structure.

Forest

A forest is a collection of one or more domains sharing a common schema and configuration. Forest-level relationships and administrative privileges can have broad consequences because they can influence multiple domains.

Objects and attributes

Users, groups, computers, organizational units, service accounts and many other entities are represented as directory objects with attributes. The schema defines object classes and attribute types. Security depends on controlling which principals can read or modify sensitive objects and attributes.

OUs are administrative containers

Organizational units are commonly used to organize objects and apply delegated administration and Group Policy. An OU is not automatically a security boundary. Effective security depends on permissions, policy inheritance and administrative design.

ConceptSecurity meaning
DomainIdentity and administrative scope with domain controllers and directory data.
ForestShared schema/configuration and broad trust/administrative relationships.
OUOrganization and delegation container; not inherently a hard security boundary.
Object ACLControls who may perform permitted operations on a directory object.

03 · DNS, service discovery and domain controller location

AD relies heavily on DNS. Clients need to locate domain controllers and services, and domain controllers use DNS to publish service-location information.

Why DNS is security-critical

If name resolution is wrong, authentication and directory operations can fail. If name resolution is maliciously influenced, clients can potentially be directed toward unintended services. DNS therefore belongs in the enterprise identity threat model.

Service discovery

AD uses DNS service records to advertise capabilities such as LDAP and Kerberos. A secure architecture needs controlled DNS administration, appropriate update permissions, monitoring and reliable time synchronization.

Time matters

Kerberos authentication is sensitive to clock differences because tickets contain time-related validity information. Enterprise time architecture is therefore part of identity reliability, not just an operations detail.

Security connection: identity infrastructure depends on supporting services. Protecting AD while leaving DNS or time administration broadly privileged can preserve an unintended path to identity failure.

04 · Kerberos authentication

Kerberos is a ticket-based authentication protocol widely used by AD. Instead of repeatedly sending a user's password to every service, the protocol uses a trusted Key Distribution Center (KDC) and cryptographic tickets.

The core ticket flow

Client → Authentication Service → TGT → Ticket Service → service ticket → application service

The Ticket Granting Ticket (TGT) establishes a basis for requesting service tickets. A service ticket identifies the intended service and carries cryptographic proof that the service can validate.

Why SPNs matter

Service Principal Names associate services with security principals. Correct SPN registration is necessary for Kerberos service authentication. Misconfiguration can cause fallback behavior or unexpected identity mappings.

Security properties

  • Tickets have defined lifetimes and are not simply permanent passwords.
  • Mutual authentication can be supported when the protocol and service use it correctly.
  • Compromise of privileged credentials or ticket-signing material can have broad consequences.
  • Authentication success does not itself prove that the caller is authorized for every resource.

05 · Kerberos abuse and credential exposure

Defenders need to understand common Kerberos abuse patterns because they reveal where identity architecture becomes fragile. This section is conceptual and intended for authorized security analysis.

Ticket theft and replay

If an attacker obtains usable authentication material from a compromised system, they may attempt to reuse it without knowing the original password. Pass-the-ticket is the general concept of using stolen Kerberos ticket material to impersonate an already-authenticated security context.

Credential material exposure

Credential theft can target memory, cached secrets, service credentials, administrative sessions or poorly protected backup material. The strongest defence is not one detection rule; it is reducing where privileged credentials are allowed to appear.

Service-account risk

Long-lived service identities can become attractive targets when their privileges are broad or their credentials are weakly governed. Prefer managed identities or managed service-account designs where appropriate, narrow privileges, rotate secrets and monitor use.

Defensive boundary: study these techniques to recognize and contain identity compromise. Testing against real enterprise accounts or systems requires explicit authorization and controlled scope.

06 · LDAP, directory queries and access control

LDAP is a protocol used to access and manipulate directory information. AD exposes LDAP interfaces that allow clients and applications to query users, groups, computers and other directory objects.

Read access is still sensitive

Many directory attributes are intentionally readable to authenticated users, but directory enumeration can reveal organizational structure, group membership, naming conventions, service identities and security-relevant relationships. The question is not simply “can users read it?” but “what can an attacker infer by combining the readable data?”

LDAP security

Use secure transport and appropriate signing/binding protections according to the Windows environment and application requirements. Avoid treating encrypted transport as a replacement for authorization.

Directory permissions

Directory objects have security descriptors and access control entries. Delegated administration should grant only the rights required for a defined task. Broad write permissions on identity objects can create indirect privilege paths.

07 · Group Policy and configuration control

Group Policy provides centralized configuration and policy management for Windows environments. It can influence security settings, software configuration, scripts, firewall behavior, auditing and many other host controls.

Why GPO is privileged

A policy that applies to many computers can change security posture at scale. A malicious or careless policy change can therefore become an enterprise-wide configuration event.

Security design

  • Separate policy authorship from unnecessary administrative privilege.
  • Control who can create, link and modify GPOs.
  • Review inheritance, enforced links and scope filtering.
  • Monitor sensitive policy changes.
  • Back up and test policy configuration before major changes.

GPO is not just configuration

From a security perspective, GPO is a distributed execution and enforcement mechanism. Treat its permissions and change paths with the same care applied to privileged application deployment systems.

08 · ACLs, delegation and unintended privilege paths

Active Directory security descriptors determine which principals can perform which operations on objects. Enterprise security becomes difficult when rights are delegated through multiple groups, inheritance relationships and nested memberships.

Effective access

A user may receive permissions through direct assignment, nested groups, inherited permissions or delegated rights. Security review must therefore reason about the effective permission graph rather than inspecting one membership at a time.

Principal → group nesting → delegated right → object → sensitive operation → privilege consequence

Dangerous design pattern

A low-privilege administrator does not need direct membership in a highly privileged group to become security-critical. If that administrator can modify an object, group, policy or service that controls a privileged identity, the indirect path can be equally important.

Least privilege

Delegate narrowly scoped rights for defined administrative jobs. Periodically review stale delegations, nested groups, orphaned accounts and permissions that no longer correspond to business responsibilities.

09 · Kerberos delegation

Kerberos delegation allows one service to act on behalf of a user when accessing another service. Delegation can be necessary for legitimate multi-tier applications, but it creates a powerful trust relationship between services.

Unconstrained delegation

Broad delegation models can expose authentication material to systems that do not need such a wide trust relationship. Modern designs should avoid unnecessary privilege and use constrained alternatives where supported.

Constrained delegation

Constrained delegation restricts which services a principal may access on behalf of users. Resource-based constrained delegation moves more of the authorization decision toward the resource service.

Security review questions

  • Which service can impersonate users?
  • Which users can reach that service?
  • Which target services can be accessed?
  • Who can modify the delegation configuration?
  • What happens if the delegating host is compromised?

10 · Privileged access, Tier 0 and administrative workstations

Modern Microsoft guidance treats identity infrastructure as a privileged control plane. The AD DS tier model separates administrative scope into trust tiers so lower-trust endpoints do not become credential exposure points for higher-trust identities.

TierTypical scopeSecurity objective
Tier 0Identity control plane: domain controllers and systems/identities that can control it.Prevent compromise of enterprise identity authority.
Tier 1Enterprise servers and applications.Contain workload/server administration.
Tier 2End-user devices and support identities.Contain endpoint and user administration.

Privileged Access Workstations

A PAW is a hardened administrative workstation dedicated to privileged administration. The principle is simple: do not type a high-tier credential into a lower-trust workstation. Otherwise the credential is exposed to the lower-trust environment.

Enterprise Access Model evolution

Microsoft's newer Enterprise Access Model extends the older AD tier model to modern environments spanning on-premises systems, multiple clouds, users and applications. The central principle remains containment of privileged access and protection of the identity control plane.

11 · Active Directory Certificate Services and PKI risk

AD CS provides certificate services that can support authentication, encryption, signing and other enterprise functions. Because certificates can represent identities, certificate configuration can become an identity-security boundary.

Why certificate templates matter

Certificate templates define enrollment and certificate properties. A template that allows an unintended principal to obtain a certificate usable for authentication can create an indirect identity escalation path.

Security review

  • Inventory certificate authorities and templates.
  • Identify who can enroll, modify templates and manage CA configuration.
  • Separate certificate issuance authority from unnecessary administrative roles.
  • Review certificate purpose, subject/SAN handling and authentication mappings.
  • Monitor anomalous enrollment and privileged certificate use.
Key idea: if a certificate can authenticate as a powerful identity, the system that issues or controls that certificate is part of the identity control plane.

12 · NTLM, legacy authentication and protocol transition

NTLM is an older Windows authentication family that remains present for compatibility in some environments. Security architecture should distinguish legacy protocol requirements from modern authentication paths and reduce unnecessary dependence on weaker mechanisms.

Pass-the-hash

Pass-the-hash describes using an obtained NTLM credential representation to authenticate without first recovering the plaintext password. The defensive implication is important: protecting only passwords is insufficient if reusable credential material can be extracted from privileged systems.

Reduction strategy

Inventory applications that require legacy authentication, remove unnecessary NTLM dependencies, prefer Kerberos where appropriate, protect privileged credentials and monitor unexpected authentication paths.

Do not confuse compatibility with trust

A protocol being supported by a Windows environment does not mean it should be accepted everywhere. Authentication policy should reflect application requirements and the sensitivity of the target resource.

13 · Domain controller hardening and identity-plane defense

Domain controllers should be treated as high-value infrastructure. Microsoft guidance emphasizes reducing privileged accounts, securing administrative hosts, protecting domain controllers, patching, controlling application execution and monitoring critical assets.

Core controls

  • Minimize permanent privileged membership.
  • Use separate administrative identities for privileged work.
  • Use hardened administrative hosts appropriate to the privilege tier.
  • Restrict interactive and remote access to domain controllers.
  • Apply supported security baselines and timely security updates.
  • Control software and services running on domain controllers.
  • Protect backups and test identity recovery.
  • Audit privileged changes and authentication events.

Defense in depth

Identity security should not depend on a single control. Endpoint security, network segmentation, credential protections, policy controls, directory permissions, logging and recovery capabilities should reinforce one another.

14 · Enterprise detection and identity telemetry

AD security requires visibility into authentication, privilege changes, directory modifications, policy changes and unusual relationships between identities and systems.

High-value telemetry

  • Authentication successes and failures, including unusual source/destination patterns.
  • Privileged group membership changes.
  • New or modified accounts and service identities.
  • Directory object and ACL changes.
  • Group Policy changes.
  • Certificate enrollment and CA/template changes.
  • Suspicious use of administrative protocols or remote management.
  • Changes to domain controller security configuration.

Detection engineering

Good detections combine identity, host, network and directory context. A single failed login is weak evidence; a privileged account authenticating from an unusual workstation followed by group membership changes is a much richer investigation signal.

ATT&CK mapping

MITRE ATT&CK documents enterprise techniques relevant to credential access, discovery, lateral movement, privilege escalation and persistence. Mapping detections to behavior helps identify coverage gaps without reducing security monitoring to a list of tool signatures.

15 · Domain compromise, containment and recovery

A suspected domain compromise is an identity incident, not simply a malware cleanup exercise. Recovery must answer whether privileged credentials, domain controllers, certificate infrastructure, policy controls or trust relationships were affected.

Containment reasoning

Containment should reduce attacker access while preserving enough evidence and operational capability to understand the incident. Actions must be coordinated because disabling identities or systems without understanding dependencies can interrupt critical business functions.

Recovery principles

  • Establish a trusted administrative path.
  • Identify affected privileged identities and credentials.
  • Assess domain controller integrity and supporting infrastructure.
  • Review persistence through accounts, groups, policy, delegation and certificates.
  • Restore from known-good sources where required.
  • Reset or rotate credentials according to a documented recovery plan.
  • Validate security controls after restoration.
Recovery is a trust decision: restoring a server is not sufficient if the identity relationships that authenticate administrators to that server remain compromised.

16 · Hybrid identity and enterprise architecture

Modern enterprises may combine on-premises AD DS with Microsoft Entra ID and managed services. Hybrid identity creates additional synchronization, federation, provisioning and privileged-access paths.

Control-plane expansion

Microsoft's current Enterprise Access Model broadens the security view beyond classic domain boundaries. Identity systems, synchronization services, cloud management planes and administrative workstations can all influence access decisions.

Entra Domain Services is different from AD DS

Microsoft Entra Domain Services provides managed domain capabilities such as domain join, Group Policy, LDAP and Kerberos/NTLM for workloads that need legacy domain protocols. It is a managed service rather than a customer-operated domain-controller deployment.

Hybrid security questions

  • Which system is authoritative for each identity attribute?
  • Which synchronization service can change cloud or on-premises identity state?
  • Which administrators can control synchronization?
  • Where are privileged credentials allowed to appear?
  • Can compromise of one plane influence the other?

17 · Directory replication, SYSVOL and identity consistency

AD DS is a distributed directory: domain controllers maintain replicas and synchronize directory changes. This supports availability, but it also means security investigations must understand replication state and convergence.

Directory data and SYSVOL

Group Policy depends on both directory objects and files in SYSVOL. Modern Windows Server deployments use DFS Replication for SYSVOL. These two stores are related to Group Policy but are not the same replication mechanism.

Security significance

  • Replication health affects whether security changes converge across controllers.
  • Unexpected replication behavior can complicate incident timelines and recovery.
  • Backups and restoration procedures must account for domain-controller state and replication.
  • Identity recovery should establish which controllers and supporting systems are trusted before normal administration resumes.
Key idea: AD security is distributed security. A correct decision on one controller is not enough if the identity state cannot be trusted across the domain.

18 · Enterprise Access Model and modern identity architecture

Microsoft's current Enterprise Access Model extends the older AD tier model to modern enterprises spanning on-premises systems, multiple clouds, user access and application access. The older Tier 0/1/2 model remains useful for AD-specific administration, but it is now a component of a broader control-plane architecture.

PlaneSecurity question
Control planeWho or what can change enterprise access decisions?
Management planeWho can administer infrastructure and platforms?
Data/workload planeWho can control business systems and data?
User/app accessWho or what can request access to resources?

Intermediaries matter

Privileged access workstations, jump hosts, automation, synchronization services and management tools can become part of the control plane when they broker or enforce privileged access. Protecting the final target while leaving a privileged intermediary weak does not preserve the trust boundary.

Architecture review

  • Identify every system that can influence privileged identity state.
  • Separate administrative identities by trust level and purpose.
  • Keep lower-trust devices from becoming credential entry points for higher-trust planes.
  • Review synchronization and federation as explicit privilege boundaries.
  • Continuously remove obsolete administrative paths.

Mastery review · 20 questions with answers

01 · What is Active Directory?
Answer: AD DS is a directory and identity infrastructure that stores network objects and supports authentication, policy-based administration and access-control-related operations.

Why: Its security importance comes from its role in controlling identities and access across many enterprise systems.
02 · What is the difference between a domain and a forest?
Answer: A domain is an AD administrative and identity scope; a forest is the larger collection of domains sharing schema and configuration.

Why: Forest-level relationships and privileges can affect multiple domains.
03 · Is an OU a hard security boundary?
Answer: No. An OU is primarily an organizational, delegation and Group Policy container.

Why: Effective security depends on ACLs, delegation, inheritance and administrative design.
04 · Why is DNS important to AD security?
Answer: AD uses DNS for service discovery and locating domain controllers.

Why: Incorrect or maliciously influenced name resolution can disrupt or redirect identity-dependent operations.
05 · What does Kerberos provide?
Answer: Kerberos provides ticket-based network authentication using a trusted KDC and cryptographic credentials.

Why: It reduces the need to repeatedly send passwords to services and supports strong service authentication patterns.
06 · What is a TGT?
Answer: A Ticket Granting Ticket is a Kerberos credential used as the basis for obtaining service tickets.

Why: Possession of sensitive ticket material can represent significant authentication risk.
07 · What is an SPN?
Answer: A Service Principal Name associates a service instance with a security principal for Kerberos service authentication.

Why: Correct SPN registration is important for reliable and secure Kerberos service identity.
08 · What is pass-the-ticket?
Answer: It is the concept of using stolen Kerberos ticket material to reuse an existing authenticated security context.

Why: It shows why credential protection must include session and ticket material, not only passwords.
09 · Why can LDAP exposure matter even when data is readable by design?
Answer: Directory data can reveal identities, groups, systems, services and relationships that enable reconnaissance.

Why: Security risk depends on what an attacker can infer from combined information, not only on whether each attribute is secret.
10 · Why is Group Policy security-critical?
Answer: GPO can change configuration and security behavior across many systems.

Why: A privileged policy change can have enterprise-wide impact, so GPO permissions and changes need strong control and monitoring.
11 · What makes delegated permissions dangerous?
Answer: A delegated right can create an indirect path to a sensitive object or privileged operation without direct membership in a privileged group.

Why: AD security must be analysed as an effective permission graph.
12 · What is Kerberos delegation?
Answer: It allows a service to act on behalf of a user when accessing another service.

Why: Delegation creates an impersonation trust, so it should be constrained to the minimum required services and principals.
13 · What is Tier 0?
Answer: Tier 0 represents the identity control plane and assets or identities that can control enterprise identity authority.

Why: Compromise of Tier 0 can undermine trust across lower tiers.
14 · Why should privileged credentials not be used on ordinary workstations?
Answer: A compromised lower-trust workstation can expose the higher-tier credentials typed or used there.

Why: Administrative workstation security is part of the privileged identity boundary.
15 · Why is AD CS part of identity security?
Answer: Certificates can represent identities and may be used for authentication.

Why: A certificate authority or template that can issue an authentication-capable certificate to an unintended principal can create a privilege path.
16 · What is pass-the-hash?
Answer: It is the reuse of obtained NTLM credential material to authenticate without first recovering the plaintext password.

Why: It demonstrates why reusable credential material on privileged systems must be strongly protected.
17 · Which changes deserve high-priority AD monitoring?
Answer: Privileged group membership, sensitive directory permissions, accounts, Group Policy, certificate infrastructure, domain-controller security configuration and unusual privileged authentication are high-value areas.

Why: These events can alter enterprise trust or indicate identity compromise.
18 · What makes domain recovery different from ordinary server recovery?
Answer: You must re-establish trusted identity and administrative control, not merely restore operating-system state.

Why: A compromised identity plane can make restored systems unsafe even when their files appear intact.
19 · What is the security challenge of hybrid identity?
Answer: Hybrid identity introduces synchronization, federation and cloud-management paths that can connect multiple control planes.

Why: Each path must be treated as a potential privilege boundary and monitored accordingly.
20 · What is the core enterprise AD security model?
Answer: Protect the identity control plane, minimize privileged access, isolate administrative trust tiers, constrain delegation, harden supporting infrastructure, monitor identity changes and maintain a tested recovery path.

Why: Enterprise AD security is an architecture problem: reducing the blast radius of a compromised endpoint or identity is more durable than relying on one detection rule.
Completion standard: You should be able to explain AD domains and forests, DNS dependency, Kerberos tickets, LDAP, GPO, ACL/delegation paths, privileged tiers, PAWs, AD CS, legacy authentication, identity telemetry and domain recovery. You should also be able to explain why a compromise of the identity control plane can propagate across otherwise healthy workloads.
