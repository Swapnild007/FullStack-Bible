Web Application & API Security.

Secure web applications by understanding trust boundaries, browser behavior, identity, authorization, input handling, data access, server-side requests, API contracts, secrets, third-party dependencies and failure modes. This chapter connects application architecture to the current OWASP web and API security guidance.

01 · Application security as trust-boundary engineering

A web application is a chain of components: browser, frontend code, edge/CDN, web server, application services, identity provider, database, object storage, queues and third-party APIs. Every boundary can change what the application knows, trusts or permits.

Untrusted input → validation → business logic → authorization → data operation → response

Security is not a frontend feature

Client-side validation improves usability but cannot enforce security because the client is controlled by the user. Security decisions involving identity, permissions, tenant ownership, pricing, workflow state or sensitive data must be enforced on trusted server-side components.

Threat modelling

Identify assets, actors, trust boundaries, entry points, privileged operations and abuse cases. Ask what happens if a request is modified, replayed, duplicated, delayed, reordered or sent without the expected UI.

Core rule: every value crossing a trust boundary should have an explicit interpretation. Do not let “it came from our frontend” become an authorization decision.

02 · Browser security model

Same-origin policy

The browser's same-origin policy limits how documents and scripts from one origin interact with resources from another. An origin is based on scheme, host and port. CORS can selectively relax certain cross-origin browser restrictions, but it does not make an API intrinsically trusted.

Cookies

Cookies can carry session identifiers. Security attributes include Secure, HttpOnly and SameSite, plus appropriate domain and path scope. Cookie configuration should reflect the application's actual cross-site requirements.

Web storage

LocalStorage and sessionStorage are accessible to JavaScript running in the origin. Consequently, placing high-value bearer credentials there can increase exposure when an XSS flaw exists. Credential storage strategy should be selected from the application's threat model rather than convenience.

Browser isolation is layered

CSP, framing controls, origin isolation, cookie policy, HTTPS, permissions policy and careful DOM APIs provide complementary controls. None removes the need for server-side authorization.

03 · Broken access control and object authorization

Access control determines whether an authenticated or otherwise identified principal may perform a specific action on a specific resource. The most dangerous failures often occur when an application verifies identity but not resource ownership or permitted action.

Object-level authorization

If an API accepts an object identifier, the server must determine whether the caller may access that particular object. Changing an ID in a request should not be enough to cross a tenant or user boundary.

Function-level authorization

Administrative actions require explicit authorization. Hiding an admin button in the UI is not authorization. Every privileged route must enforce the required policy server-side.

Property-level authorization

An object can contain fields with different sensitivity. A user may be allowed to update a display name but not a billing status, owner identifier, role or internal risk field. Avoid binding arbitrary request objects directly to persistence models.

DecisionQuestion
AuthenticationWho is the principal?
Object authorizationMay this principal act on this resource?
Function authorizationMay this principal invoke this operation?
Property authorizationMay this principal change or see this field?

04 · Input validation and injection

Input validation is about defining what the application accepts and how that value is interpreted. Injection occurs when untrusted data changes the structure or meaning of a command, query, template, expression or markup.

SQL injection

SQL should be constructed through parameterized queries or safe query APIs. A string that contains SQL syntax must remain data rather than becoming executable query structure.

Command injection

Passing user-controlled strings to operating-system command interpreters creates a high-risk boundary. Prefer direct library APIs with structured arguments instead of shell interpretation. If a command is genuinely required, use strict allowlists and separate data from command structure.

HTML and DOM injection

HTML is an interpreter context. Context-aware output encoding, safe DOM APIs and a restrictive Content Security Policy can reduce XSS risk. Sanitization is context-dependent; a sanitizer suitable for HTML fragments is not automatically safe for JavaScript, CSS or URL contexts.

Template, expression and parser injection

Template engines, expression languages, YAML/XML parsers and serialization formats can create their own interpretation boundaries. Understand the parser and avoid evaluating attacker-controlled expressions.

Defense pattern: parameterize structured operations, validate business constraints, encode at the output context and minimize interpreters.

05 · Authentication security

Password authentication

Passwords should be stored using dedicated password-hashing algorithms designed for password storage, with unique salts and parameters appropriate to current guidance. Plaintext passwords and fast general-purpose hashes are not acceptable password storage designs.

MFA and phishing resistance

Multi-factor authentication reduces dependence on passwords. Phishing-resistant methods such as passkeys/WebAuthn provide stronger protection because authentication is cryptographically bound to the legitimate relying-party origin.

Account recovery

Password reset, email changes, backup codes and help-desk recovery are authentication paths. They need strong identity proof, rate controls, auditing and careful notification.

Authentication versus authorization

Even a perfectly authenticated user can be unauthorized to access another user's data or invoke an administrative operation.

06 · Session management and credential lifecycle

After authentication, the application needs a mechanism to associate subsequent requests with the authenticated principal. A session identifier is a credential and must be protected accordingly.

Session fixation

Applications should establish a fresh session identifier after authentication or privilege elevation so an attacker cannot force a victim to use a known session identifier.

Cookie controls

  • Secure: restricts cookie transmission to HTTPS.
  • HttpOnly: prevents normal JavaScript access to the cookie.
  • SameSite: controls cross-site cookie sending according to the selected policy.
  • Scope: keep Domain and Path as narrow as practical.

Token lifecycle

Bearer tokens should have an explicit issuer, audience, scope and expiration. OAuth security guidance now recommends stronger protections against authorization-code attacks and token replay, including PKCE and sender-constrained mechanisms where appropriate.

Logout and revocation

Define what logout means, how sessions are invalidated, what happens after password or privilege changes, and how compromised credentials are revoked.

07 · CSRF, CORS and cross-origin behavior

CSRF

Cross-site request forgery abuses a browser's ability to attach ambient credentials to a request. It matters particularly for cookie-authenticated state-changing operations.

Defenses

SameSite cookies can reduce exposure, while synchronizer tokens or equivalent request-binding mechanisms can provide explicit proof that the request originated from the intended application flow. Sensitive operations can also require reauthentication or other user presence signals.

CORS is not an authentication control

CORS controls whether browser JavaScript may read certain cross-origin responses. A server may still receive a request even when a browser blocks JavaScript from reading the response. CORS should therefore be configured according to explicit trusted origins and methods, not used as a substitute for authorization.

08 · API security architecture

APIs expose application capabilities directly. The current OWASP API Security Top 10 (2023) highlights risks including broken object-level authorization, broken authentication, broken object-property authorization, unrestricted resource consumption, broken function-level authorization, sensitive business-flow abuse, SSRF, misconfiguration, poor API inventory and unsafe consumption of third-party APIs.

API request model

Identity → endpoint policy → object policy → property policy → business rule → data access → response policy

Schema validation

Define request and response schemas. Reject malformed or semantically invalid values before they reach sensitive business logic. Validate types, ranges, enumerations, lengths and relationships.

Response minimization

Return only fields required by the caller. A database row should not automatically become an API response object. Sensitive internal fields, credentials, authorization metadata and tenant identifiers should be deliberately controlled.

Resource consumption

Rate limits are only one control. Also constrain pagination, upload sizes, query complexity, batch sizes, expensive searches, concurrency and downstream fan-out. Resource limits protect both security and availability.

09 · Business-logic and workflow security

Not every vulnerability is a malformed input. Applications can be technically correct at the request level while violating business rules.

State-machine thinking

Draft → Submitted → Approved → Fulfilled → Closed

If an endpoint accepts a state transition without checking the current state, actor permissions and required conditions, a caller may skip intended controls. Model sensitive workflows explicitly.

Replay and duplication

Payments, invitations, password resets, job submissions and other operations may be retried. Use idempotency keys or server-side state where repeated requests must not produce repeated effects.

Race conditions

Authorization and business invariants can fail when two requests execute concurrently. Use appropriate transactional boundaries, uniqueness constraints, locking or other concurrency controls.

10 · Server-Side Request Forgery

SSRF occurs when a server retrieves a remote resource based on attacker-controlled input and the attacker can influence the destination beyond the intended policy.

Why SSRF matters

The server may have network access that the user does not: internal services, administrative endpoints, metadata services or private APIs. SSRF therefore crosses a network trust boundary using the application's own privileges.

Defense architecture

  • Prefer fixed destinations when the feature does not require arbitrary URLs.
  • Use strict destination allowlists for approved integrations.
  • Validate URL schemes, hosts, ports and redirect behavior.
  • Resolve and connect under a network policy that denies unintended private destinations.
  • Do not assume DNS validation performed once remains valid for the subsequent connection.
  • Limit response size, timeout and redirect depth.
  • Log outbound requests with sufficient context.
Important: SSRF defenses are layered. A string-based “is this a private IP?” check alone is not a complete network security boundary.

11 · Data access, databases and multi-tenant isolation

Authorization must reach the data boundary

Checking authorization in one controller is fragile when other code paths can access the same data. Data-access functions should preserve tenant and ownership constraints, and database-level controls such as row-level security can provide an additional boundary where appropriate.

Mass assignment

Never allow arbitrary client fields to update a persistence model. Define explicit writable fields and map them deliberately.

Tenant isolation

Every query involving tenant-scoped data should establish tenant context from trusted identity rather than from a freely supplied request parameter. Test for cross-tenant access as a first-class security property.

Secrets and sensitive data

Minimize storage of secrets and sensitive information. Encrypt data in transit and at rest according to the threat model, restrict database privileges and prevent sensitive values from appearing in logs or error messages.

12 · Error handling, logging and observability

Error behavior is part of the security boundary. Detailed internal exceptions can expose filesystem paths, database structure, stack traces, tokens or implementation details.

Safe error responses

Return stable, useful error codes to clients while keeping sensitive diagnostic detail in protected server-side telemetry. Do not leak credentials, connection strings or raw exception objects.

Security logging

Log authentication events, authorization failures, administrative actions, security-sensitive configuration changes, suspicious workflow transitions and relevant API abuse signals. Preserve principal, action, resource, outcome and time context.

Logging failures

OWASP Top 10:2025 includes Security Logging & Alerting Failures as A09. Logs that exist but cannot support detection or investigation are a security weakness.

13 · Browser-facing hardening

Content Security Policy

CSP can constrain script, style, image, frame and other resource sources. A well-designed policy reduces the impact of injection but requires understanding of application dependencies.

Security headers

Headers such as HSTS, frame-ancestors through CSP, Referrer-Policy and appropriate content-type protections can reduce browser attack surface. Exact configuration should match application behavior rather than copying a generic list.

HTTPS and transport

HTTPS provides authenticated, encrypted transport when certificate validation succeeds. It protects credentials and data in transit but does not make a vulnerable application secure once traffic reaches the server.

Clickjacking

Framing controls prevent an attacker-controlled page from embedding sensitive application interfaces in ways that can trick users into unintended interaction.

14 · Dependencies, software supply chain and integrity

Applications depend on packages, build tools, container images, CI systems, registries and deployment infrastructure. A compromise in any trusted build dependency can become application code.

Dependency security

  • Maintain an inventory of direct and transitive dependencies.
  • Pin or constrain versions according to the project's update strategy.
  • Review security advisories and transitive exposure.
  • Remove unused packages and capabilities.
  • Protect package and deployment credentials.
  • Generate and maintain an SBOM where appropriate.

Build integrity

Protect source repositories, CI credentials, signing keys and artifact registries. Separate build authority from deployment authority where practical and retain provenance for production artifacts.

OWASP 2025

OWASP Top 10:2025 lists Software Supply Chain Failures as A03, reflecting the broader security boundary created by modern dependency and build ecosystems.

15 · Third-party APIs and external integrations

External API responses are data from another trust domain. Do not assume they are safe simply because the integration is documented or authenticated.

Validate external data

Apply schema validation, size limits, timeouts and business-rule checks to third-party responses. Treat URLs, HTML, file names and identifiers received from partners as untrusted data.

Least privilege

Give integrations only the scopes and network access they need. Separate credentials per integration and rotate or revoke them through a defined lifecycle.

Failure containment

Use timeouts, bounded retries, circuit breakers and safe fallbacks. An external service failure should not automatically cause credential leakage, unbounded resource consumption or inconsistent business state.

16 · Secure development and security testing

Security requirements

Translate threats into testable requirements: “A user cannot read another tenant's invoice” is testable. “The API is secure” is not.

Testing layers

  • Unit tests: authorization predicates and validation rules.
  • Integration tests: database, identity and service boundaries.
  • End-to-end tests: realistic user and permission flows.
  • Static analysis: source and dependency analysis.
  • Dynamic testing: behavior of a running application.
  • Threat-driven testing: abuse cases and trust-boundary failures.

Security regression

Every important security bug should produce a regression test that fails if the boundary is broken again. This turns incident knowledge into durable engineering control.

17 · Secure application architecture

A mature application treats security as a set of explicit boundaries rather than a final scanning step.

Browser → Edge → App/API → Identity → Authorization → Data → External services ↓ ↓ ↓ ↓ browser transport policy audit/telemetry

Security properties to preserve

  • Every sensitive operation has an explicit authorization decision.
  • Every trust boundary validates and interprets incoming data.
  • Every credential has a lifecycle and narrow scope.
  • Every external dependency has bounded failure behavior.
  • Every critical security decision is observable enough to investigate.
  • Every important security invariant is tested.
Architecture rule: secure design is not “add more filters.” It is choosing boundaries so a single compromised input, session, service or dependency cannot automatically cross the next security boundary.

18 · Mastery review — 20 questions with answers

01 · Why can client-side validation not enforce security?
Answer: The client is controlled by the user and can be modified or bypassed.

Why: Security decisions must be enforced on trusted server-side boundaries.
02 · What is object-level authorization?
Answer: It checks whether the current principal may access or modify the specific resource identified by the request.

Why: Authentication alone does not authorize every object a user can name.
03 · What is property-level authorization?
Answer: It controls which fields of an object a principal may read or modify.

Why: A user may be allowed to edit a profile name but not its owner, role or billing state.
04 · What is injection?
Answer: Injection occurs when untrusted data changes the structure or meaning of an interpreter's command, query, markup or expression.

Why: Parameterization and context-aware encoding keep data separate from executable structure.
05 · Why is SQL parameterization important?
Answer: It keeps user-supplied values separate from SQL syntax.

Why: The database receives data as parameters rather than treating the value as query structure.
06 · What is phishing-resistant authentication?
Answer: Authentication where the credential is cryptographically bound to the legitimate relying-party context, such as WebAuthn/passkeys.

Why: A copied password or one-time code can be relayed; origin-bound public-key authentication provides stronger resistance.
07 · What is the purpose of HttpOnly?
Answer: It prevents ordinary JavaScript from reading a cookie.

Why: This can reduce direct theft of session cookies through some client-side injection scenarios, although it does not prevent all XSS effects.
08 · What is CSRF?
Answer: CSRF causes a victim's browser to send an authenticated request to a site without the user's intended action.

Why: Ambient credentials such as cookies can be attached automatically.
09 · Why is CORS not an authorization mechanism?
Answer: CORS primarily controls browser JavaScript access to cross-origin responses; it does not decide whether the server should authorize the request.

Why: Server-side authentication and authorization remain necessary.
10 · What is BOLA?
Answer: Broken Object Level Authorization occurs when an API exposes object identifiers but fails to verify whether the caller may access the referenced object.

Why: Changing an identifier can otherwise cross ownership or tenant boundaries.
11 · What is SSRF?
Answer: SSRF occurs when an application can be induced to make a server-side request to an unintended destination.

Why: The server may have network privileges unavailable to the user.
12 · Why is URL allowlisting alone not always enough for SSRF?
Answer: DNS resolution, redirects, alternate address representations and changes between validation and connection can undermine simplistic checks.

Why: SSRF defense requires application and network-layer controls.
13 · Why should APIs minimize response fields?
Answer: Returning only required fields reduces accidental exposure of sensitive or internal data.

Why: A database model should not automatically define the public API contract.
14 · What is a business-logic vulnerability?
Answer: It is a flaw where technically valid operations violate an intended business rule or workflow.

Why: Input validation cannot detect every invalid state transition or economic abuse.
15 · Why are idempotency controls important?
Answer: They prevent retries or duplicate submissions from unintentionally creating repeated side effects.

Why: Networks and clients can legitimately retry requests.
16 · What does CSP provide?
Answer: Content Security Policy restricts which types and sources of browser resources may execute or load.

Why: A strong policy can reduce the impact of certain injection and framing attacks.
17 · Why are third-party APIs untrusted input?
Answer: They belong to another trust domain and their responses can be malformed, compromised, unexpectedly large or semantically unsafe.

Why: Authentication of a partner does not make every returned value safe.
18 · What is a security regression test?
Answer: A test that encodes a previously identified security requirement or failure so the defect cannot silently return.

Why: It converts security knowledge into repeatable engineering control.
19 · What is the current OWASP Top 10 version?
Answer: OWASP Top 10:2025 is the current released web-application Top 10. It includes categories such as Broken Access Control, Security Misconfiguration, Software Supply Chain Failures, Cryptographic Failures, Injection and Authentication Failures.

Why: Security guidance should use the current released version while recognizing that the Top 10 is an awareness document, not a complete application-security standard.
20 · What is the core web/API security mental model?
Answer: Identify the principal, resource, action and trust boundary; validate the input; enforce authorization at the resource boundary; constrain credentials and dependencies; limit resources; observe important decisions; and test the security invariant.

Why: Secure applications are designed around explicit trust boundaries rather than assumptions about clients or networks.
Completion standard: You should be able to trace a request from browser to database, identify each trust boundary, explain object/function/property authorization, reason about injection and SSRF, distinguish authentication from authorization, secure API contracts, and design security regression tests.
