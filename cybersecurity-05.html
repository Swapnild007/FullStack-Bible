01 · The identity security model

Principal, subject, resource and action

An identity system makes decisions about a principal acting on a resource through an action under a policy and context. A principal may be a human, service, device, workload or application. The resource may be a file, API object, database row, cloud account or administrative operation.

Decision = Policy(subject, action, resource, context) → allow / deny / require-more-proof

This model is more useful than thinking of IAM as “login.” Login is only one point in a much larger lifecycle. The system must establish identity, issue credentials, evaluate access, record important actions, revoke access and recover from compromise.

Authentication, authorization and accounting

Authentication establishes or verifies identity. Authorization decides what that identity may do. Accounting/auditing records security-relevant actions. Conflating these functions causes design errors such as trusting a client-supplied role as if it were an authorization decision.

Human and non-human identity

Humans use passwords, passkeys, hardware authenticators and federated identity. Workloads use certificates, workload identity tokens, managed identities or other machine credentials. Treating service accounts like ordinary employees often creates excessive lifetime, shared secrets and weak ownership.

02 · Authentication and authenticator assurance

Authentication factors

Authentication factors are commonly grouped as knowledge, possession and inherence. A password is knowledge; a cryptographic hardware authenticator is possession; a biometric can provide inherence. Two-factor authentication requires two distinct factor types rather than two passwords.

Phishing resistance

Phishing-resistant authentication binds the authentication ceremony to the legitimate relying party so a copied password or captured one-time code is not sufficient. WebAuthn/passkeys use public-key credentials and origin binding to provide strong phishing resistance.

Password authentication

Password authentication remains common. The verifier should store a password-derived verifier using an appropriate password KDF, enforce sensible password policies, protect recovery flows and detect compromised/common passwords where policy permits. Password reset is itself an authentication boundary and must not be weaker than normal login.

MFA fatigue and recovery

More prompts do not automatically mean stronger security. Push-based MFA can be abused through repeated approval requests. Recovery channels, backup authenticators and help-desk identity proofing must be treated as part of the authentication system because an attacker can target the weakest recovery path.

Security question: if an attacker controls the user's email, phone number, browser session or recovery channel, which other authenticators can still establish identity?

03 · Authorization: from roles to resource policy

RBAC

Role-Based Access Control maps permissions to roles and assigns subjects to those roles. It is understandable and operationally useful, but role explosion can occur when every resource or contextual condition becomes a new role.

ABAC

Attribute-Based Access Control evaluates attributes of the subject, resource, action and environment. Example attributes include department, device posture, data classification, transaction amount and time. ABAC can express richer policy but requires trustworthy attribute sources and careful policy governance.

ReBAC

Relationship-Based Access Control evaluates relationships such as “user is a member of team,” “document belongs to project,” or “manager supervises employee.” It is useful for collaborative applications where access follows an object graph rather than a fixed organizational role.

Object-level authorization

API authorization must be evaluated for the specific resource being requested. Knowing that a user can read “documents” does not imply that they can read every document. BOLA/IDOR vulnerabilities occur when an application authenticates a user but fails to verify authorization for the requested object.

Least privilege

Least privilege means granting only the access necessary for the task. It should be applied to users, services, tokens, database roles, cloud IAM identities and administrative tooling.

04 · OAuth 2.0: delegated authorization

The roles

OAuth defines an authorization server, resource server, client and resource owner. The authorization server issues credentials; the resource server protects an API; the client requests delegated access on behalf of a user or itself.

Authorization Code flow

A browser-based authorization code flow redirects the user to the authorization server. After authentication and consent/policy evaluation, the client receives an authorization code and exchanges it for tokens. The code is not the API credential.

User → Authorization Server → authorization code → Client → token endpoint → access token → Resource Server

PKCE

PKCE binds the authorization request to a secret generated by the client. RFC 9700, published in January 2025, updates OAuth security best practice and states that public clients must use PKCE; it also recommends PKCE for confidential clients.

Redirect URI security

Redirect URIs are a critical trust boundary. Modern OAuth security guidance requires exact matching of registered redirect URIs except for specified localhost cases and prohibits open redirectors in authorization flows.

Token scope and audience

An access token should be constrained to the resources and operations it is intended to authorize. Scope describes permissions; audience identifies the intended resource or service. A token valid for one API should not automatically be accepted by another API.

Bearer versus sender-constrained tokens

A bearer token can generally be used by whoever possesses it. Sender-constrained mechanisms such as mTLS or DPoP bind token use to a cryptographic key held by the legitimate client, reducing replay risk after token theft. RFC 9700 discusses these mechanisms.

05 · OpenID Connect: authentication on OAuth

OAuth is primarily an authorization framework. OpenID Connect adds an identity layer so a client can receive authenticated identity information from an OpenID Provider.

ID token versus access token

An ID token communicates authentication information to the client. An access token is intended for a protected resource. A client should not blindly send an ID token to an API as if it were an access token.

Core validation

OIDC validation includes issuer, audience, signature, expiration and transaction-specific nonce checks as required by the flow. The client must use the provider's metadata and keys according to the protocol rather than accepting arbitrary issuer configuration.

State and nonce

State binds an authorization response to the transaction initiated by the client and helps prevent request-forgery/mix-up problems. Nonce binds an ID token to the authentication request and helps detect replay. They must be generated and checked per transaction.

Discovery and key rotation

OIDC providers publish metadata describing endpoints and supported capabilities. Signing keys rotate, so clients need a controlled key-discovery and caching strategy rather than hard-coding one public key forever.

06 · SAML and enterprise federation

Assertions

SAML uses signed XML assertions to communicate authentication and authorization-related information between an identity provider and service provider. It is common in enterprise single sign-on environments.

Trust configuration

Federation depends on both sides agreeing on entity identifiers, endpoints, signing certificates, bindings, assertion constraints and attribute mappings. A valid signature from an unexpected issuer must not be accepted.

Assertion validation

Consumers need to validate signature, issuer, audience, destination/recipient where applicable, time conditions, replay protections and the relationship between the authenticated browser transaction and assertion. XML parsing and signature handling should rely on mature libraries.

Federation versus authorization

Federation establishes an identity relationship across administrative boundaries. It does not automatically define application permissions. The service provider still needs authorization policy for what that identity can access.

07 · Policy engines and authorization architecture

PEP, PDP and PAP

A Policy Enforcement Point (PEP) intercepts access. A Policy Decision Point (PDP) evaluates policy. A Policy Administration Point (PAP) manages policy. Separating these concepts helps large systems reason about where decisions are made and how they are audited.

Centralized versus embedded policy

Central policy services provide consistency but add latency and availability dependencies. Embedded policy can be faster and resilient but risks drift across applications. Many systems combine local enforcement with centrally managed policy or policy bundles.

Policy inputs

Policy decisions should use trusted attributes. Never treat an HTTP header such as “X-Role: admin” as authoritative merely because a browser sent it. Identity claims should originate from a trusted authentication system and authorization should be evaluated server-side.

Decision explainability

Security teams need to understand why access was granted or denied. Policy systems should expose safe audit context: principal, resource, action, policy version, important attributes and decision outcome without leaking sensitive data.

08 · Zero Trust Architecture

NIST SP 800-207 describes zero trust as a shift away from implicit trust based on network location toward protection of resources and explicit authentication and authorization.

Never assume internal means trusted

A device inside a corporate network may be compromised. A cloud workload may be internet-accessible. A user may be remote. Network location therefore becomes one context signal rather than the sole basis for authorization.

Continuous evaluation

Access decisions can consider identity, device state, resource sensitivity, requested action, risk signals and session context. The exact frequency of re-evaluation depends on the system and threat model.

Policy Enforcement Point

NIST's architecture separates policy decision and enforcement functions. The enforcement point mediates access to protected resources; the decision system uses policy and contextual information to determine whether access should be permitted.

Cloud-native zero trust

NIST SP 800-207A extends the model to cloud-native and multi-cloud applications, emphasizing application and service identities in addition to network parameters.

Important: zero trust is an architecture and policy model, not a product, VPN replacement or marketing label.

09 · Privileged access management

Why privilege is different

An ordinary account may access one application; a domain administrator, cloud organization administrator or production root identity can alter the trust boundary itself. Privileged access therefore deserves stronger authentication, shorter exposure and tighter auditing.

JIT and JEA

Just-in-time (JIT) access grants privilege only when needed and for a limited period. Just enough administration (JEA) narrows what an administrator can perform rather than granting an unrestricted shell or administrator role.

Privileged identity separation

Administrators should have separate privileged identities where practical so everyday browsing and email do not occur under high-privilege credentials. Administrative workstations and hardened management paths further reduce credential exposure.

Break-glass access

Emergency accounts are necessary in some environments but should be rare, strongly protected, monitored and periodically tested. A break-glass account that nobody can use during an outage is not a recovery control.

10 · Identity lifecycle and governance

Joiner, mover, leaver

When a person joins, changes role or leaves, identity and entitlement changes should follow authoritative business events. Manual spreadsheets and tickets alone create stale-access risk when changes occur faster than administrators can process them.

Service-account lifecycle

Every non-human identity should have an owner, purpose, permissions, credential type, rotation strategy and retirement process. Shared service accounts make attribution and revocation difficult.

Access reviews

Periodic access reviews compare actual entitlements with current business need. Reviews should be risk-based: highly privileged or sensitive access deserves more scrutiny than low-impact permissions.

Separation of duties

Critical operations can require independent approval or multiple roles so one compromised identity cannot complete the entire sensitive workflow. Examples include production deployment, financial approval and security-policy changes.

11 · Sessions, tokens and credential lifecycle

Session identifiers

A session cookie is a bearer credential representing an authenticated session. It should be unpredictable, protected with Secure and appropriate HttpOnly/SameSite settings, scoped narrowly and invalidated according to the application's lifecycle.

Access tokens

Tokens should have a defined issuer, audience, scope and expiration. Short-lived access tokens reduce exposure but do not replace authorization checks. Refresh tokens require stronger lifecycle controls and rotation/reuse detection appropriate to the deployment.

Revocation

Logout, password changes, account disablement and compromise response may require session invalidation. Systems need an explicit strategy: server-side session stores, token revocation, short expiration, key rotation or combinations thereof.

Token leakage

Tokens can leak through logs, URLs, browser history, referrers, screenshots and third-party telemetry. Keep sensitive credentials out of URLs and avoid logging authorization headers or cookies.

12 · Workload and machine identity

Service identity

Modern distributed systems need to distinguish services from the human users who operate them. Workload identity can be based on certificates, signed identity tokens, cloud-managed identities or service-mesh identity.

Short-lived credentials

Short-lived workload credentials reduce the value of a stolen credential and simplify rotation. The trade-off is greater dependence on reliable identity issuance and time synchronization.

mTLS

Mutual TLS authenticates both ends of a TLS connection using certificates. It can establish service identity and encrypt transport, but application authorization still determines whether service A may perform a particular action on service B.

Identity propagation

In microservices, a request may cross many services. Systems must distinguish end-user identity from service identity and prevent confused-deputy behavior where a privileged service performs actions merely because another service asked it to.

13 · Federation, claims and trust boundaries

Claims

A claim is a statement about a principal, such as subject identifier, email, group, tenant or assurance level. Claims should have defined issuers and semantics. A string named “admin” has no security meaning without a trusted issuer and policy interpretation.

Tenant isolation

Multi-tenant applications must bind identity to tenant context and enforce tenant boundaries at every data-access layer. A valid token for tenant A must not grant access to tenant B merely because the user changes an object identifier.

Identity brokers

A broker can connect multiple identity providers and translate claims into an application's canonical identity model. The broker becomes a critical trust boundary and must be protected accordingly.

Trust transitivity

Trust should not spread farther than intended. If system A trusts system B and B accepts claims from C, A may indirectly depend on C. Mapping these relationships is essential in federated architectures.

15 · Designing an enterprise IAM architecture

A mature architecture normally separates identity proofing, authentication, federation, token issuance, policy evaluation, enforcement, privileged administration and audit. The exact products can vary; the security boundaries should remain explicit.

Identity source → Authentication → Federation/token issuance → Policy decision → Enforcement → Resource → Audit

For a web application, the identity provider may authenticate the user; the application establishes a session; every sensitive API operation performs authorization against server-side resource ownership and policy. For a cloud platform, human administrators may authenticate through a central identity provider while workloads use short-lived machine identity.

Failure isolation

IAM is a critical dependency. Design for provider outages, expired signing keys, clock skew, network partitions and accidental policy changes. Recovery accounts and local emergency procedures should be governed as carefully as ordinary authentication.

Observability

Security-relevant identity telemetry includes successful and failed authentication, MFA changes, recovery events, privilege grants, policy changes, token issuance anomalies and administrative actions. Logs should preserve enough context to reconstruct decisions without unnecessarily collecting sensitive credential material.

16 · Identity engineering rules

  • Authenticate with established standards and mature libraries.
  • Perform authorization on the server at the resource boundary.
  • Never trust client-supplied role, tenant or ownership fields without independent verification.
  • Keep ID tokens, access tokens and session credentials conceptually separate.
  • Use PKCE and exact redirect URI validation for OAuth authorization flows according to current guidance.
  • Prefer phishing-resistant authentication for high-value accounts.
  • Use short-lived workload credentials where the platform supports reliable issuance.
  • Design account recovery as a first-class security boundary.
  • Make privilege temporary and auditable where practical.
  • Plan for key rotation, provider outages and policy rollback.

17 · Mastery review — 20 questions with answers

01 · What is the difference between authentication and authorization?
Answer: Authentication establishes who or what the principal is; authorization decides what that principal may do.

Why: A valid login does not grant universal access.
02 · Why is object-level authorization necessary?
Answer: A user can be authorized for an operation without being authorized for every object. The server must check ownership, tenant, relationship or policy for the specific resource.

Why: This prevents BOLA/IDOR-style access failures.
03 · What problem does RBAC solve?
Answer: RBAC groups permissions into roles and assigns users or other principals to those roles.

Why: It provides a manageable abstraction for recurring access patterns.
04 · When is ABAC useful?
Answer: ABAC is useful when decisions depend on multiple contextual attributes such as user, device, resource sensitivity, action or time.

Why: It can express policies that would otherwise create large numbers of roles.
05 · What is OAuth 2.0?
Answer: OAuth is an authorization framework for delegated access to protected resources.

Why: It lets a client obtain scoped access without receiving the resource owner's password.
06 · Why is PKCE important?
Answer: PKCE binds the authorization code exchange to the client transaction and helps prevent authorization-code interception/injection.

Why: Current OAuth security best practice requires PKCE for public clients and recommends it broadly.
07 · What is OpenID Connect adding to OAuth?
Answer: OIDC adds an identity/authentication layer and defines the ID token and associated validation rules.

Why: OAuth access authorization and user authentication are different protocol purposes.
08 · Why should an ID token not automatically be used as an API access token?
Answer: The tokens have different intended audiences and semantics.

Why: An API should validate credentials issued for that resource and policy context.
09 · What does zero trust mean?
Answer: It removes implicit trust based solely on network location or ownership and focuses access decisions on protected resources, explicit identity and policy.

Why: Modern environments include remote users, cloud workloads and compromised internal devices.
10 · What is least privilege?
Answer: Grant only the permissions required for the task and no broader authority.

Why: It reduces the impact of credential compromise and application mistakes.
11 · What is JIT privileged access?
Answer: Privilege is granted only when required and for a constrained period.

Why: It reduces the time a high-value credential can be abused.
12 · Why are recovery flows part of authentication security?
Answer: An attacker who cannot defeat normal authentication may target password reset, email takeover, help-desk procedures or backup authenticators.

Why: The weakest alternate path can become the effective authentication mechanism.
13 · What is workload identity?
Answer: It is an identity mechanism for software workloads and services rather than human users.

Why: Distributed systems need attributable, scoped machine credentials.
14 · Why are short-lived credentials useful?
Answer: A stolen credential has a smaller useful lifetime and rotation becomes easier to automate.

Why: Reduced credential lifetime limits exposure after compromise.
15 · What is a confused deputy?
Answer: A more-privileged component is induced to use its authority on behalf of a less-trusted caller in an unintended way.

Why: Service-to-service systems can accidentally turn one component's privilege into another component's capability.
16 · Why must tenant identity be bound to authorization?
Answer: Authentication proves a principal exists, but it does not authorize access to every tenant or object that principal can name.

Why: Server-side tenant checks prevent cross-tenant data exposure.
17 · What is federation?
Answer: Federation allows one administrative domain to rely on identity assertions from another trusted domain.

Why: It enables enterprise SSO and cross-organization identity without duplicating credentials everywhere.
18 · What should identity logs capture?
Answer: Relevant authentication, recovery, privilege, policy and administrative events with principal, target, action, outcome and timing context.

Why: Identity incidents require reconstruction of who did what and which policy allowed it.
19 · What is the biggest mistake in authorization design?
Answer: Treating authentication as if it were authorization or trusting unverified client claims as policy decisions.

Why: Authorization must be independently evaluated at the resource boundary.
20 · What is the core IAM mental model?
Answer: Principal + resource + action + context + trusted identity + policy → decision, followed by enforcement, audit and lifecycle management.

Why: IAM is a continuous control system, not merely a login screen.
Completion standard: You should be able to explain an identity architecture from authentication through authorization, distinguish OAuth from OIDC, reason about federation and workload identity, and identify where a trust boundary or authorization decision can fail.
