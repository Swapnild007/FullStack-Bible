LEARNING HUB · PRACTICE

Make your brain do the work.

Practice should force recall, reasoning and debugging—not just recognition. Start with small challenges, explain your answer, then verify it by running code or checking the relevant documentation.

FOUNDATION

Web request detective

Given a URL, describe what happens from entering it in the browser to receiving and rendering the response. Identify where DNS, HTTP, browser parsing and developer tools fit.

Open DevTools → Network on a real page. Identify the document request, one stylesheet, one script and one image. Record status, method and response type.
HTML · CSS

Accessible card

Build a card with a heading, image, link and metadata. Make it usable with keyboard only and preserve a visible focus indicator.

Use semantic elements first. Test Tab order. Inspect the accessibility tree. Check that the link has a meaningful accessible name and the image has an appropriate alternative.
JAVASCRIPT

Debug the state

A list updates visually but resets after refresh. Find the missing persistence boundary and explain why the UI alone cannot preserve state across a new page load.

Trace state → serialization → storage → page load → deserialization → render. Use the Application/Storage panel and Console to verify each step.
TYPESCRIPT

Model a request state

Represent idle, loading, success and failure without allowing impossible combinations such as loading=true and error=null while data is stale.

type State = {status:'idle'} | {status:'loading'} | {status:'success'; data:Lesson[]} | {status:'error'; message:string}
SQL

Relationship query

Given learners, courses, enrollments and lessons, return every course a learner is enrolled in and the number of lessons in each course.

Think in relationships first: learner → enrollment → course → lesson. Then decide which joins and aggregate are required. Test the query with an empty enrollment set too.
BACKEND

Authorization drill

A user changes /lessons/42 to /lessons/43. Decide what the server must verify before returning lesson 43.

Authentication answers “who are you?” Authorization must answer “may this user access this exact resource?” Never rely on hiding the ID in the UI.
PRODUCTION

Failure-path test

Design tests for a lesson-completion request when the network times out, the server returns 500, validation fails, and the database write succeeds but the response is lost.

For each case define the expected user-visible state, retry policy, server behaviour and whether repeating the request is safe. Consider idempotency and duplicate writes.
AI

Prompt-injection boundary

A lesson contains text that tells the model to ignore system instructions and reveal private data. Design the application boundary.

Treat retrieved content as untrusted data. Keep secrets and authorization outside the model. Validate model outputs and make tool permissions explicit in application code.
