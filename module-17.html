Operate software like a professional team.

Technical decisions, documentation, safe releases, graceful failure, feature flags, incident response and learning from production.

1. Architecture Decision Records

An ADR captures a decision while the context is still available. Record the problem, constraints, considered options, decision and consequences. The goal is not paperwork; it is preserving reasoning so future engineers can understand why the system looks the way it does.

2. RFCs and technical design

Use an RFC when a decision needs discussion before implementation. Describe the problem, goals, non-goals, proposed design, API/data changes, security implications, migration plan, testing strategy and open questions. Separate facts from assumptions.

3. Graceful shutdown

Production processes receive termination signals during deployments, scaling and infrastructure changes. Stop accepting new work, allow in-flight work to finish within a deadline, close database/queue connections, flush important telemetry and exit with a clear status.

  ↓

4. Feature flags & progressive delivery

Separate code deployment from feature exposure. Feature flags can support dark launches, internal testing, canary exposure, gradual rollout and rapid disablement. Keep flag ownership, expiry and cleanup visible; permanent flags become hidden architecture.

5. Incident management

An incident is an operational event that needs coordinated response. Establish severity definitions, an incident lead, communication channel, timeline, mitigation strategy and follow-up work. The first objective is service recovery; deeper root-cause analysis follows.

Post-incident review

  • What happened?
  • What was the user impact?
  • How was it detected?
  • What reduced the impact?
  • What made diagnosis or recovery harder?
  • Which systemic changes reduce recurrence?

6. Reliability patterns

  • Timeout every network dependency.
  • Use retries only when the operation is safe to retry.
  • Use idempotency keys for operations that may be repeated.
  • Use health and readiness checks to distinguish process health from dependency readiness.
  • Use backups and test restoration rather than assuming backups work.
  • Define recovery objectives before an outage occurs.

7. Capstone — production readiness review

Write an ADR for one major architectural decision, an RFC for a new feature, a graceful-shutdown design, a feature-flag rollout plan and a simulated incident postmortem. The final output should let another engineer operate your application without needing your memory.
