1. Technical decisions that survive people

Professional engineering makes important decisions explicit. An Architecture Decision Record (ADR) captures the context, decision, alternatives and consequences of an architectural choice. An RFC is broader: it gives other engineers a structured proposal to challenge before implementation.

ADR

Use after a meaningful architectural decision. Preserve why, not just what the code does.

RFC

Use before a consequential change when design feedback, migration planning or cross-team agreement matters.

# ADR-004 — PostgreSQL as system of record

Status: accepted
Context: What problem and constraints exist?
Decision: What are we choosing?
Alternatives: What else was considered?
Consequences: What becomes easier/harder?
Follow-up: What must be revisited?
Engineering habit: record assumptions separately from verified facts. An assumption that affects architecture should eventually become a measurable or testable statement.

RFC review checklist

  • Problem and user impact are explicit.
  • Goals and non-goals prevent scope drift.
  • Architecture and data-flow are understandable.
  • Security, privacy and failure modes are addressed.
  • Migration and rollback paths exist.
  • Testing and observability are part of the design.
  • Open questions have owners.

2. Safe change and progressive delivery

Deployment and release are different operations. Deployment puts code into an environment; release makes behavior available to users. Separating them gives a team more control over exposure.

commit → build → test → deploy dark → verify → expose gradually → observe → expand → complete / rollback

Feature flags

Control exposure independently of deployment. Define owner, purpose, audience, kill behavior and expiry.

Canary

Expose a change to a limited population first. Compare predefined health signals before expanding.

Rollback

Return to a known-good behavior quickly. Prefer reversible changes and compatible database migrations.

Progressive delivery

Use staged exposure with explicit gates instead of relying on a single “deploy succeeded” signal.

Flag debt is real engineering debt. A flag without an owner or removal plan becomes permanent conditional architecture and increases the number of states that must be tested.

Release gate

  • Build artifact is reproducible.
  • Automated checks pass.
  • Migration compatibility is verified.
  • Telemetry exists before exposure increases.
  • Rollback or mitigation is known.
  • Owner is available during the change window.

3. Reliability engineering

Reliability is not “never failing.” Production systems encounter dependency failures, traffic spikes, software defects, configuration mistakes and infrastructure disruptions. Engineering makes the failure mode bounded, observable and recoverable.

Timeouts

Every remote dependency needs a bounded wait. An unbounded wait can consume threads, connections and memory.

Retries

Retry only when the operation is safe and the failure may be transient. Use bounded exponential backoff and jitter.

Circuit breaking

Stop repeatedly calling an unhealthy dependency when continued calls increase pressure.

Bulkheads

Keep one failing workload from exhausting shared capacity needed by unrelated work.

Graceful degradation

Preserve the core user journey when an optional dependency is unavailable. Stale or partial data can be preferable to total failure.

Backpressure

Bound queues and admission when downstream capacity is lower than incoming work.

For distributed systems, AWS guidance explicitly recommends patterns including graceful degradation, throttling, controlled retries, fail-fast behavior, client timeouts and emergency levers.

Graceful shutdown

SIGTERM
  ↓
stop accepting new work
  ↓
finish bounded in-flight work
  ↓
flush important telemetry
  ↓
close connections / consumers
  ↓
exit before deadline

A shutdown path should be tested, not merely written. Verify what happens to HTTP requests, queue consumers, database transactions, scheduled jobs and telemetry when a process terminates.

4. Observability: know what production is doing

Observability is the ability to understand internal system behavior from emitted outputs. OpenTelemetry currently defines traces, metrics and logs as core signals, with baggage for context propagation.

Metrics

Numerical measurements over time: request rate, latency, error rate, queue depth, saturation and business outcomes.

Logs

Structured records of events. Include useful context without leaking secrets or unnecessary personal data.

Traces

Follow a request across boundaries so latency and failures can be attributed to a specific operation or dependency.

Correlation

Carry request/trace context across services so one user operation can be reconstructed across telemetry.

From telemetry to action

user symptom
    ↓
service-level signal
    ↓
metric / trace / log
    ↓
correlate deployment + dependency + traffic
    ↓
form hypothesis
    ↓
mitigate
    ↓
verify recovery
Do not monitor everything equally. Start with signals tied to user-visible behavior and the resources required to deliver it.

5. SLOs, SLIs and error budgets

An SLI is the measured indicator; an SLO is the target for that indicator over a defined period. An error budget is the amount of unreliability permitted by the SLO. This gives product and engineering teams a common language for balancing feature delivery and reliability work.

SLI: successful requests / eligible requests
SLO: 99.9% over 30 days
error budget: 0.1% of eligible requests

Define the population, measurement window, exclusions and user impact before calculating a target. Avoid choosing a “number of nines” simply because it sounds impressive.

Good SLO questions

  • What user journey does this measure?
  • What counts as success?
  • Which traffic is included?
  • What time window matters?
  • What action follows when the budget is being consumed?
  • Can the team actually measure it reliably?

6. Incident response

An incident is an operational event requiring coordinated response. The response system should reduce confusion while the technical team restores service. NIST SP 800-61 Rev. 3, published in April 2025, supersedes Rev. 2 and places incident response within broader cybersecurity risk management.

Incident lead

Coordinates priorities, delegates work and prevents parallel responders from losing the shared picture.

Communications

Maintain a concise timeline and stakeholder updates. State what is known, unknown and being tested.

Operations

Investigate and mitigate the active failure. Prefer reversible, low-risk actions first.

Recorder

Capture timestamps, hypotheses, commands, changes and evidence while responders work.

Incident flow

detect → declare → assign roles → assess impact → stabilize → communicate → verify → recover → close → learn
Do not improvise irreversible production changes under pressure. Use a known mitigation, record the action, define the expected signal and verify the result.

Post-incident review

  • What happened and when?
  • What was the user/business impact?
  • How was it detected?
  • Which signals were useful or missing?
  • Which mitigation reduced impact?
  • Which conditions made the failure possible?
  • What changes have owners and due dates?

7. Recovery and disaster readiness

Backups are not a recovery strategy until restoration has been exercised. Define recovery objectives from business impact, then choose and test an implementation that can meet them. AWS defines RTO as the maximum acceptable delay between interruption and restoration, and RPO as the maximum acceptable time since the last recovery point.

RTO

How long can the service be unavailable before the business objective is missed?

RPO

How much recent data can the business afford to lose after a recovery event?

Backup

A recoverable copy. Verify retention, integrity, access and restoration procedure.

Restore test

Evidence that a backup can actually become a usable system or dataset.

Recovery exercise

  1. Choose a failure scenario.
  2. State RTO/RPO targets.
  3. Execute the documented recovery procedure.
  4. Measure actual recovery time and data loss.
  5. Record gaps and unexpected dependencies.
  6. Fix the procedure or architecture.
  7. Repeat after significant changes.

AWS recommends defined recovery strategies and testing them to validate that the implementation can meet recovery objectives.

8. Operational readiness

Before a system becomes someone else's production responsibility, another engineer should be able to answer: What does it do? How is it deployed? What can fail? How do we know? How do we roll it back? How do we recover? Who owns it?

Runbook

Concrete operational procedure for common tasks and known failure modes.

Service ownership

Clear team, escalation path and operational responsibility.

Health model

Liveness, readiness, dependency health and user-facing success should not be conflated.

Change record

Know what changed before a regression, outage or unusual metric.

Production-readiness review

  • Architecture and ADRs are discoverable.
  • Threat model and security controls are documented.
  • Critical user journeys have measurable SLIs/SLOs.
  • Logs, metrics and traces cover important paths.
  • Alerts are actionable and have owners.
  • Deployment, rollback and migration plans are tested.
  • Backup restoration is tested.
  • Incident and escalation procedures are documented.
  • Known limitations and failure modes are explicit.

9. Deliberate failure drills

Use controlled failures to test whether your assumptions are true. Start in a safe environment and define abort conditions before injecting a failure.

Drill A — dependency outage

Disable an optional dependency. Verify graceful degradation, timeout behavior and user-visible messaging.

Drill B — slow dependency

Introduce latency. Verify timeouts, bounded queues and retry behavior.

Drill C — bad release

Deploy a deliberately faulty change behind a flag. Exercise detection, disablement and rollback.

Drill D — recovery

Restore a known backup into an isolated environment and measure the real recovery path.

Evidence beats confidence. A recovery procedure, backup, alert or rollback plan is only an operational capability after it has been exercised.

Turn the Learning Hub from Module 12 into a service that another engineer could operate.

11. Capstone — Professional Engineering Review

Produce a complete operational package for a production Learning Hub. Your reviewer should be able to understand the architecture, assess a proposed change, release it safely, observe it, respond to failure and recover the system without relying on undocumented tribal knowledge.

Required evidence

  • Architecture diagram and ADR.
  • RFC with review questions and resolved decisions.
  • Feature-flag rollout and rollback plan.
  • Deployment checklist and release gates.
  • SLI/SLO definition with measurement method.
  • Observability plan covering logs, metrics and traces.
  • Incident response procedure and sample timeline.
  • Runbook for at least two failure modes.
  • RTO/RPO and tested recovery procedure.
  • Postmortem from a controlled failure drill.
Definition of professional: the artifact is not complete because you wrote it. It is complete when another engineer can use it, challenge it and reproduce the important operational steps.
