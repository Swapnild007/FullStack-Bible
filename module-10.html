The production mental model

Production is a system, not a final button.

Production readiness means the application can be deployed repeatedly, operated safely, observed when something goes wrong, and improved without guessing. Security, performance, testing, and deployment are connected: a fast application with weak security is not ready; a secure application that cannot be tested or recovered is not ready either.

01 · Security

Assume the application will be attacked.

Security is a design and engineering discipline, not a checklist added at the end. OWASP's current Top 10:2025 identifies risks including broken access control, security misconfiguration, software supply chain failures, cryptographic failures, injection, authentication failures, integrity failures, logging failures, and mishandling exceptional conditions. OWASP ASVS 5.0 provides a much more detailed basis for verifying technical security controls. citeturn2search2turn1search3

Protect the boundaries

Every boundary is an opportunity for untrusted input: browser → API, API → database, application → third-party service, developer → repository, and CI → deployment environment.

  • Validate data at the server boundary.
  • Authorize every protected operation, not just the page that links to it.
  • Use parameterized database access rather than constructing SQL from strings.
  • Keep secrets out of source control and client-side bundles.
  • Use HTTPS for application traffic.
  • Return safe errors to users while retaining useful diagnostic detail in protected logs.

OWASP's security guidance treats headers, TLS, authentication, authorization, logging, and secure coding as layers rather than one magic control. citeturn0search6turn0search7

Security headers

Response headers can give the browser additional instructions. Content Security Policy can restrict where scripts and other resources may come from and provides defense in depth against classes of injection attacks. Use a policy appropriate to the actual application; do not blindly paste a permissive policy from a tutorial. citeturn0search2

Content-Security-Policy: default-src 'self';
  object-src 'none';
  base-uri 'self';
  frame-ancestors 'none';
  upgrade-insecure-requests

Other controls may include HSTS, clickjacking protection, MIME-type protections, and carefully configured referrer behavior. The correct set depends on the application and its dependencies.

Secrets and configuration

Separate code from environment-specific configuration. Public configuration may be exposed to the browser; private credentials must remain server-side.

# .env.example
DATABASE_URL=
SESSION_SECRET=
PAYMENT_PROVIDER_KEY=

# Never commit real secrets.
# .env.local
# .env.production
# should be protected by your deployment platform.
Never use the browser as a secret store. A value delivered to client-side JavaScript should be treated as visible to the user. Environment variables are not automatically secret merely because they are called environment variables.

Dependency and supply-chain security

Your application contains code you did not write. Dependency risk includes vulnerable packages, compromised maintainers, malicious packages, CI/CD compromise, and unsafe build configuration. OWASP recommends dependency inventory, monitoring, version control, automated security checks, and stronger supply-chain controls. An SBOM provides a machine-readable inventory of software components and can be generated as part of the build. citeturn2search0turn2search1

  • Commit and review lockfiles.
  • Remove dependencies you do not need.
  • Review security advisories.
  • Do not blindly accept automated dependency upgrades.
  • Protect CI credentials with least privilege.
  • Consider SCA/SAST/secret scanning in CI.
02 · Performance

Make the application feel fast.

Performance is about the experience of real users, not just a benchmark on your laptop. Measure loading, responsiveness, visual stability, server response, network transfer, JavaScript execution, database latency, and the effect of third-party code.

Core Web Vitals

The current Core Web Vitals focus on loading, interactivity, and visual stability: LCP, INP, and CLS. The commonly recommended “good” thresholds are LCP ≤ 2.5 seconds, INP ≤ 200 ms, and CLS ≤ 0.1, evaluated at the 75th percentile. Field data matters because lab tests cannot reproduce every real interaction and network condition. citeturn1search10turn1search6

MetricWhat it tells youTypical investigation
LCPHow quickly the main content appearsServer response, images, fonts, render-blocking resources
INPHow responsive interactions feelLong JavaScript tasks, event handlers, rendering work
CLSWhether the page unexpectedly movesImage dimensions, injected content, fonts, layout changes

Reduce work before adding hardware

  • Send less JavaScript.
  • Load expensive features only when needed.
  • Optimize images and reserve their layout space.
  • Remove unnecessary third-party scripts.
  • Use server rendering and framework caching where appropriate.
  • Paginate large datasets.
  • Fix slow database queries and add indexes based on measured access patterns.
  • Keep backend and database regions appropriately close when the architecture requires it.

Next.js's current production guidance specifically calls out caching, layouts, optimized images, error handling, security, bundle analysis, Lighthouse, and production builds. citeturn1search0

HTTP caching

Caching can prevent repeated work by reusing responses. Use Cache-Control deliberately and understand the difference between fresh caching, revalidation, private data, and immutable static assets. ETag can let a client revalidate a representation and receive 304 Not Modified when it has not changed. citeturn0search0turn0search3turn0search5

# Static fingerprinted asset
Cache-Control: public, max-age=31536000, immutable

# Personalized response
Cache-Control: no-cache, private

# Sensitive response that must not be stored
Cache-Control: no-store
Do not cache by reflex. A response containing one user's private information must never become a shared response that another user can receive.

Measure, then optimize

Use browser DevTools Performance and Network panels, Lighthouse, real-user metrics, server timing, application logs, and database query analysis. Capture a baseline before changing code. After the change, measure again. Performance work without measurement easily becomes premature optimization.

03 · Testing

Test what users depend on.

Testing is a confidence system. Different tests answer different questions, so a production application normally needs multiple layers rather than one enormous test suite.

Unit

Tests a small piece of logic in isolation. Fast and useful for calculations, transformations, validation rules, and pure functions.

Integration

Tests several pieces working together, such as an API handler with validation and a database boundary.

End-to-end

Tests a real user journey through the application, browser, backend, and relevant services.

Security tests

Verify authorization, input handling, session behavior, headers, secrets, dependency risks, and important abuse cases.

Test behavior, not implementation trivia

Playwright recommends testing user-visible behavior and keeping tests isolated so one test does not contaminate another through cookies, storage, or shared state. citeturn0search1

test('learner can complete a lesson', async ({ page }) => {
  await page.goto('/lessons/sql-foundations');
  await page.getByRole('button', { name: 'Mark complete' }).click();
  await expect(page.getByText('Completed')).toBeVisible();
});

The selector describes what the user interacts with instead of depending on an internal CSS class or JavaScript implementation detail.

Reliable test design

  • Give each test its own data and state.
  • Avoid arbitrary timeouts when an explicit condition can be awaited.
  • Use deterministic test data.
  • Keep failures diagnosable.
  • Test important failure paths, not only successful paths.
  • Run tests in CI on every meaningful change.
  • Keep slow end-to-end coverage focused on high-value journeys.

Test the failure paths

For the Learning Hub, test at least: unauthenticated access, forbidden access, malformed input, duplicate email, missing resource, expired session, database failure, slow network, empty state, and a failed deployment health check.

Production habit: every serious bug should become either a regression test or a documented reason why an automated test is not appropriate.
04 · Delivery

Turn commits into repeatable releases.

Deployment should not depend on remembering a sequence of manual commands. A basic CI/CD pipeline verifies a change, creates a production artifact, and releases it through a controlled path.

PushCommit
CheckLint + types
TestAutomated suite
BuildProduction artifact
ReleaseDeploy

CI should be boring

A healthy pipeline is predictable. A typical web application pipeline can run:

  1. Install dependencies from the lockfile.
  2. Run formatting/lint checks.
  3. Run TypeScript checking.
  4. Run unit/integration tests.
  5. Run security and dependency checks.
  6. Build the production application.
  7. Run a smoke or end-to-end test against the resulting environment.

Security checks are not a replacement for review, and automated scanners can produce false positives and false negatives. Treat their output as evidence that needs engineering judgment. citeturn2search0

Environment separation

EnvironmentPurposeTypical data
DevelopmentFast local iterationLocal/test data
Preview/StagingRelease verificationSafe representative data
ProductionReal usersReal protected data

Never copy production secrets or sensitive production data into a development environment simply because it is convenient. Make configuration explicit and protect each environment separately.

Deployment strategies

Learn the concepts before memorizing a provider:

  • Rolling: replace instances gradually.
  • Blue/green: keep two environments and switch traffic.
  • Canary: expose a new release to a controlled portion of traffic.
  • Rollback: return to a known-good release when a new one fails.

For Next.js, current documentation supports deployment as a Node.js server, Docker container, static export, or through platform adapters; Node.js and Docker support the full feature set, while static export has limitations. citeturn1search8

05 · Deployment & operations

Shipping is the beginning of operation.

Once users depend on your application, you need visibility into its behavior. Logs, metrics, traces, health checks, alerts, and a recovery plan turn production from a black box into an operable system.

Logs

Detailed events useful for debugging. Avoid passwords, tokens, secrets, and unnecessary personal data.

Metrics

Numbers over time: request rate, error rate, latency, database duration, queue depth, and resource use.

Traces

Follow one request across services to find where time or failure was introduced.

Health checks

Give deployment and infrastructure systems a safe way to determine whether the application is alive and ready.

Error handling

Production errors should be useful without exposing internals. Give users a stable message and give operators a correlation/request ID that can connect the user-visible failure to protected logs.

HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "Something went wrong.",
    "requestId": "req_8f3c..."
  }
}

Backups and recovery

A backup that has never been restored is an assumption, not a recovery plan. Define what data must be recoverable, how often backups run, how long they are retained, who can restore them, and how restoration is tested. Understand the difference between RPO (how much recent data you can afford to lose) and RTO (how quickly service should be restored).

Release checklist

  • Production build succeeds.
  • Critical tests pass.
  • Dependencies have been reviewed.
  • No secrets are committed.
  • Environment variables are configured.
  • Database migrations are reviewed and recoverable.
  • Security headers and HTTPS are verified.
  • Performance baseline is understood.
  • Logs and alerts work.
  • Rollback path is known.
  • Smoke test passes after deployment.
Capstone lab · Productionize the Learning Hub

Take the application from “works” to “operable.”

Use the Learning Hub from Modules 07–09. Your job is to prepare a release that another developer could deploy without relying on your memory.

Phase 1 — Threat model

  1. List valuable assets: accounts, sessions, course data, learner progress, database credentials.
  2. List trust boundaries.
  3. Identify abuse cases: account takeover, unauthorized course edits, IDOR, injection, secret leakage, dependency compromise.
  4. Choose concrete controls and tests for each important risk.

Phase 2 — Performance baseline

  1. Run a production build.
  2. Measure Lighthouse and Core Web Vitals.
  3. Inspect Network and Performance panels.
  4. Identify the largest JavaScript, image, API, and database costs.
  5. Make one measured improvement and record before/after results.

Phase 3 — Test pyramid

  1. Add unit tests for core learning/progress logic.
  2. Add integration tests for API validation and authorization.
  3. Add end-to-end tests for login, course access, lesson completion, and forbidden actions.
  4. Add at least one regression test for a deliberately discovered bug.

Phase 4 — CI/CD

  ↓

  ↓

  ↓

  ↓

Document the pipeline so a new developer can understand what blocks a release and why.

Phase 5 — Operations drill

Deliberately introduce a controlled failure: a broken API dependency, invalid environment variable, or failing health check. Observe the failure, identify it through logs/metrics, restore the previous known-good state, and document the recovery steps.

Capstone outcome: you should finish with a repeatable build, automated checks, measurable performance, explicit security controls, a deployment path, a rollback path, and enough observability to diagnose a real failure.
